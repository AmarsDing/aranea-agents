## 0. 指导思想

### 0.1 核心洞察

> 每个记忆块语意完整，相互关联，当某个记忆块改动，自动复盘相关联记忆块是否需要更新。
> —— `docs/_deprecated/需求/notes.md`

当前 L0-L4 五层架构已落地"存储"和"检索"，但记忆的**演化**环节严重缺失——记忆只会被创建和衰减，不会合并、修正、关联更新。这导致：

- 用户换了工作城市，Agent 仍推荐北京的通勤路线
- 用户纠正了一条偏好，相关联的旧偏好仍然生效
- 长期使用后记忆库膨胀为噪声仓库，检索质量持续下降

### 0.2 与系统统一思想的对齐

| 统一原则 | 本需求如何对齐 |
|----------|---------------|
| 用户拥有最终控制权 | 联动更新产生的变更必须可审计、可回滚；高风险变更仍需人工审批 |
| 可解释优先 | 每条联动更新的链路可追溯，用户能理解"为什么 A 变了导致 B 也变了" |
| 隐私默认收紧 | 时间线变更、联动更新均遵守 scope 权限；PII 事实的联动受额外限制 |
| 数据密集但不压迫 | 联动更新在后台静默执行，用户只在"待处理"区域看到需审批的变更 |

## 1. 心智模型与边界

### 1.1 新增概念

| 概念 | 用户理解 | 类比 |
|------|----------|------|
| **语义时间线** | 记忆有"实际发生时间"，不只是"对话中提到的时间" | "我上周换了工作"中的"上周"是语义时间 |
| **持续性记忆** | 一段持续有效的事实（如"2023-2025 住在北京"） | 类似简历上的时间段 |
| **关联链接** | 记忆之间的关联关系（语义/时间/因果/矛盾） | 类似笔记之间的双向链接 |
| **联动更新** | 一条记忆变更后，自动评估并更新相关联记忆 | 类似"改了工作城市，通勤方式自动跟着变" |
| **记忆巩固** | 后台整理记忆：去重、合并、提炼、消歧 | 类似"睡一觉后把零散印象整理成清晰记忆" |
| **印迹成熟** | 频繁被使用的记忆越来越牢固 | 类似"反复练习的技能不容易忘" |
| **波动性** | 不同类型事实的变化速度不同 | "出生地"不会变，"当前心情"随时变 |

### 1.2 与现有模块的边界

| 边界 | 属于本需求 | 不属于本需求 |
|------|-----------|-------------|
| 与 L3.md | L3 fact 的时间线字段、关联链接、联动更新 | L3 基础 CRUD、向量检索、scope 管理 |
| 与 L4.md | L4 relation 的双时态模型、冲突自动失效 | L4 基础实体/关系管理、图谱可视化 |
| 与 memory.md | Memory-Agent 后台守护、巩固调度 | Memory Center UX、权限、信息架构 |
| 与 memory-optimization-2026-05-26.md | 不重叠；MEM-OPT-01~06 是代码级修复，本需求是业务能力升级 | — |

### 1.3 非目标

- 不改变 L0/L1 的现有行为
- 不引入新的存储引擎（继续使用 SQLite + pgvector）
- 不做参数化记忆（编码进模型权重）或隐空间记忆
- 不做多模态记忆（后续需求）
- 不做跨 Agent 记忆共享（后续需求）

## 2. 需求清单

### 2.1 功能需求

| # | 需求 | 必要性 | 业务价值 |
|---|------|--------|----------|
| F-01 | L3 fact 支持语义时间线（实际发生时间 + 持续性区间） | 必须 | 解决"Agent 不知道事实何时有效" |
| F-02 | L3 fact 支持关系波动性分类（静态/动态/瞬态） | 必须 | 解决"出生地和工作地用同样衰减策略" |
| F-03 | L4 relation 支持双时态模型（valid_from/valid_until） | 必须 | 解决"旧关系不失效，新关系不生效" |
| F-04 | L3 fact 之间支持关联链接（语义/时间/因果/矛盾） | 必须 | 实现"记忆块相互关联" |
| F-05 | 记忆联动更新：一条 fact 变更后自动评估并更新关联 fact | 必须 | 实现"自动复盘相关联记忆块" |
| F-06 | L3-L4 联合推理：fact 检索与图谱遍历交叉验证 | 必须 | 解决"fact 和图谱是两套独立系统" |
| F-07 | 睡眠期巩固：后台去重、合并、持续性记忆构建、实体消歧 | 必须 | 解决"记忆库长期使用后膨胀为噪声" |
| F-08 | 干扰性遗忘：基于语义冲突的动态衰减，替代固定衰减因子 | 必须 | 解决"被取代的旧事实和新事实衰减一样慢" |
| F-09 | 印迹成熟：频繁被召回的记忆 importance 递增 | 应该 | 解决"重要记忆和冷门记忆衰减一样快" |
| F-10 | 提取再巩固：fact 被召回时触发过时检查和冲突评估 | 应该 | 解决"过时记忆被反复召回但无人修正" |
| F-11 | Memory-Agent 后台守护：统一记忆管理入口 | 应该 | 解决"记忆管理分散在多个独立 Worker" |
| F-12 | Agent 自主记忆编辑：Agent 可通过 Tool 主动写入/更新 L3/L4 | 应该 | 解决"Agent 对自身记忆零控制力" |
| F-13 | 记忆提取增加对话摘要上下文 | 可以 | 提升长对话中的提取质量 |
| F-14 | 标准化评测：接入 LongMemEval / LoCoMo 基准 | 必须 | 解决"无法量化记忆质量" |

### 2.2 非功能需求

| # | 需求 | 目标值 |
|---|------|--------|
| NF-01 | 联动更新延迟 | 从 fact 变更到关联 fact 评估完成 < 5s（低风险自动执行）；人工审批 < 24h |
| NF-02 | 巩固吞吐 | 单 tenant 每小时可巩固 ≥ 1000 条 fact |
| NF-03 | 巩固精度 | 去重合并的保留精度 ≥ 95%（不丢失有效信息） |
| NF-04 | 存储缩减 | 巩固后 fact 存储量缩减 ≥ 30% |
| NF-05 | 检索不退化 | 新增时间线/链接字段后，recall 延迟增加 < 10% |
| NF-06 | 递归深度保护 | 联动更新最大递归深度 3，防止无限循环 |
| NF-07 | 审计完整 | 所有联动更新、巩固操作、冲突解决均写入审计日志 |
| NF-08 | 多租户隔离 | 巩固/联动更新按 tenant 隔离，互不影响 |

## 3. 时间感知记忆

### 3.1 用户故事

**US-T01**：作为用户，当我告诉 Agent"我上周换了工作"时，Agent 应该：
- 记录"换了工作"的实际发生时间（上周），而非对话时间
- 将旧的"工作于 X 公司"标记为已结束
- 后续推荐与新工作相关的信息

**US-T02**：作为用户，当我问"我之前在哪里工作"时，Agent 应该能回答历史事实，而非只记住当前状态。

**US-T03**：作为用户，当我纠正"我现在不住北京了，搬到纽约了"时，Agent 不应再推荐北京的交通方式和天气。

### 3.2 功能规格

#### 3.2.1 L3 语义时间线

- 每条 fact 可选关联语义时间区间（开始时间、结束时间）
- 结束时间为空表示"持续有效"
- 提取阶段由 LLM 从对话中识别语义时间
- 检索时优先返回"当前有效"的事实；时序推理时返回历史事实

#### 3.2.2 L4 双时态关系

- 每条 relation 记录生效时间和失效时间
- 新 relation 与旧 relation 冲突时，自动将旧 relation 标记为失效
- 失效的 relation 不删除，保留用于历史查询
- 高风险变更（身份变更等）仍走级联提案审批

#### 3.2.3 关系波动性分类

- 每条 fact/relation 自动分类波动性等级（静态/慢变/快变/瞬态）
- 不同波动性对应不同的衰减和更新策略
- 静态事实（如"出生在"）不衰减；瞬态事实（如"今天心情"）快速衰减

### 3.3 验收标准

- [ ] 用户说"我上周换了工作"后，旧工作事实被标记为已结束，新工作事实生效
- [ ] 用户问"我之前在哪里工作"时，Agent 能返回历史事实
- [ ] 用户纠正居住城市后，Agent 不再推荐旧城市的交通/天气
- [ ] 静态事实（出生地等）不随时间衰减

## 4. 记忆联动更新

### 4.1 用户故事

**US-L01**：作为用户，当我的工作地点从北京变为纽约时，Agent 应自动更新与"北京"关联的通勤方式、附近餐厅、天气关注等记忆，而不是等我逐条纠正。

**US-L02**：作为用户，当我在 Memory Center 修改一条 fact 时，我想看到"这条修改可能影响哪些其他记忆"的提示。

**US-L03**：作为 Agent Owner，我想审批高风险的联动更新（如身份变更导致的连锁修改），低风险的自动执行即可。

### 4.2 功能规格

#### 4.2.1 L3 关联链接

- fact 之间可建立关联链接，类型包括：语义关联、时间关联、因果关联、矛盾关联
- 新 fact 写入时，自动检索语义相似的已有 fact，由 LLM 判断关联类型
- 关联链接支持双向遍历

#### 4.2.2 联动更新引擎

- 当一条 fact 被变更（内容修改、时间线变更、状态变更）时，自动查询其关联 fact
- 对每条关联 fact，由 LLM 评估是否需要更新
- 低风险更新自动执行；高风险更新生成提案等待审批
- 联动更新链路写入审计日志，可追溯
- 最大递归深度 3，防止无限循环

#### 4.2.3 L3-L4 联合推理

- L3 语义检索结果中的实体，在 L4 图谱中查找关联路径
- 图谱遍历发现的新实体，反查 L3 中的相关 fact
- 合并去重后按综合评分排序

### 4.3 验收标准

- [ ] 工作地点变更后，与旧地点关联的通勤/餐厅/天气记忆被自动评估和更新
- [ ] 用户在 Memory Center 修改 fact 时，能看到"可能影响 N 条关联记忆"的提示
- [ ] 低风险联动更新自动执行，高风险更新生成审批提案
- [ ] 联动更新链路可在审计日志中完整追溯
- [ ] 联动更新不会产生无限递归

## 5. 仿生记忆生命周期

### 5.1 用户故事

**US-B01**：作为用户，我希望 Agent "越用越懂我"——经常被提及的偏好应该越来越牢固，而不是和冷门记忆一样慢慢衰减。

**US-B02**：作为用户，我希望 Agent 能自动"整理记忆"——重复的记忆被合并，过时的记忆被归档，而不是记忆库越来越乱。

**US-B03**：作为用户，当 Agent 回忆起一条可能过时的信息时，应该主动验证而非盲目使用。

### 5.2 功能规格

#### 5.2.1 睡眠期巩固

- 后台低峰期自动执行：去重合并、持续性记忆构建、Episode→Fact 二次提炼、图谱实体消歧、链接补全
- 巩固操作不删除原始数据，而是标记状态（合并/归档）
- 巩固结果写入审计日志

#### 5.2.2 干扰性遗忘

- 替代当前的固定衰减因子
- 衰减速率由三个因素决定：波动性（静态事实不衰减）、访问频率（频繁召回的衰减更慢）、语义干扰（被新事实取代的旧事实加速衰减）
- 被新事实取代的旧事实不立即删除，而是标记为"已过时"

#### 5.2.3 印迹成熟

- 每次 fact 被召回时，递增访问计数和刷新最后访问时间
- 访问计数越高，importance 越不容易衰减
- 用户可看到每条 fact 的"被使用次数"

#### 5.2.4 提取再巩固

- fact 被召回时触发轻量检查：是否已过时？是否与同 scope 内其他 fact 冲突？
- 过时事实标记降权；冲突事实触发联动更新评估
- 高波动性事实超过一定时间未验证时标记为"待验证"

### 5.3 验收标准

- [ ] 频繁被召回的 fact 的 importance 高于同等初始值但从未被召回的 fact
- [ ] 巩固后 fact 存储量缩减 ≥ 30%，且不丢失有效信息（保留精度 ≥ 95%）
- [ ] 被新事实取代的旧事实的衰减速度明显快于未被取代的事实
- [ ] 超过 30 天未被验证的高波动性事实被标记为"待验证"
- [ ] 所有巩固操作可在审计日志中追溯

## 6. Memory-Agent 后台守护

### 6.1 用户故事

**US-M01**：作为 Workspace Admin，我希望有一个统一的"记忆管家"在后台运行，自动整理记忆，而不是记忆管理分散在多个定时任务中互不协调。

**US-M02**：作为 Agent Owner，我希望能配置记忆管家的行为（开关、频率、策略），而不是所有 Agent 用同一套固定策略。

### 6.2 功能规格

#### 6.2.1 统一管理入口

- Memory-Agent 作为独立后台服务，随系统启动，可配置开关
- 统一调度：实时监控（即时提取）、睡眠巩固（低峰整理）、质量审计（定期评估）、策略自优化（根据审计结果调整参数）

#### 6.2.2 睡眠巩固调度

- 触发条件：系统低负载 + 距上次巩固超过最小间隔
- 租户隔离：每个 tenant 独立巩固队列
- 增量处理：只处理自上次以来的增量数据
- 超时保护：单次巩固最长 5 分钟

#### 6.2.3 质量审计

- 定期抽样评估记忆提取质量、检索相关性、衰减策略有效性
- 生成审计报告，包含改进建议
- 审计结果驱动策略自优化

### 6.3 验收标准

- [ ] Memory-Agent 可通过配置开关启用/禁用
- [ ] 巩固任务按 tenant 隔离，互不影响
- [ ] 单次巩固超时后保存进度退出，不丢失数据
- [ ] 质量审计报告可在 Memory Center 查看

## 7. Agent 自主记忆编辑

### 7.1 用户故事

**US-E01**：作为 Agent，我想在对话中主动记住用户明确告知的重要信息，而不是只能等后台异步提取。

**US-E02**：作为 Agent Owner，我担心 Agent 自主写入记忆可能产生错误信息，我需要安全控制。

### 7.2 功能规格

#### 7.2.1 Memory Tool

- 为 Agent 提供 Memory Tool：`memory_fact_add`、`memory_fact_update`、`memory_fact_search`、`memory_entity_link`
- 需 Agent 配置显式开启，默认关闭
- 写入操作经过 PII 检测和冲突检测
- 低置信度写入降级为"候选事实"，等待巩固验证

#### 7.2.2 写入安全

- 所有 Agent 写入操作写入审计日志
- 与现有 fact 冲突时触发冲突解决流程
- PII 内容自动脱敏处理

### 7.3 验收标准

- [ ] Agent 可通过 Tool 主动添加 fact，fact 出现在 Memory Center
- [ ] Agent 写入的低置信度 fact 被标记为"候选"，不影响即时检索
- [ ] Agent 写入的 PII 内容被自动脱敏
- [ ] 所有 Agent 写入操作可在审计日志中追溯

## 8. 标准化评测

### 8.1 用户故事

**US-R01**：作为架构师，我需要量化记忆系统的质量，而不是依赖主观感受。

**US-R02**作为开发者，我每次修改 memory 模块后需要自动验证记忆质量没有退化。

### 8.2 功能规格

- 接入 LongMemEval（500 题，6 类）和 LoCoMo（1,540 题，4 类）评测基准
- 建立 CI 评测流水线：模块变更后自动跑分
- 重点关注时序推理和多会话推理两个维度
- 得分低于阈值的变更阻断合并

### 8.3 验收标准

- [ ] LongMemEval 评测可自动运行并输出各维度得分
- [ ] 时序推理维度得分高于无时间感知基线 ≥ 10pp
- [ ] CI 评测流水线集成到合并流程

## 10. 风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| 联动更新 LLM 调用成本 | 每次联动评估需 LLM 判断，可能增加 token 消耗 | 低风险更新用规则引擎；仅高风险更新调用 LLM |
| 巩固任务与在线请求竞争 | 巩固可能占用 DB 资源 | 低峰期执行；超时保护；增量处理 |
| 时间提取不准确 | LLM 可能错误解析"上周""去年"等模糊时间 | 保留 dialogue_time 作为兜底；时间置信度字段 |
| 联动更新误判 | LLM 可能错误判断关联 fact 需要更新 | 高风险变更需人工审批；所有变更可回滚 |
| 递归联动爆炸 | A→B→C→D... 无限链式更新 | 最大深度 3；单次联动总 LLM 调用上限 |

## 11. 关键结论

本需求的核心是补全记忆的**演化**环节——从"写入→衰减→删除"升级为"形成→巩固→演化→检索/再巩固"的完整生命周期。

三个最重要的业务能力：

1. **时间感知**：让 Agent 知道事实"何时有效"，不再混淆过去和现在
2. **联动更新**：让记忆块相互关联，一处变更自动复盘关联记忆
3. **仿生生命周期**：让记忆像人类记忆一样巩固、成熟、遗忘，而非机械衰减

这三项能力共同实现了原始设计愿景中的"神经记忆系统"。

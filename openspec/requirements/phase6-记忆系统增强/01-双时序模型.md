# 01 — 双时序模型

> **借鉴来源**：Zep/Graphiti（Bi-Temporal Knowledge Graph）
> **优先级**：高（投入小、收益大）
> **影响层**：L3 语义记忆、L4 知识图谱
> **最后更新**：2026-06-06

---

## 一、需求文档

### 1.1 背景

当前 L3 Fact 和 L4 Relation 仅有 `created_at`/`updated_at` 时间戳，无法区分：
- **事实何时为真**（valid_time）vs **系统何时记录**（transaction_time）
- **事实何时失效**（invalid_at）vs **系统何时得知失效**（expired_at）

这导致：
1. **过时事实复活**：用户从 Adidas 改选 Puma，但"喜欢 Adidas"仍被语义检索召回
2. **无法回答时序问题**："2 月时用户偏好什么？"无法回答
3. **冲突事实并存**：新旧事实同时出现在上下文中，Agent 无法判断哪个当前有效
4. **衰减无法精确**：仅靠时间衰减因子，无法区分"刚变更不稳定"与"长期稳定"

### 1.2 Zep/Graphiti 的双时序模型

每个事实跟踪 4 个时间戳：

| 时间戳 | 含义 | 示例 |
|--------|------|------|
| `created_at` | 系统何时记录此事实 | 2026-01-15 |
| `valid_at` | 事实在世界何时开始为真 | 2026-01-10 |
| `invalid_at` | 事实何时不再为真 | 2026-03-01 |
| `expired_at` | 系统何时得知此事实已失效 | 2026-03-02 |

**冲突解决**：新事实与旧事实冲突时，自动设置旧事实的 `invalid_at`，并创建因果边。

### 1.3 目标

1. L3 Fact 增加 `valid_at`/`invalid_at`/`expired_at` 字段
2. L4 Relation 增加 `valid_at`/`invalid_at`/`expired_at` 字段
3. 召回时默认 `time_scope=current`（仅返回当前有效的事实）
4. 支持显式 `time_scope=historical` 查询历史事实
5. 冲突事实自动设置 `invalid_at`

### 1.4 功能需求

#### P0 — 必须实现

| ID | 需求 | 说明 |
|----|------|------|

| BT-P0-3 | time_scope=current 召回 | 默认仅返回 `invalid_at IS NULL OR invalid_at > now()` 的事实 |

### 1.5 验收标准

1. 新写入的 Fact/Relation 自动填充 `valid_at`（默认=创建时间）
2. 冲突检测后旧事实 `invalid_at` 被正确设置
3. `time_scope=current` 召回不返回已失效事实
4. `time_scope=historical` 可查询指定时间点的事实
5. 现有数据迁移后行为不变（`invalid_at=NULL` 视为仍有效）
6. `make wire && make build && make test` 全部通过

## 二、设计文档

### 2.1 数据模型变更

#### L3 Fact 扩展

```sql
ALTER TABLE memory_facts ADD COLUMN valid_at TIMESTAMP;
ALTER TABLE memory_facts ADD COLUMN invalid_at TIMESTAMP;
ALTER TABLE memory_facts ADD COLUMN expired_at TIMESTAMP;

-- 现有数据迁移
UPDATE memory_facts SET valid_at = created_at WHERE valid_at IS NULL;
```

#### L4 Relation 扩展

```sql
ALTER TABLE memory_relations ADD COLUMN valid_at TIMESTAMP;
ALTER TABLE memory_relations ADD COLUMN invalid_at TIMESTAMP;
ALTER TABLE memory_relations ADD COLUMN expired_at TIMESTAMP;

UPDATE memory_relations SET valid_at = created_at WHERE valid_at IS NULL;
```

#### 因果边类型

```sql

```

### 2.2 召回逻辑变更

**L3 Fact 召回**（`memory_shim_l3_recall.go`）：

```go
// 现有：无条件时间过滤
// 新增：time_scope 过滤
type RecallOptions struct {
    TimeScope   TimeScope   // current | historical | all
    QueryTime   *time.Time  // historical 模式下的查询时间点
}

type TimeScope string

const (
    TimeScopeCurrent     TimeScope = "current"     // 默认：仅当前有效
    TimeScopeHistorical  TimeScope = "historical"  // 指定时间点
    TimeScopeAll         TimeScope = "all"          // 全部（含已失效）
)

// SQL 过滤条件
func timeScopeFilter(scope TimeScope, queryTime *time.Time) string {
    switch scope {
    case TimeScopeCurrent:
        return "(invalid_at IS NULL OR invalid_at > NOW())"
    case TimeScopeHistorical:
        return "(valid_at <= ? AND (invalid_at IS NULL OR invalid_at > ?))"
    case TimeScopeAll:
        return "1=1"
    }
}
```

### 2.3 冲突检测与自动失效

**新增 `TemporalConflictResolver`**：

```go
type TemporalConflictResolver interface {
    // 检测新事实与已有事实的冲突
    DetectConflicts(ctx context.Context, newFact *Fact, candidates []*Fact) ([]*Conflict, error)
    // 解决冲突：设置旧事实 invalid_at + 创建因果边
    ResolveConflicts(ctx context.Context, conflicts []*Conflict) error
}

type Conflict struct {
    OldFact    *Fact
    NewFact    *Fact
    Reason     string  // 冲突原因
    InvalidAt  time.Time  // 旧事实的失效时间
}
```

**冲突检测策略**：
1. 向量相似度 >= 0.85 且语义矛盾（LLM 判断）
2. 同一 fact_key 的新值覆盖旧值
3. 同一实体的互斥属性（如"素食"vs"喜欢烤肉"）

### 2.4 与 theory.md 的对齐

`theory.md` §13 明确指出：
> 时间是结构维度而非 metadata。Ledger 既要 transaction_time 也要 valid_time；二者不等价。
> 默认 time_scope=current ⇒ "宁可漏不可错"。

本设计完全遵循此原则：
- `created_at` = transaction_time（系统何时记录）
- `valid_at` = valid_time（事实何时为真）
- `invalid_at` = valid_time 的终点
- `expired_at` = transaction_time 的终点（系统何时得知失效）

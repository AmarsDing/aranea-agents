## Context

Aranea-Agents 当前 CI 流水线包含 6 个 Job（lint / test-go / test-web / smoke / wire-clean / proto-clean），覆盖基本的 lint + 测试 + 冒烟验证。但缺乏闭环自我迭代能力：

- **无自动修复**：CI 失败后需人工诊断、修复、提交、等待下一轮 CI
- **无自动发布**：无 GoReleaser、无 CD 流水线、无版本号自动管理
- **无文档同步**：代码变更后 spec/changelog 需手动更新
- **测试覆盖不足**：无 E2E 测试、无前端组件测试、无集成测试自动化
- **前端 Lint 缺失**：无 ESLint、无 Prettier、无 commitlint

当前已有基础：350+ Go 测试文件、59 前端 spec 文件、araneactl lint（12 条规则）、CodeQL 安全扫描、Docker 多阶段构建。

### 自我迭代闭环（核心架构）

```
┌─────────────────────────────────────────────────────────────────────┐
│                        自我迭代闭环                                  │
│                                                                      │
│   ┌─────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐  │
│   │  运行    │────▶│  采集    │────▶│  分析    │────▶│  优化    │  │
│   │  (CI/CD) │     │  (遥测)  │     │  (AI)    │     │  (行动)  │  │
│   └─────────┘     └──────────┘     └──────────┘     └──────────┘  │
│        ▲                                                  │          │
│        └──────────────────────────────────────────────────┘          │
│                     闭环反馈：优化结果验证后进入下一轮               │
└─────────────────────────────────────────────────────────────────────┘
```

## Goals / Non-Goals

**Goals:**

1. 构建"失败检测→AI 诊断→自动修复→验证→PR"的闭环自动修复引擎
2. 建立 GoReleaser 自动发布流水线（tag→build→release→deploy staging→smoke→promote production）
3. 实现代码变更→文档影响分析→自动更新→PR 的文档同步引擎
4. 补齐 E2E 测试（Playwright）和集成测试（testcontainers-go）
5. 补齐前端 Lint（ESLint + Prettier）和 Git Hooks（Husky + lint-staged + commitlint）
6. 建立迭代仪表盘，每周自动生成迭代周报
7. 建立失败模式知识库，让系统从每次修复中学习

**Non-Goals:**

- 不做生产环境的全自动部署（production promote 需人工确认）
- 不做 AI 自动重构或功能增强（仅修复 CI 失败和 lint 错误）
- 不做性能自动调优（仅采集指标，不做自动参数调整）
- 不做前端组件测试（当前仅补 E2E，组件测试后续迭代）
- 不做 K8s 部署配置（当前仅 Docker + staging 环境）
- 不修改任何业务逻辑代码

## Decisions

### D1: 自动修复引擎 — GitHub Actions + 自托管 Agent（项目自身 LLM 能力）

**选择**：GitHub Actions workflow（`workflow_run` 触发）+ 自托管 Agent API（项目自身的 Chat API）

**理由**：
- 项目本身就是一个 AI Agent 平台，已有完整的 LLM 集成（trpc-agent-go 运行时）
- 通过 `POST /v1/chat/messages` 调用自身的 Agent 来诊断 CI 失败，无需外部 API key
- Agent 使用项目已配置的 LLM provider（OpenAI/Claude/等），LLM API key 只需在 aranea-agents 后端配置一次
- 这正是"火箭发动机自我迭代"的精髓——用自身的 AI 能力修复自身
- 修复 PR 需人工 review，保证安全性

**备选方案**：
- A) 直接调用 OpenAI API（需要额外的 OPENAI_API_KEY secret）→ 否决，违反自我迭代原则
- B) 仅用规则匹配修复（覆盖面窄，无法处理复杂问题）→ 作为 Agent 不可用时的回退方案
- C) 自建修复服务（需额外运维，过重）→ 否决

**设计**：

```
CI 失败
  │
  ▼
workflow_run (conclusion: failure)
  │
  ├─ 获取失败日志 (gh run view --log-failed)
  │
  ├─ 判断失败类型
  │   ├─ lint 错误 → 规则修复 (golangci-lint --fix / eslint --fix)
  │   ├─ 测试/构建失败 → 自托管 Agent 诊断 + 修复
  │   │   ├─ ARANEA_API_URL 已配置？
  │   │   │   ├─ 是 → 调用 POST /v1/chat/messages 请求 Agent 生成 patch
  │   │   │   └─ 否 → 回退到 pattern-fix.sh（基于已知修复模板的模式匹配）
  │   │   └─ Agent 返回 patch → git apply → 验证
  │   └─ Proto/Wire 同步 → make api && make wire
  │
  ├─ 生成修复 patch
  │
  ├─ 本地验证 (make test / make lint)
  │   ├─ 通过 → 创建 auto-fix PR
  │   └─ 失败 → 放弃修复，记录到知识库
  │
  └─ 记录失败模式到 .auto-fix/patterns.jsonl
```

**安全约束**：
- 自动修复 PR 必须经过 CI 验证 + 人工 review
- 每日修复上限 10 次（防止 API 费用失控）
- 不修改 .github/workflows/、Makefile、go.mod 等关键文件
- 不修改 proto 文件（proto 变更需走完整提案流程）

**auto-fix.yml 核心结构**：

```yaml
# .github/workflows/auto-fix.yml
name: Auto Fix
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
    conclusion: failure

jobs:
  auto-fix:
    runs-on: ubuntu-latest
    if: ${{ github.event.workflow_run.conclusion == 'failure' }}
    steps:
      - uses: actions/checkout@v4
        with:
          token: ${{ secrets.PAT_TOKEN }}

      - name: Get failure logs
        run: |
          gh run view ${{ github.event.workflow_run.id }} \
            --log-failed > failure-logs.txt
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Classify and fix
        run: |
          # lint 错误 → 规则修复
          # test/build 失败 → LLM 诊断 + 修复
          python3 scripts/auto-fix.py --logs failure-logs.txt

      - name: Verify fix
        run: make test && make lint

      - name: Create auto-fix PR
        if: success()
        run: |
          git checkout -b auto-fix/${{ github.event.workflow_run.id }}
          git add -A
          git commit -m "fix: auto-fix for CI failure #${{ github.event.workflow_run.id }}"
          git push origin auto-fix/${{ github.event.workflow_run.id }}
          gh pr create \
            --title "🤖 Auto-fix: CI failure #${{ github.event.workflow_run.id }}" \
            --body "Automated fix generated by AI. Please review." \
            --label "auto-fix"
        env:
          GH_TOKEN: ${{ secrets.PAT_TOKEN }}

      - name: Record failure pattern
        if: always()
        run: |
          echo "{\"timestamp\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\",\"run_id\":\"${{ github.event.workflow_run.id }}\",\"fix_succeeded\":\"${{ job.status == 'success' }}\"}" >> .auto-fix/patterns.jsonl
```

**失败模式知识库结构**：

```
.auto-fix/
├── patterns.jsonl          # 失败模式记录（JSONL 格式，追加写入）
├── known-fixes/            # 已知修复模板
│   ├── race-condition.md   # 竞态条件修复模板
│   ├── nil-pointer.md      # 空指针修复模板
│   ├── import-cycle.md     # 循环导入修复模板
│   └── proto-sync.md       # Proto 同步修复模板
└── stats.json              # 统计：修复成功率、常见模式等
```

### D2: E2E 测试 — Playwright

**选择**：Playwright（而非 Cypress）

**理由**：
- Playwright 原生支持多浏览器（Chromium/Firefox/WebKit）
- 更好的自动等待机制，减少 flaky 测试
- 更轻量，无需额外安装桌面应用
- 更好的 TypeScript 集成

**测试金字塔**：

```
            ╱  E2E 测试  ╲           ← Playwright (新增)
           ╱   (关键路径)   ╲
          ╱──────────────────╲
         ╱   集成测试         ╲      ← testcontainers-go (新增)
        ╱   (API 端点+DB)      ╲
       ╱────────────────────────╲
      ╱     单元测试              ╲   ← 已有 350+ Go + 59 前端
     ╱   (业务逻辑+工具函数)       ╲
    ╱──────────────────────────────╲
```

**关键路径覆盖**：
1. 完整聊天流程：创建会话 → 发送消息 → 收到回复
2. Agent 创建与配置
3. Team 编排与运行
4. MCP 服务器管理

### D4: 自动发布 — GoReleaser

**选择**：GoReleaser（而非手动脚本或自定义 CI）

**理由**：
- 社区标准工具，维护活跃
- 自动构建多平台二进制 + Docker 镜像 + Changelog
- 与 GitHub Releases 原生集成
- 支持自定义 hooks（make api / make wire）

**Release Workflow**：

```yaml

name: Release
```

### D5: 文档同步 — LLM 辅助 + 规则匹配

**选择**：规则匹配（Proto 变更→重新生成 OpenAPI）+ LLM 辅助（spec 文档更新）

**理由**：
- Proto→OpenAPI 是确定性映射，规则匹配更可靠
- spec 文档更新需要语义理解，LLM 更适合
- 文档 PR 需人工 review，关键 spec（蓝图、交叉参考）仅自动提醒

**文档同步流程**：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  代码变更     │────▶│  影响分析     │────▶│  文档更新     │
│  (git push)  │     │  (AI 分析)   │     │  (自动 PR)   │
└──────────────┘     └──────────────┘     └──────────────┘
       │                    │                     │
       ▼                    ▼                     ▼
  Proto 变更?         影响哪些模块?          更新对应 spec
  API 变更?           影响哪些文档?          更新 changelog
  架构变更?           需要同步哪些?          更新交叉参考
```

**代码→文档映射规则**：

| 变更路径 | 影响文档 | 更新方式 |
|----------|----------|----------|
| api/kratos/**/*.proto | architecture-blueprint.md, OpenAPI | 规则：make api 重新生成 |
| internal/biz/* | module-cross-reference.md | LLM 辅助 + Issue 通知 |
| internal/service/* | module-cross-reference.md | LLM 辅助 + Issue 通知 |
| internal/data/ent/schema/* | architecture-blueprint.md | LLM 辅助 + Issue 通知 |
| web/src/features/* | frontend-layers.md | LLM 辅助 |

**覆盖率门禁递进**：

```yaml
- name: Coverage gate
  run: |
    COVERAGE=$(go tool cover -func=coverage.out | grep total | awk '{print $3}' | sed 's/%//')
    MILESTONE=$(cat .milestone)
    case $MILESTONE in
      M3) THRESHOLD=40 ;;
      M4) THRESHOLD=60 ;;
      M5) THRESHOLD=70 ;;
    esac
    if (( $(echo "$COVERAGE < $THRESHOLD" | bc -l) )); then
      echo "Coverage ${COVERAGE}% below threshold ${THRESHOLD}%"
      exit 1
    fi
```

## Risks / Trade-offs

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| LLM 自动修复引入新 bug | 高 | 修复 PR 必须经过 CI + 人工 review；限制修改范围 |
| LLM API 费用 | 中 | 每日修复上限 10 次；简单 lint 错误用规则修复 |
| Playwright E2E 测试不稳定 | 中 | retry 机制 + 失败截图/trace；仅 nightly 运行非关键路径 |
| testcontainers-go 启动慢 | 低 | CI 中使用 service containers 预启动；本地测试用 SQLite |
| 自动发布可能发布有问题的版本 | 高 | staging 冒烟验证 → 人工 promote 到 production |
| 文档自动更新不准确 | 中 | 文档 PR 需人工 review；关键 spec 仅自动提醒 |
| Husky 在 Windows 上兼容性 | 低 | 使用 Husky v9+（原生 Windows 支持） |
| 新增依赖过多 | 低 | 均为开发依赖，不影响生产构建 |

## Migration Plan

### Phase 1: 基础加固（Week 1-2）

1. 安装 Husky + lint-staged + commitlint
2. 配置 ESLint + Prettier
3. CI 新增 commitlint / typecheck-web Job
4. 搭建 Playwright E2E 框架 + 首个关键路径测试
5. 搭建 testcontainers-go 集成测试 + 首个 API 集成测试

验证标准：所有 commit 自动 lint+format，CI 全绿

### Phase 2: 自动修复（Week 3-4）

1. 创建 auto-fix GitHub Action
2. 实现 araneactl --fix 模式
3. 建立失败模式知识库
4. CI 新增 test-integration / e2e-nightly Job

验证标准：CI 失败自动修复成功率 > 50%，人工介入 < 3次/周

### Phase 3: 自动发布 + 文档同步（Week 5-8）

1. 配置 GoReleaser
2. 创建 release workflow
3. 创建 doc-sync workflow
4. 创建 changelog workflow
5. 创建迭代仪表盘 workflow

验证标准：从代码变更到文档更新到发布全链路无人值守

### 回滚策略

- 每个 Phase 独立，可单独回滚
- auto-fix workflow 可通过删除 workflow 文件禁用
- GoReleaser 可通过删除 tag 回滚 release
- 文档同步 PR 可直接关闭

## 实现偏差记录

> 以下记录代码实际实现与设计文档的差异，供后续迭代参考。

### D1 偏差：自动修复引擎 — 自托管 Agent API 替代 OPENAI_API_KEY

**设计文档**：任务 6.13 提到配置 `OPENAI_API_KEY`，D1 决策中提到"自托管 Agent API"。

**实际实现**：auto-fix.yml 使用以下环境变量调用自托管 Agent：
- `ARANEA_API_URL`：自托管 aranea-agents 实例 URL
- `ARANEA_AUTO_FIX_SESSION`：预配置的 Agent session ID
- `ARANEA_API_TOKEN`：API 认证 token

未配置时回退到 `.auto-fix/scripts/pattern-fix.sh`（7 种模式匹配：race condition、nil pointer、import cycle、proto/wire 同步、gofmt drift、goimports drift、go mod tidy），而非文档中的 4 种 known-fixes。

**影响**：GitHub Secrets 需配置的是 ARANEA_API_URL / ARANEA_AUTO_FIX_SESSION / ARANEA_API_TOKEN，而非 OPENAI_API_KEY。

### D4 偏差：GoReleaser 配置

**设计文档**：before hooks 包含 `make api` 和 `make wire`；ldflags 注入 `main.version`、`main.commit`、`main.date`；araneactl 入口为 `./cmd/araneactl`。

**实际实现**：
- before hooks 仅 `go mod tidy`（无 make api/make wire）
- ldflags 注入 `main.Version` 和 `main.Name`（无 commit/date）
- araneactl 入口为 `./cmd/aranea`（非 ./cmd/araneactl）
- 新增 archives 配置（tar.gz + zip for windows）

### D4 偏差：Release Workflow

**设计文档**：release workflow 包含 staging 部署 → 冒烟测试 → production promote（需人工审批）。

**实际实现**：release.yml 仅包含 GoReleaser + Docker push 到 ghcr.io，无 staging/production 步骤。staging 和 production 部署需在基础设施就绪后补充。

### D6 偏差：Husky + lint-staged 状态

**设计文档**：Husky pre-commit hook 调用 lint-staged，commit-msg hook 调用 commitlint。

**实际实现**：
- `.husky/pre-commit` 内容为 `# lint-staged disabled`
- `.husky/commit-msg` 内容为 `# commitlint disabled`
- 根目录无 package.json，husky/lint-staged/commitlint 的 npm 依赖未安装
- `.commitlintrc.yml` 文件不存在
- CI 中 commitlint 通过 `npm install -g` 临时安装

**原因**：可能为避免影响开发体验而临时禁用，待代码库规范化后再启用。

### D9 偏差：CI Pipeline 结构

**设计文档**：CI 12 Job 包含独立的 doc-sync-check job。

**实际实现**：CI 有 12 个 job，但无独立的 doc-sync-check job。proto-clean job 中包含 OpenAPI spec 存在性检查（`if [ -f api/openapi.yaml ]`），功能已部分覆盖 doc-sync-check 的职责。security-scan 使用 Trivy filesystem scan（非容器扫描），且 continue-on-error: true。CodeQL 在独立的 codeql.yml workflow 中运行。

### D5 偏差：文档同步引擎

**设计文档**：doc-sync 包含 LLM 辅助 spec 更新步骤。

**实际实现**：doc-sync.yml 中无 LLM 辅助 spec 更新步骤。当前仅包含：变更范围检测、OpenAPI 重新生成、关键 spec Issue 通知、changelog 条目生成。LLM 辅助 spec 更新待后续实现。

### D8 偏差：迭代仪表盘

**设计文档**：发布频率采集从 GitHub Releases API 获取最近一周的发布数据。

**实际实现**：使用 `gh release list --limit 50 | grep $(date +%Y-%m)` 统计当月发布数（非周维度）。覆盖率仅采集最新值，无历史趋势对比。

### 额外实现：pattern-fix.sh 回退脚本

代码中实现了 `.auto-fix/scripts/pattern-fix.sh`，包含 7 种已知失败模式的自动修复尝试：
1. Race condition → 提示手动修复（无法安全自动修复）
2. Nil pointer dereference → 提示手动修复
3. Import cycle → 提示手动修复
4. Proto/wire out of sync → `make api && make wire`
5. gofmt drift → `gofmt -w .`
6. goimports drift → `goimports -w .`
7. go mod tidy needed → `go mod tidy`

此脚本在自托管 Agent API 不可用时作为回退方案，设计文档中未详细描述。

### 额外实现：集成测试骨架

chat_integration_test.go 和 agent_integration_test.go 仅为骨架实现——启动 PostgreSQL 容器后只打印 DSN，实际 API 测试标记为 TODO。需要后续补充 Wire 注入的完整服务器实例来运行真实 API 测试。

**2026-06-05 复查确认**：两个集成测试文件仍为空壳状态，testcontainer 工具（`internal/testutil/testcontainer.go`）已完整实现，但测试逻辑未补充。

### D11 偏差：commitlint 配置缺失

**设计文档**：CI commitlint job 使用 `.commitlintrc.yml` 配置文件。

**实际实现**：`.commitlintrc.yml` 文件不存在。CI commitlint job 引用了 `--config .commitlintrc.yml` 参数，但文件缺失，该 job 在 PR 场景下可能会失败。commitlint 通过 `npm install -g @commitlint/cli @commitlint/config-conventional` 临时安装，但缺少配置文件可能导致使用默认配置或报错。

### 额外实现：ESLint 渐进式规则

ESLint 配置使用渐进式规则（gradual adoption），包括：
- `vue/no-mutating-props: warn`（而非 error）
- `no-undef: off`（TypeScript 编译器覆盖）
- `@typescript-eslint/no-explicit-any: warn`
- `@typescript-eslint/no-unused-vars: warn`（argsIgnorePattern: ^_）
- `vue/multi-word-component-names: off`
- 忽略 `src/services/**`（自动生成代码）

### 额外实现：Prettier 扩展配置

Prettier 配置比文档描述更完整，额外包含：
- `trailingComma: "all"`
- `bracketSpacing: true`
- `arrowParens: "always"`
- `endOfLine: "lf"`
- `vueIndentScriptAndStyle: false`

### 额外实现：Playwright 仅 Chromium

Playwright 配置仅使用 Chromium 项目（设计文档提到多浏览器支持），本地运行时自动启动 `pnpm dev` 作为 webServer。baseURL 默认为 `http://localhost:9001`。

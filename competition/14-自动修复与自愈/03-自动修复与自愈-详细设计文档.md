## 1. 数据库字段设计

### 1.1 PostgreSQL (twinmonitor) 表：remediation_policies（修复策略表）

**作用**：存储修复策略配置，定义"什么告警触发什么修复动作"，是自愈闭环的规则入口。

| 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| id | BIGINT | Y | 自增 | 主键ID |
| name | VARCHAR(255) | Y | -- | 策略名称（如：磁盘空间不足自动清理） |
| description | TEXT | N | NULL | 策略描述 |
| alert_source | VARCHAR(50) | Y | -- | 告警来源：zabbix, prometheus, custom |
| alert_level | VARCHAR(50) | N | NULL | 告警级别：为空表示全部；可选 disaster, high, medium, warning, info |
| keywords | TEXT | N | NULL | 标题关键词匹配，逗号分隔多个关键词 |
| tags | TEXT | N | NULL | 标签匹配，逗号分隔多个标签 |
| execution_mode | VARCHAR(20) | Y | -- | 执行模式：auto-自动执行, approval-审批后执行, suggestion-仅建议 |
| scenario_id | BIGINT | Y | -- | 关联修复场景模板ID（13-AI智能运维 ai_scenario_templates.id） |
| scenario_params | JSONB | N | NULL | 场景参数 JSON 模板，支持 `{{alert.*}}` 变量注入 |
| max_executions_per_hour | INT | N | 5 | 每小时最大执行次数，默认 5 |
| cooldown_seconds | INT | N | 300 | 冷却时间（秒），默认 300 |
| verify_enabled | SMALLINT | N | 0 | 是否启用修复后验证：0-否, 1-是 |
| verify_scenario_id | BIGINT | N | NULL | 验证场景模板ID（13-AI智能运维 ai_scenario_templates.id） |
| verify_timeout_seconds | INT | N | 120 | 验证超时（秒），默认 120 |
| verify_params | JSONB | N | NULL | 验证参数 JSON |
| rollback_enabled | SMALLINT | N | 0 | 是否启用自动回滚：0-否, 1-是 |
| rollback_scenario_id | BIGINT | N | NULL | 回滚场景模板ID（13-AI智能运维 ai_scenario_templates.id） |
| rollback_on_failure | SMALLINT | N | 1 | 修复失败时自动回滚：0-否, 1-是（默认开） |
| status | SMALLINT | Y | 1 | 状态：1-启用, 0-禁用 |
| created_by | BIGINT | N | NULL | 创建人ID（users.id） |
| updated_by | BIGINT | N | NULL | 更新人ID（users.id） |
| deleted_by | BIGINT | N | NULL | 删除人ID（users.id） |
| created_at | TIMESTAMPTZ | Y | CURRENT_TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMPTZ | Y | CURRENT_TIMESTAMP | 更新时间 |
| deleted_at | TIMESTAMPTZ | N | NULL | 删除时间（软删除） |

**索引**：
- PRIMARY KEY (`id`)
- INDEX `idx_remediation_policies_alert_source` (`alert_source`)
- INDEX `idx_remediation_policies_status` (`status`)
- INDEX `idx_remediation_policies_execution_mode` (`execution_mode`)
- INDEX `idx_remediation_policies_scenario_id` (`scenario_id`)
- INDEX `idx_remediation_policies_deleted_at` (`deleted_at`)

**关联关系**：
- 逻辑关联 13-AI智能运维 `ai_scenario_templates` 表（通过 `scenario_id`、`verify_scenario_id`、`rollback_scenario_id`，HTTP 校验 + 5 分钟 Redis 缓存，禁止跨库 JOIN）
- 逻辑关联用户表 `users`（通过 `created_by`、`updated_by`、`deleted_by`）

**scenario_params 示例**：
```json
{
  "server_id": "{{alert.asset_id}}",
  "alarm_title": "{{alert.title}}",
  "alarm_level": "{{alert.level}}",
  "cleanup_path": "/var/log",
  "threshold_percent": 90
}
```

## 2. 后台服务功能设计

自动修复与自愈服务（remediation）采用 Golang Kratos v2.9.2 微服务框架，分层架构为：service（服务层）→ biz（业务逻辑层）→ data（数据访问层），使用 Google Wire 进行依赖注入。

服务端口规划：HTTP:8110, gRPC:9110。

### 2.1 核心流程：告警 → 策略匹配 → 模式分流 → 执行 → 验证 → 回滚

#### 2.1.2 状态转换规则表

| 当前状态 | 目标状态 | 触发条件 | 操作 |
|----------|----------|----------|------|
| (none) | pending_approval | approval 模式策略命中 | 创建执行记录，发布审批请求事件 |
| (none) | running | auto 模式策略命中 | 创建执行记录，立即调用 13 创建修复场景任务 |
| pending_approval | running | 审批员批准（策略级） | 更新状态，记录审批信息，创建修复场景任务 |
| pending_approval | rejected | 审批员拒绝 | 更新状态，记录拒绝原因（必填） |
| pending_approval | cancelled | 人工取消 | 更新状态，记录取消原因 |
| running | success | 修复场景任务 completed 且验证通过/未启用验证 | 更新状态，记录执行结果，发布成功事件 |
| running | failed | 修复场景任务 failed 或验证未通过/超时；或任务创建失败（141021） | 更新状态，记录错误信息，触发自动回滚（如启用） |
| running | cancelled | 人工取消（调用 13 任务取消接口，转发 aranea 取消语义） | 更新状态，记录取消原因 |
| failed | rolled_back | 自动/手动回滚场景任务 completed | 更新状态，记录回滚信息 |
| failed | running | 人工重试 | 创建新执行记录（retry_of 关联原记录） |
| rolled_back | running | 人工重试 | 创建新执行记录（retry_of 关联原记录） |

> **"场景内审批中"不是独立状态**：场景执行中遇 aranea 审批点时，13 任务进入 waiting_approval 并发布 `ai.task.events`，本模块仅在 execution_log 追加展示标记（前端显示"场景内审批中，请前往 13 审批中心处理"），执行记录保持 running，审批动作由 13 审批中心完成。

#### 2.1.3 13 任务状态 → 本模块执行状态映射表（v2.0）

13 任务镜像状态枚举（`ai_tasks.status`）：`pending` / `running` / `waiting_approval` / `completed` / `failed` / `cancelled`。一条执行记录最多关联 3 个任务：修复（ai_task_id）、验证（verify_ai_task_id）、回滚（remediation_rollbacks.rollback_ai_task_id）。事件按 payload.task_id 先定位所属任务，再按下表映射：

| 13 任务事件 | 所属任务 | 本模块动作 |
|-------------|----------|-----------|
| started | 修复/验证/回滚 | 刷新 started_at，execution_log 追加 scenario_running / verify_started / rollback_started |
| node_started / node_output / node_completed | 任意 | execution_log 追加节点摘要步骤（scenario_node），状态保持 running |
| waiting_approval | 修复/验证/回滚 | execution_log 追加"场景内审批中"展示标记，状态保持 running |
| completed | 修复 | 启用验证 → 创建验证场景任务；未启用 → success（写 finished_at/duration_ms/result_output，发 remediation.events） |
| completed | 验证 | verify_result=passed → success |
| completed | 回滚 | 回滚记录 success → 执行记录 rolled_back |
| failed | 修复 | failed（写 result_error），启用自动回滚 → 创建回滚场景任务 |
| failed | 验证 | verify_result=failed → failed，触发自动回滚（如启用） |
| failed | 回滚 | 回滚记录 failed，执行记录保持 failed，execution_log 标记回滚失败原因 |
| cancelled | 修复/验证/回滚 | cancelled（记录取消信息） |

### 2.2 策略匹配引擎（PolicyMatcher）

#### 2.2.1 匹配流程

```
告警事件/手动触发
    │
    ▼
加载启用策略列表（Redis 缓存 remediation:policies:enabled，TTL 5min）
    │
    ▼
遍历策略，逐一匹配：
    │
    ├── 告警来源匹配：policy.alert_source == alert.source
    │
    ├── 告警级别匹配：policy.alert_level 为空 OR policy.alert_level == alert.level
    │
    ├── 关键词匹配：policy.keywords 为空 OR alert.title 包含任一关键词
    │   （keywords 逗号分隔，如 "磁盘,内存,CPU"）
    │
    └── 标签匹配：policy.tags 为空 OR alert.tags 包含任一标签
        （tags 逗号分隔）
    │
    ▼
全部条件满足 → 命中策略
    │
    ▼
冷却检查：Redis SETNX remediation:cooldown:{policy_id}:{alert_id}
    ├── 设置失败（已存在）→ 冷却期内，跳过该策略
    └── 设置成功 → 继续频率检查
    │
    ▼
频率检查：Redis INCR remediation:ratelimit:{policy_id}:{hour_bucket}
    ├── 计数 > max_executions_per_hour → 超出频率限制，跳过该策略
    └── 计数 ≤ max → 通过检查，创建执行记录
    │
    ▼
按 execution_mode 分流：
    ├── auto → 状态=running，立即调用 13 创建修复场景任务
    ├── approval → 状态=pending_approval，发布审批请求事件
    └── suggestion → 仅记录匹配结果，不创建执行记录
```

#### 2.2.3 变量注入实现

```go
// RenderScenarioParams 渲染场景参数（变量注入）
func RenderScenarioParams(template map[string]interface{}, alert *AlertContext) map[string]interface{} {
    result := make(map[string]interface{})
    for k, v := range template {
        if str, ok := v.(string); ok {
            result[k] = renderString(str, alert)
        } else {
            result[k] = v
        }
    }
    return result
}

func renderString(s string, alert *AlertContext) string {
    s = strings.ReplaceAll(s, "{{alert.alarm_id}}", alert.AlarmID)
    s = strings.ReplaceAll(s, "{{alert.asset_id}}", fmt.Sprintf("%d", alert.AssetID))
    s = strings.ReplaceAll(s, "{{alert.asset_name}}", alert.AssetName)
    s = strings.ReplaceAll(s, "{{alert.title}}", alert.Title)
    s = strings.ReplaceAll(s, "{{alert.level}}", alert.Level)
    s = strings.ReplaceAll(s, "{{alert.source}}", alert.Source)
    s = strings.ReplaceAll(s, "{{alert.metric_key}}", alert.MetricKey)
    s = strings.ReplaceAll(s, "{{alert.metric_value}}", fmt.Sprintf("%.2f", alert.MetricValue))
    return s
}
```

### 2.3 频率限制与冷却控制

#### 2.3.1 Redis Key 设计

| Key | 类型 | TTL | 说明 |
|-----|------|-----|------|
| `remediation:policies:enabled` | String (JSON) | 300s | 启用策略列表缓存 |
| `remediation:cooldown:{policy_id}:{alert_id}` | String | policy.cooldown_seconds | 冷却控制（SETNX） |
| `remediation:ratelimit:{policy_id}:{hour_bucket}` | String (Counter) | 3600s | 频率限制计数器 |
| `remediation:scenario:{scenario_id}` | String (JSON) | 300s | 场景模板存在性/启用校验缓存（13 HTTP 校验结果） |
| `remediation:alert:{alert_id}` | String (JSON) | 300s | 告警详情缓存 |
| `remediation:asset:{asset_id}` | String (JSON) | 300s | 资产详情缓存 |
| `remediation:dashboard:stats` | String (JSON) | 300s | 仪表盘统计缓存 |
| `remediation:execno:{yyyymmdd}` | String (Counter) | 86400s | 执行编号当日序号（INCR 原子计数，Redis 不可用降级时间戳） |
| `remediation:evt:{event_id}` | String | 86400s | ai.task.events / ai.analysis.completed 消费幂等去重（SET NX EX 24h） |
| `remediation:poll:lock` | String | 25s | 兜底轮询分布式锁（SET NX EX，多实例唯一轮询） |

#### 2.3.2 频率限制流程

```
创建执行记录前
    │
    ▼
冷却检查（SETNX）
    │
    ├── SETNX 失败（key 已存在）
    │   └── 返回：冷却期内，跳过
    │
    └── SETNX 成功
        │
        ▼
    频率检查（INCR + EXPIRE）
        │
        ├── hour_bucket = time.Now().Format("2006010215")
        ├── key = remediation:ratelimit:{policy_id}:{hour_bucket}
        ├── count = INCR key
        ├── 如果 count == 1 → EXPIRE key 3600
        │
        ├── count > max_executions_per_hour
        │   └── 返回：超出频率限制，跳过
        │
        └── count ≤ max
            └── 通过检查，创建执行记录
```

#### 2.5.1 创建场景任务（修复/验证/回滚）

**接口**：`POST /api/v1/monitor/aiops/tasks`

**请求体**：
```json

    "server_id": "1001",
    "alarm_title": "磁盘使用率超过90%",
```

### 2.6 ai.task.events 消费（TaskEventConsumer，v2.0 新增）

状态回流主链路，替代 v1.x 的 5s 轮询与回调规划（13 Webhook + NATS 事件链路使回调不再需要）。

#### 2.6.1 消费流程

```

    ▼

    ▼

    ▼
```

### 2.8 兜底轮询器（FallbackPoller，v2.0 新增）

事件丢失/服务重启恢复时的收敛链路（60 秒内收敛）。

- **扫描范围**：status=running 且存在未终态任务（ai_task_id / verify_ai_task_id / rollback_ai_task_id 非空）的执行记录。
- **周期与互斥**：30 秒周期；多实例经 Redis 分布式锁 `remediation:poll:lock`（SET NX EX 25s）保证唯一轮询。
- **比对推进**：批量（≤10 并发）调用 13 `GET /tasks/{id}` 比对状态，落后则按 §2.1.3 相同动作补齐；与事件消费的去重键共享（`remediation:evt:` + `poll:{task_id}:{status}`），防止与事件重复推进。
- **验证超时扫描**：同一周期内检查验证任务 `started_at + verify_timeout_seconds < now()` 且未终态 → verify_result=timeout → failed → 触发自动回滚（如启用）。
- **连续失败保护**：单任务连续 10 次查询失败标记 failed（原因「13 状态不可达」）。
- **重启恢复**：服务启动即扫一遍 running 记录重新挂入轮询。

### 3.2 策略编辑器（核心配置页）

**页面布局**：整页表单（非弹窗），分 6 个卡片分区。

**头部**：
- 「← 返回」按钮
- 标题：新建修复策略 / 编辑修复策略
- 「🗑 删除」按钮（仅编辑态，`confirm('确定要删除此策略吗？')`）
- 「保存」主按钮（蓝色）

**分区 1：基本信息**
- 策略名称*（占位：例如：磁盘空间不足自动清理）
- 描述（多行文本）

**分区 2：触发条件**
- 告警来源*：下拉选择（zabbix / prometheus / custom）
- 告警级别：下拉选择（全部 / 灾难 / 高 / 中 / 警告 / 信息）
- 关键词匹配：文本输入（占位：逗号分隔多个关键词，如：磁盘,内存,CPU）
- 标签匹配：文本输入（占位：逗号分隔多个标签）
- 「匹配测试」按钮：以当前触发条件 + 模拟标题/标签调用 match-test 接口，展示命中/跳过策略清单（v2.0 新增）

**分区 3：执行策略**
- 执行模式*：单选按钮组（auto 自动执行 / approval 审批后执行 / suggestion 仅建议）
- 关联场景模板*：下拉选择（从 13-AI 智能运维 `GET /api/v1/monitor/aiops/scenarios?is_enabled=1` 接口加载，显示场景名称+风险等级徽章）
- 场景参数 JSON：代码编辑器（占位：`{"server_id": "{{alert.asset_id}}"}`，支持告警变量模板注入；编辑器旁固定列出可用变量 `{{alert.alarm_id}}` / `{{alert.asset_id}}` / `{{alert.asset_name}}` / `{{alert.title}}` / `{{alert.level}}` / `{{alert.source}}` / `{{alert.metric_key}}` / `{{alert.metric_value}}`）

**分区 4：触发控制**
- 每小时最大执行次数：数字输入（默认 5）
- 冷却时间秒：数字输入（默认 300）

**分区 5：验证配置**
- 「启用修复后验证」勾选开关
- 展开后显示：
  - 验证场景模板：下拉选择（同源 13 场景接口）
  - 验证超时秒：数字输入（默认 120）
  - 验证参数 JSON：代码编辑器

**分区 6：回滚配置**
- 「启用自动回滚」勾选开关
- 展开后显示：
  - 回滚场景模板：下拉选择（同源 13 场景接口）
  - 「修复失败时自动回滚」勾选开关（默认开）

### 3.3 自愈工作台

**待审批区**（仅本模块 **策略级审批** 待办；场景内 aranea 审批点待办在 13 审批中心处理，不在此重复展示）：
- 卡片式待办列表，按创建时间倒序排列。
- 每张卡片显示：
  - 风险等级徽章（高-红色 / 中-黄色 / 低-蓝色）
  - 策略名称
  - 告警摘要（告警标题 + 设备名称）

  - 「执行」（蓝色，仅审批通过后可见）

**最近执行记录表**：

## 增补：解决方案沉淀与成熟度晋升（2026-07-24 评审通过；2026-07-28 v2.0 对齐）

### A. solution_library 表（twinmonitor 库；遵循索引名全局唯一与 idx_deleted_at 约束）

字段草案：`id` / `name` / `symptom_pattern`（症状模式） / `rootcause_pattern` / `match_condition`（JSONB：告警类型+设备类型+指标条件） / `playbook_ref`（JSONB：引用 16 运维工具与 13 脚本的有序步骤） / `verify_scenario_id`（验证场景模板，v2.0 更名） / `rollback_scenario_id`（回滚场景模板，v2.0 更名） / `maturity`（draft|probation|trusted） / `success_count` / `fail_count` / `rollback_count` / `source_ticket_id` / `reviewed_by` / `created_at` / `updated_at` / `deleted_at`；索引：`uk_solution_library_name`（name 唯一）、`idx_solution_library_deleted_at`。

### B. 闭环与三级执行模式映射

工单（10）关闭 → LLM 总结生成 Solution（`maturity=draft`，人工评审入库）→ 同类告警到达时经 remediation_policies 策略匹配：`draft`=仅推送建议（模式3 suggestion）、`probation`=审批后执行（模式2 approval，走 **本模块策略级审批/自愈工作台**）、`trusted`=自动执行（模式1 auto）→ 验证场景 → 失败自动回滚场景。

### C. 成熟度晋升与熔断

`probation` 连续成功 ≥5 次且 0 回滚 → 系统自动发起晋升审批单（**13 审批中心**，经 `POST /api/v1/monitor/aiops/approvals` 生成 source=promotion 审批单），审批结果经 NATS `ai.task.events`（event_type=`approval.promotion.result`）回告本模块，审批通过升 `trusted`；`trusted` 发生 1 次回滚 → 自动降回 `probation` 并通知管理员。每一步（匹配/审批/执行/验证/回滚/晋升/降级）落 `remediation_executions` + NATS 事件 + 12 审计，不可篡改。`trusted` 模式仅在总体方案 P2 阶段后开放。

### D. 语音追溯接口

新增 solution 追溯查询（solution + executions + 工单联查），支撑精灵"某问题怎么解决的"语音追溯报告（见 `19-语音精灵交互/`）。

- **版本**: v2.0
- **创建日期**: 2026-07-17
- **更新日期**: 2026-07-28

- **服务端口**: HTTP:8110, gRPC:9110

## 1. 模块定位

自动修复与自愈模块是 TwinMonitor 集中监控数字孪生平台"告警 → AI 根因 → 修复 → 验证 → 回滚"自愈闭环的执行中枢。该模块以修复策略为规则入口，消费 04-告警服务的告警事件与 13-AI智能运维的根因分析结果，通过调用 13-AI智能运维的任务创建 API 执行修复/验证/回滚 **场景**（场景 = aranea Graph 在 13 的治理注册项，编排在 aranea、执行代理由 13 任务中心提供、命令下发经 TwinMonitor-MCP-Server → 16-运维工具），实现从告警识别到自动修复的端到端自愈能力。

模块自身不实现编排引擎、不做 AI 诊断、不发送通知、不生成告警、不直接下发命令，仅作为编排消费者、状态管理者与结果记录者。在平台微服务体系中，本模块作为独立 remediation 服务部署，通过 HTTP/gRPC 对外提供策略管理、执行管理、工作台、仪表盘、AI 记录、手动处理等接口，通过 NATS 发布执行状态变更与审批请求事件、订阅告警与 13 任务/分析事件。

## 2. 模块职责

- 修复策略管理：策略 CRUD、触发条件匹配（来源/级别/关键词/标签）、执行模式控制（auto/approval/suggestion）、频率限制与冷却控制、启用/禁用、场景参数变量注入。
- 修复执行管理：执行记录状态机（pending_approval/running/success/failed/rolled_back/rejected/cancelled）、审批/拒绝/重试/取消、执行结果与步骤级日志记录、触发方式管理。
- 修复后验证：验证场景调用、超时控制（默认 120 秒）、验证结果判定（passed/failed/timeout/skipped）。
- 自动回滚：回滚场景调用、修复失败时自动回滚（默认开）、回滚记录管理、手动回滚支持。
- 自愈工作台：待审批队列（风险等级徽章/策略信息/告警摘要，**仅策略级审批**）、最近执行记录查询（详情/回滚/验证）。
- 修复仪表盘：统计卡片（总策略数/今日执行数/平均执行时间/待审批数）、执行趋势、策略成功率排行、告警来源分布。
- AI 修复记录：AI 诊断+修复全链路记录存储与查询（设备信息/诊断报告 Markdown/命令清单/逐条执行结果）。
- 手动触发：告警中心"处理"按钮联动，策略匹配 + 根因分析记录创建，返回处理结果摘要。
- 事件发布：执行状态变更事件（remediation.events）、审批请求事件（remediation.approval.required）的 NATS 发布。
- 事件订阅：`alarm.events`（自动触发）、`ai.task.events`（13 任务状态回流推进状态机）、`ai.analysis.completed`（AI 诊断结果关联）。

## 3. 技术架构

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 后端框架 | Golang Kratos v2.9.2 | 独立 remediation 微服务，HTTP/gRPC 双协议 |
| ORM/实体 | Ent v0.11.1 | 策略配置、执行记录、回滚记录、AI 修复记录的类型安全实体定义与迁移 |

| 前端 | Vue 3 + TypeScript + Quasar v2 | 策略编辑器、自愈工作台、修复仪表盘、执行记录、AI 修复记录 |

## 5. 服务划分与端口

| 服务名 | 协议 | 端口 | 说明 |
|--------|------|------|------|
| remediation | HTTP | 8110 | REST API，对外提供策略/执行/工作台/仪表盘/AI 记录/手动处理接口，经 API 网关统一入口 |
| remediation | gRPC | 9110 | 内部服务间调用（服务间查询） |

服务以独立进程部署，支持多实例水平扩展；多实例间 `ai.task.events` 消费经 NATS Queue Group 去重，兜底轮询通过 Redis 分布式锁保证唯一性。

## 6. 核心数据模型

### 6.1 PostgreSQL (twinmonitor) 配置表

| 表名 | 说明 | 关键字段 |
|------|------|----------|
| `remediation_policies` | 修复策略表，自愈闭环的规则入口 | name、alert_source、alert_level、keywords、tags、execution_mode、scenario_id、scenario_params、max_executions_per_hour、cooldown_seconds、verify_*、rollback_*、status |

### 6.2 PostgreSQL (twinmonitor_log) 事件表

| 表名 | 说明 | 关键字段 |
|------|------|----------|
| `remediation_executions` | 修复执行记录表，全生命周期状态机 | execution_no、policy_id、alert_id、asset_id、trigger_type、status、execution_mode、scenario_id、ai_task_id、verify_result、result_output、execution_log、risk_level、审批字段、时间字段、retry_of、version |
| `remediation_rollbacks` | 回滚记录表，与执行记录关联 | execution_id、rollback_ai_task_id、status、result_output、started_at、finished_at |
| `remediation_ai_records` | AI 修复记录表，AI 诊断+修复全链路 | record_no、alert_id、execution_id、asset_id、risk_level、status、diagnosis_report、command_list、command_results、error_message |

所有表遵循项目硬约束：主键 `id` bigint 自增；审计字段 created_at/updated_at/deleted_at + created_by/updated_by/deleted_by；配置表软删除 deleted_at + 索引 `idx_<表名>_deleted_at`；索引名 schema 全局唯一（`idx_<表名>_<字段>` 格式）；ent schema 实现 Privacy() 与 Edge。

> **v2.0 字段变更**：`workflow_id` → `scenario_id`（关联 13 `ai_scenario_templates.id`）；`workflow_task_id`/`verify_workflow_task_id`/`rollback_workflow_task_id` → `ai_task_id`/`verify_ai_task_id`/`rollback_ai_task_id`（关联 13 `ai_tasks.id` 任务镜像，镜像内含 aranea_run_id 与 Trace 链接）；`root_cause_task_id` → `rca_record_id`（关联 13 `ai_rca_records.id`）。一期已建表随二期执行下发段统一迁移（见实施进度文档）。

## 8. NATS 主题表

统一信封格式：`event_id`(UUID) / `event_type` / `event_version`("1.0") / `occurred_at`(RFC3339) / `asset_id`(uint64) / `operator_id` / `trace_id` / `payload`(map)。

| 主题 | 角色 | 对端 | 说明 |
|------|------|------|------|
| `remediation.events` | 发布 | 05-通知服务、07-可视化展示、04-告警服务 | 执行状态变更事件（created/pending_approval/approved/rejected/running/success/failed/rolled_back/cancelled），04 消费后回写告警"已自动处理"标记 |
| `remediation.approval.required` | 发布 | 05-通知服务 | 审批请求事件，携带风险等级/策略/告警摘要，通知值班审批员 |
| `alarm.events` | 订阅 | 04-告警服务生产 | 告警事件（firing）自动匹配策略触发（trigger_type=auto，一期已实施） |
| `ai.task.events` | 订阅 | 13-AI智能运维生产 | 场景任务状态事件（started/node_started/node_completed/completed/failed/cancelled/waiting_approval），按 trigger_ref_id=execution_no 过滤推进执行状态机（v2.0 主链路，替代轮询） |
| `ai.analysis.completed` | 订阅 | 13-AI智能运维生产 | AI 分析完成（RCA/自动诊断结果摘要），关联到执行记录与 AI 修复记录 |

## 9. 模块交互

### 9.1 与 04-告警服务

| 交互方向 | 方式 | 说明 |
|----------|------|------|
| 04 → 14 | HTTP | 告警中心"处理"按钮调用 `/api/v1/monitor/remediation/manual/process` |
| 14 → 04 | HTTP | 手动处理时查询告警详情（标题/级别/来源/标签/asset_id），5 分钟 Redis 缓存 |
| 14 → 04 | NATS `remediation.events` | 执行成功后回写告警"已自动处理"标记（alarm_events.is_solve=1） |
| 04 → 14 | NATS `alarm.events` | 订阅告警事件（firing）自动匹配策略（一期已实施） |

### 9.2 与 13-AI智能运维（场景执行代理，v2.0 契约）

| 交互方向 | 方式 | 说明 |
|----------|------|------|
| 14 → 13 | HTTP `POST /api/v1/monitor/aiops/tasks` | 创建修复/验证/回滚场景任务：scenario_id + 渲染后 params + trigger_type=remediation + trigger_ref_id=execution_no + idempotency_key=`remediation:{execution_no}:{scene}` |
| 13 → 14 | NATS `ai.task.events` | 任务状态回流主链路：按 trigger_ref_id 匹配执行记录推进状态机（v2.0） |
| 14 → 13 | HTTP `GET /api/v1/monitor/aiops/tasks/{id}` | 兜底查询：事件丢失/重启恢复时轮询（30s，Redis 分布式锁防多实例重复） |
| 14 → 13 | HTTP `POST /api/v1/monitor/aiops/tasks/{id}/cancel` | 取消执行（转发 aranea 取消语义） |
| 14 → 13 | HTTP `GET/POST /api/v1/monitor/aiops/rca-records` | 创建根因分析记录（手动处理联动），回写 rca_record_id |
| 13 → 14 | NATS `ai.analysis.completed` | RCA/自动诊断完成，关联执行记录"已诊断"标记与 AI 修复记录 |
| 14 → 13 | HTTP `GET /api/v1/monitor/aiops/scenarios/{id}` | 校验策略关联的场景模板存在且启用（5 分钟 Redis 缓存） |
| 13 → 16 | 间接 | 命令实际下发由 13 经 TwinMonitor-MCP-Server 调用 16-运维工具，本模块不直接交互 |

**双层审批边界**：本模块审批（策略级，创建 13 任务之前）在本模块自愈工作台处理；场景执行中 aranea 审批点（waiting_approval）由 13 审批中心处理，本模块仅经 `ai.task.events` 感知状态展示，不重复呈现待办。

## 10. 关键业务流程

### 10.1 告警 → 策略匹配 → 模式分流 → 执行 → 验证 → 回滚主流程（v2.0）

1. 告警中心点击"处理"或订阅 `alarm.events`（firing）→ 构建告警上下文 AlertContext。
2. 策略匹配引擎加载启用策略（Redis 缓存），按来源/级别/关键词/标签匹配。
3. 命中策略后依次执行冷却检查（SETNX）、频率检查（INCR），通过后按执行模式分流：
   - auto：创建执行记录（running）→ 调用 13 `POST /tasks` 创建场景任务（幂等键防重）。
   - approval：创建执行记录（pending_approval）→ 发布审批请求事件 → 审批员批准后创建场景任务。
   - suggestion：仅记录匹配结果。
4. 状态回流（v2.0 主链路）：消费 13 `ai.task.events`（按 trigger_ref_id=execution_no 匹配）→ 任务成功 → 启用验证则创建验证场景任务；任务失败 → 标记 failed。兜底链路：running 记录每 30 秒轮询 13 `GET /tasks/{id}`（事件丢失 60 秒内收敛）。
5. 验证通过 → success；验证失败/超时 → failed。
6. failed 且启用自动回滚 → 创建回滚场景任务 → 回滚成功 → rolled_back。
7. 每次状态变更发布 remediation.events 事件，记录步骤级执行日志。

### 10.2 手动处理聚合流程

1. 接收 alert_id → HTTP 查询 04 告警详情（缓存 5 分钟）。
2. 构建 AlertContext → 策略匹配 → 按模式分流创建执行记录。
3. 调用 13 `POST /api/v1/monitor/aiops/rca-records` 创建根因分析记录，回写执行记录 rca_record_id。
4. 返回聚合结果：命中策略数/创建执行数/根因分析记录 ID/策略列表。

### 10.3 审批流流程（策略级）

1. approval 模式创建执行记录（pending_approval）→ 发布 remediation.approval.required 事件。
2. 值班审批员在工作台查看待审批队列 → 批准（running + 创建场景任务）或拒绝（rejected + 必填原因）。
3. 状态变更通过乐观锁保证并发安全，发布 remediation.events 事件。
4. 场景执行中如遇 aranea 审批点：13 任务置 waiting_approval 并发布 `ai.task.events`，本模块将执行记录标记"场景内审批中"展示，审批动作在 13 审批中心完成，本模块不重复处理。

### 10.4 ai.task.events 消费流程（v2.0 新增）

1. NATS Queue Group 订阅 `ai.task.events`（多实例去重）。
2. 统一信封解析 + event_id 幂等去重（Redis SET NX EX 24h）。
3. 按 payload.trigger_type=remediation + trigger_ref_id=execution_no 定位执行记录；非本模块触发的任务事件直接忽略。
4. 状态映射：started→running（刷新节点进度）/completed→按验证配置分流/failed→failed（触发回滚）/cancelled→cancelled/waiting_approval→标记场景内审批中。
5. 终态事件同时回写耗时、结果摘要、错误信息；节点摘要追加到 execution_log。
6. 消费失败进入重试（NATS 红投）+ 兜底轮询收敛，保证最终一致。

## 11. 关键设计决策

### 11.1 策略匹配引擎

- 策略列表缓存到 Redis（key: `remediation:policies:enabled`，TTL 5 分钟），策略变更时主动清除缓存。
- 匹配规则：告警来源精确匹配 AND 告警级别匹配（策略级别为空或等于告警级别）AND 关键词任一命中 AND 标签任一命中。
- 匹配结果按策略创建时间升序，全部命中策略均创建执行记录（多策略并行处理同一告警）。

### 11.2 频率限制与冷却控制

- **频率限制**：Redis 滑动窗口计数器，key 格式 `remediation:ratelimit:{policy_id}:{hour_bucket}`（hour_bucket 格式 2006010215），INCR + EXPIRE 3600s，超过 max_executions_per_hour 拒绝。
- **冷却控制**：Redis SETNX + TTL，key 格式 `remediation:cooldown:{policy_id}:{alert_id}`，TTL 为策略 cooldown_seconds（默认 300s），SETNX 失败表示冷却期内。
- 冷却优先级高于频率限制，先检查冷却再检查频率；两者失败均记录跳过原因到匹配结果。

### 11.3 执行状态机与并发安全

- 状态变更通过数据库事务 + 乐观锁（version 字段）保证并发安全，防止并发审批/取消导致状态错乱。
- 状态变更后异步发布 NATS remediation.events 事件，发布失败记录日志并进入补偿队列。
- 任务状态回流 v2.0：`ai.task.events` 消费为主（NATS Queue Group 多实例去重 + event_id 幂等），兜底轮询 13 任务 API 为辅（30s 间隔、Redis 分布式锁、终态停止；替代 v1.x"5s 轮询"与"回调机制（v2 规划）"——13 Webhook + NATS 事件链路使回调不再需要）。

### 11.4 跨模块引用校验

- `policy.scenario_id` → 13 场景模板：HTTP 校验（存在且启用）+ 5 分钟 Redis 缓存（key: `remediation:scenario:{scenario_id}`）。
- `execution.alert_id` → 04 告警事件：HTTP 校验 + 5 分钟 Redis 缓存（key: `remediation:alert:{alert_id}`）。
- `execution.asset_id` → 02 设备资产：HTTP 校验 + 5 分钟 Redis 缓存（key: `remediation:asset:{asset_id}`）。
- **禁止跨库 JOIN**：所有跨模块数据通过 HTTP API 获取，冗余字段（policy_name/alert_title/asset_name/scenario_name）在创建时快照存储。

### 11.5 变量注入

- 场景参数 JSON 模板支持 `{{alert.*}}` 变量占位符，在创建执行记录时渲染。
- 支持的变量：`{{alert.alarm_id}}`、`{{alert.asset_id}}`、`{{alert.asset_name}}`、`{{alert.title}}`、`{{alert.level}}`、`{{alert.source}}`、`{{alert.metric_key}}`、`{{alert.metric_value}}`。
- 渲染后的参数持久化到执行记录 scenario_params 字段，保证执行时参数与渲染时一致（可追溯）。

### 11.6 手动处理聚合

- 手动处理接口同步执行：查询告警 → 匹配策略 → 创建执行记录 → 创建根因分析记录 → 返回聚合结果。
- 目标响应时间 ≤ 3s；根因分析记录创建失败不阻塞主流程，返回结果中标记根因创建失败。

### 11.7 编排引擎解耦（v2.0）

- 场景执行通过调用 13 任务创建 API（`POST /api/v1/monitor/aiops/tasks`），本模块不内嵌任何编排引擎逻辑、不感知 aranea 连接细节。
- 通过 trigger_type="remediation" + trigger_ref_id=execution_no 标识任务来源，供 13 追溯统计、供本模块事件匹配；幂等键 `remediation:{execution_no}:{scene}` 防重复执行。
- 命令实际下发经 13 → TwinMonitor-MCP-Server → 16-运维工具，本模块完全不感知命令通道细节；13/aranea 不可用时任务创建明确失败（业务错误码"执行引擎未就绪"），不伪造结果。

## 12. 边界约定

- 本模块不实现编排引擎，仅作为 13-AI智能运维场景执行代理的调用方与结果消费者；场景（Graph）编排在 aranea-agents。
- 本模块不做 AI 诊断，仅消费 13 的根因分析结果并关联到修复执行记录。
- 本模块不发送通知，通过 NATS 事件触发 05-通知服务。
- 本模块不生成告警，仅消费 04-告警服务的告警事件。
- 本模块不直接下发命令，命令执行由 13 经 MCP 调用 16-运维工具完成。
- 本模块不维护设备/资产基础信息，仅通过 HTTP 查询 02-设备资产管理。
- 本模块仅承载策略级审批；场景内 HITL 审批归 13 审批中心，两者不重复呈现。
- 配置表遵循软删除约束（deleted_at + `idx_<表名>_deleted_at` 索引），索引命名全局唯一 `idx_<表名>_<字段>` 格式；事件表追加型。
- 跨模块引用必须 HTTP 校验 + 5 分钟 Redis 缓存，禁止跨库 JOIN。
- 分层架构 service → biz → data，禁止 service 直连 data；biz 层 Repo 接口用 WithTx 传播事务。

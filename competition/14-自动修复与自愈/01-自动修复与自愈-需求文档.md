## 1. 模块概述

自动修复与自愈模块是 TwinMonitor 集中监控数字孪生平台"告警 → AI 根因 → 修复 → 验证 → 回滚"自愈闭环的执行中枢。该模块承载自动修复分组能力，通过修复策略将"什么告警触发什么修复动作"规则化，并与 13-AI智能运维（场景执行代理与 AI 根因分析）、04-告警服务（告警事件与告警中心"处理"按钮）联动，实现从告警识别到自动修复的端到端自愈能力。

在平台整体链路中，本模块位于告警服务下游、通知服务上游：告警产生后，本模块负责决策"是否需要修复、如何修复、是否需要人工审批"；修复动作的实际编排在 **aranea-agents**（Graph 图编排），执行通道由 13-AI智能运维的 **场景执行代理** 提供（13 任务中心创建 aranea 执行并镜像状态），命令的实际下发由 13 经 TwinMonitor-MCP-Server 调用 16-运维工具完成；执行结果通过 NATS 事件通知 05-通知服务与 07-可视化展示，并回写 04-告警服务的"已自动处理"标记，形成完整闭环。

模块核心定位：
- **策略化**：以修复策略为规则入口，定义触发条件、执行模式、频率控制、验证与回滚配置，支持可视化编辑与启禁用管理。
- **编排消费**：不实现编排引擎，通过调用 13-AI智能运维的任务创建 API 执行修复/验证/回滚 **场景**（场景定义注册于 13、执行于 aranea），仅作为场景的调用方与结果消费者。
- **安全可控**：三级执行模式（自动/审批/建议）+ 频率限制 + 冷却控制 + 自动回滚，防止误操作与告警风暴导致的重复修复。
- **可追溯**：完整记录执行日志、命令输出、审批信息、AI 诊断报告，支撑审计、复盘与策略优化。

### 1.1 平台自愈闭环全景（系统级视图）

```
04 告警事件 ──alarm.events──► 14 策略匹配（冷却+频限）
                                  │ 按模式分流
              ┌───────────────────┼─────────────────────┐
              ▼ auto              ▼ approval            ▼ suggestion
        创建执行单(running)  创建执行单(pending_approval)  仅记录建议
              │                   │ 14 策略级审批
              ▼                   ▼
        13 任务中心 POST /tasks（scenario_id + 渲染参数 + trigger_type=remediation）
              │                   13 创建 aranea 执行（Graph 编排）
              ▼
        aranea Graph 执行 ──经 MCP──► TwinMonitor-MCP-Server ──► 16 运维工具下发命令
              │ 场景内审批点 ──► 13 审批中心（HITL，与 14 策略级审批独立）
              ▼
        13 Webhook 回收事件 ──ai.task.events──► 14 推进执行状态机
              │                                   │
              ▼                                   ▼
        13 RCA/自动诊断 ──ai.analysis.completed──► 14 关联 AI 修复记录
                                              验证场景 → 失败回滚场景 → remediation.events
                                                                  │
                                              05 通知 / 07 大屏 / 04 回写"已自动处理"
```

**双系统职责切分**：aranea-agents 负责"怎么编排、怎么执行、执行细节与 Trace"；14 负责"该不该修、何时修、修完算不算数（验证）、失败怎么办（回滚）、谁批准的、效果如何（仪表盘）"。13 是两个系统之间的治理与代理层。

## 2. 模块边界

### 2.1 包含范围

- 修复策略管理：策略 CRUD、触发条件（告警来源/告警级别/标题关键词/标签匹配）、执行模式（auto/approval/suggestion）、关联场景模板、场景参数 JSON 模板（支持告警变量注入）、频率限制（每小时最大执行次数/冷却时间）、启用/禁用。
- 修复执行管理：执行记录状态机（pending_approval/running/success/failed/rolled_back/rejected/cancelled）、批准/拒绝（必填原因）/重试/取消、执行结果（命令输出/13 任务 ID）、触发方式（自动/手动/告警联动）、完整执行日志。
- 修复后验证：可配置验证场景、验证超时秒（默认 120）、验证参数 JSON；验证不通过视为修复失败。
- 自动回滚：可配置回滚场景、修复失败时自动回滚开关（默认开）、回滚记录管理。
- 自愈工作台：待审批队列（风险等级高/中/低徽章、策略信息、告警摘要、批准/拒绝/执行操作）、最近执行记录（查看详情/回滚/验证按钮）。
- 修复仪表盘：总策略数/今日执行数/平均执行时间/待审批数统计卡片、修复执行趋势、策略成功率排行、告警来源分布。
- AI 修复记录：AI 自动诊断+修复全链路记录（设备信息、AI 诊断报告 Markdown、修复命令清单[命令+说明]、逐条命令执行结果[stdout/stderr/退出码]、风险等级）。
- 手动触发：04-告警中心"处理"按钮 → 本模块匹配策略 + 13 根因分析，返回处理结果摘要（命中策略数/创建执行数/根因分析记录 ID）。

### 2.2 不包含范围

- **不实现编排引擎**：场景（Graph）定义、节点编排、执行调度由 aranea-agents 承载；场景的注册治理与执行代理由 13-AI智能运维承载。本模块仅作为场景的调用方与结果消费者。
- **不做 AI 诊断**：AI 根因分析、诊断报告生成、修复建议生成由 13-AI智能运维（分析执行在 aranea）负责，本模块仅消费其结果并关联到修复执行记录。
- **不发通知**：审批请求通知、执行结果通知由 05-通知服务负责，本模块通过发布 NATS 事件触发通知，不直接对接任何通知渠道。
- **不生成告警**：告警事件的生成、状态机、抑制规则、告警升级由 04-告警服务负责，本模块仅消费告警事件。
- **不直接下发命令**：SSH/Agent/脚本等命令的实际下发由 16-运维工具负责，本模块通过 13 场景执行代理间接调用（13 经 MCP → 16）。
- **不维护设备/资产基础信息**：设备信息、资产信息由 02-设备资产管理负责，本模块仅通过 HTTP 接口查询校验。

## 4. 功能需求

### 4.1 修复策略管理

#### 4.1.1 策略 CRUD

- 支持创建、查询（分页/筛选）、详情、更新、删除（软删除）修复策略。
- 策略字段：名称、描述、触发条件、执行模式、关联场景、场景参数、频率限制、验证配置、回滚配置、状态。
- 支持策略启用/禁用开关，禁用后不再匹配新告警；正在执行中的执行记录不受影响。
- 删除策略前校验：存在 running 或 pending_approval 状态的执行记录时，禁止删除并提示。

#### 4.1.2 触发条件

- 告警来源：zabbix / prometheus / custom，必填，精确匹配。
- 告警级别：全部 / 灾难 / 高 / 中 / 警告 / 信息，可选（默认全部），为空表示匹配所有级别。
- 关键词匹配：告警标题中包含任一关键词即命中，多个关键词逗号分隔（如"磁盘,内存,CPU"）。
- 标签匹配：告警标签中包含任一标签即命中，多个标签逗号分隔。
- 匹配逻辑：来源 AND 级别 AND 关键词 AND 标签，所有非空条件均需满足。

#### 4.1.3 执行模式

- `auto`（自动执行）：告警命中策略后立即创建执行记录并调用 13 创建场景执行任务，无需人工干预。适用于低风险、标准化的修复场景（如日志清理、缓存刷新）。
- `approval`（审批后执行）：创建执行记录后进入待审批状态，需值班审批员批准后才执行。适用于中高风险操作（如服务重启、配置变更）。
- `suggestion`（仅建议）：仅记录匹配结果，不创建执行记录，供人工参考。适用于新策略灰度验证或复杂故障场景。

> **双层审批说明**：本模块的审批是 **策略级审批**（执行单准入，发生在创建 13 任务之前）；13 审批中心承载 **场景内审批**（aranea Graph 审批点，发生在场景执行过程中，如高危工具调用前置审批）。两者相互独立：approval 模式策略批准后才创建场景任务；场景执行中如遇 aranea 审批点，任务进入 waiting_approval，由 13 审批中心处理并继续/终止，本模块经 `ai.task.events` 感知状态。

#### 4.1.4 关联场景模板

- 关联 13-AI智能运维的场景模板 ID（`scenario_id`，对应 13 `ai_scenario_templates.id`，场景定义在 aranea Graph），必填，创建/更新时通过 13 HTTP 接口校验场景存在性与启用状态（5 分钟 Redis 缓存）。
- 场景参数 JSON 模板，支持告警变量注入，如 `{{alert.asset_id}}`、`{{alert.title}}`、`{{alert.alarm_id}}`、`{{alert.level}}`、`{{alert.source}}`、`{{alert.metric_key}}`、`{{alert.metric_value}}` 等。
- 变量注入在创建执行记录时完成，将告警上下文字段渲染到场景参数中，渲染后的参数持久化到执行记录。

#### 4.1.5 频率限制

- 每小时最大执行次数：默认 5 次，同一策略在同一自然小时内最多触发执行次数，防止告警风暴导致重复修复。
- 冷却时间（秒）：默认 300 秒，同一策略对同一告警在冷却期内不重复创建执行记录，保证幂等防重。
- 频率限制基于 Redis 滑动窗口计数器实现（key 含 policy_id + 小时桶），冷却基于 Redis SETNX + TTL 实现。
- 冷却检查优先于频率检查；两者任一不通过即跳过该策略并记录跳过原因。

**验收要点**：同一策略在同一小时内触发 5 次后，第 6 次告警不再创建执行记录；同一告警在冷却期内（300 秒）重复触发，不创建新执行记录。

### 4.2 修复执行管理

#### 4.2.1 执行记录状态机

执行记录状态枚举全表：

| 状态 | 中文 | 说明 | 可流转到 |
|------|------|------|----------|
| `pending_approval` | 待审批 | 仅 `approval` 模式进入此状态 | running, rejected, cancelled |
| `running` | 执行中 | 13 场景任务已创建，等待执行结果 | success, failed, cancelled |
| `success` | 成功 | 场景执行成功且验证通过（如启用验证） | （终态，可手动回滚/重试验证） |
| `failed` | 失败 | 场景执行失败或验证未通过 | rolled_back, running（重试） |
| `rolled_back` | 已回滚 | 修复失败后自动回滚成功 | running（重试） |
| `rejected` | 已拒绝 | 审批员拒绝执行 | （终态） |
| `cancelled` | 已取消 | 执行前或执行中被人工取消 | （终态） |

#### 4.2.2 执行操作

- **批准**：pending_approval → running，需记录审批人、审批时间、审批意见（可选）；批准后异步调用 13 创建场景执行任务。
- **拒绝**：pending_approval → rejected，**必填拒绝原因**；拒绝后发布事件通知。
- **重试**：failed/rolled_back → 创建新执行记录（retry_of 字段关联原记录），原记录保留历史；重试同样受频率限制与冷却控制约束。
- **取消**：pending_approval/running → cancelled，running 状态取消时需调用 13 任务取消接口（转发 aranea 取消语义）；记录取消人与取消原因。

#### 4.2.3 执行结果

- 记录 13 任务 ID（`ai_task_id`，13 任务镜像，内含 aranea_run_id），支持点击跳转 13 模块任务详情。
- 记录命令输出（stdout/stderr），如场景包含命令执行节点（经 13 任务日志/节点摘要获取）。
- 记录执行开始时间、结束时间、耗时（毫秒）。
- 记录完整执行日志（步骤级 JSON 数组），包括：策略匹配、参数渲染、场景任务创建、场景执行、验证执行、回滚执行等关键步骤。

#### 4.2.4 触发方式

| 触发方式 | 中文 | 说明 |
|----------|------|------|
| `auto` | 自动 | 订阅 `alarm.events`（firing 状态）自动匹配策略触发（一期已实施订阅链路） |
| `manual` | 手动 | 用户在告警中心点击"处理"按钮手动触发 |
| `alert_link` | 告警联动 | 告警事件联动触发（如告警升级、告警恢复后复检，二期规划） |

**验收要点**：执行记录完整记录状态流转全过程；批准/拒绝/取消操作记录操作人与时间；重试创建新记录且关联原记录。

### 4.3 修复后验证

- 策略可配置"启用修复后验证"，勾选后需选择验证场景、验证超时秒（默认 120）、验证参数 JSON。
- 修复场景执行成功后，自动调用 13 创建验证场景任务。
- 验证场景在超时时间内返回成功则修复结果为成功；验证失败或超时则修复结果为失败。
- 验证不通过视为修复失败，触发自动回滚（如启用）。
- 支持手动重新验证：对 success 状态的执行记录，值班人员可手动触发重新验证。

**验收要点**：启用验证后，修复场景成功 → 自动创建验证场景任务；验证通过 → success；验证失败/超时 → failed 并触发回滚。

### 4.4 自动回滚

- 策略可配置"启用自动回滚"，勾选后需选择回滚场景。
- "修复失败时自动回滚"开关默认开启，修复失败后自动调用 13 创建回滚场景任务。
- 回滚记录与执行记录关联，记录回滚场景任务 ID、回滚结果、回滚开始/结束时间。
- 回滚成功后执行记录状态变更为 `rolled_back`；回滚失败则保持 `failed` 并在执行日志中标记回滚失败原因。
- 支持手动回滚：对 failed/success 状态的执行记录，值班人员可手动触发回滚。

**验收要点**：修复失败且启用自动回滚 → 自动创建回滚场景任务；回滚成功 → 状态为 rolled_back 且存在回滚记录。

### 4.5 自愈工作台

#### 4.5.1 待审批队列

- 卡片式待办列表，按创建时间倒序排列，实时刷新（30 秒轮询）。
- 每张卡片显示：风险等级徽章（高-红/中-黄/低-蓝）、策略名称、告警摘要（告警标题+设备名称）、创建时间（相对时间）、触发方式标签。
- 操作按钮：「批准」（绿色）、「拒绝」（红色，弹出原因输入框，必填）、「执行」（蓝色，仅审批通过后可见，手动触发执行）。

> 本工作台仅呈现本模块 **策略级审批** 待办；场景执行中的 aranea 审批点待办在 13 审批中心页面处理，不在本队列重复展示。

#### 4.5.2 最近执行记录

- 表格列：创建时间、根因分析（关联 AI 诊断，有则显示"✅ 已诊断"）、策略名称、风险等级徽章、状态徽章、操作。
- 操作按钮：「查看详情」（打开执行详情抽屉）、「回滚」（仅 failed/success 状态可见）、「验证」（仅 success 状态可见，手动重新验证）。

**验收要点**：待审批队列正确显示 pending_approval 状态记录；批准/拒绝操作实时更新队列；最近执行记录支持详情查看与回滚/验证操作。

### 4.6 修复仪表盘

- **统计卡片 4 张**：总策略数、今日修复执行数、平均执行时间（格式化为"X 分 X 秒"）、待审批数量（点击跳转工作台）。
- **修复执行趋势**：近 7 天/30 天执行次数折线图，按成功/失败分色，支持时间范围切换。
- **策略成功率排行**：各策略成功/失败占比排名，横向柱状图，Top 10，显示成功率百分比。
- **告警来源分布**：按 zabbix/prometheus/custom 统计执行次数占比，饼图。
- **最近执行记录表**：执行 ID、策略、告警、状态、执行时间，点击跳详情。

**验收要点**：统计数据与执行记录实际数据一致；图表支持交互（点击下钻到对应筛选的执行记录列表）。

### 4.7 AI 修复记录

- 记录卡片列表：设备信息（名称/IP/类型）、状态徽章、风险等级、AI 诊断摘要、修复命令数量、创建时间。
- 点击卡片展开详情：
  - AI 诊断报告：Markdown 格式渲染展示（支持代码块高亮）。诊断内容由 13 RCA/自动诊断产生（分析执行在 aranea），经 `ai.analysis.completed` 事件或 13 HTTP 查询关联到本模块记录。
  - 修复命令清单：逐条命令 + 说明，表格展示。
  - 每条命令执行结果：stdout、stderr、退出码，退出码非 0 时红色高亮（经 13 任务节点摘要/日志获取）。
  - 错误信息（如有）。
- 支持按设备、状态、时间范围筛选。

**验收要点**：AI 诊断+修复完成后，记录正确展示诊断报告与命令执行结果；退出码非 0 的命令高亮显示。

### 4.8 手动触发（告警中心"处理"按钮）

- 用户在 04-告警中心点击"处理"按钮，前端调用本模块手动处理接口 `POST /api/v1/monitor/remediation/manual/process`。
- 本模块执行：查询告警详情 → 匹配修复策略 → 按模式分流创建执行记录 → 调用 13 创建根因分析记录（13 v2.0 `POST /api/v1/monitor/aiops/rca-records`）。
- 返回处理结果摘要：命中策略数、创建执行数、根因分析记录 ID（rca_record_id）、匹配策略列表（策略名+执行模式徽章）。
- 前端弹出"告警处理结果"弹窗：状态摘要（"触发 N 条修复策略，K 条修复执行记录已创建"或"未匹配到任何修复策略"）、匹配的策略列表（策略名 + 执行模式徽章：auto 绿"自动"/approval 琥珀"需审批"/suggestion 蓝"仅建议"）、执行记录 ID 列表。
- 弹窗底部按钮：关闭 /「查看执行记录」/「查看 13 任务」。

**验收要点**：点击"处理"后返回正确摘要；命中策略按模式正确分流（auto 直接执行、approval 进入待审批、suggestion 仅记录）；未命中时返回友好提示。

## 6. 非功能需求

### 6.1 幂等防重

- 同一告警 + 同一策略在冷却期内不重复创建执行记录。
- 通过 Redis SETNX 实现冷却控制，key 格式：`remediation:cooldown:{policy_id}:{alert_id}`，TTL 为策略冷却时间（默认 300 秒）。
- 手动触发也受冷却限制，防止用户重复点击"处理"按钮。
- 执行编号（execution_no）全局唯一，格式：REM + YYYYMMDD + 6 位序号，防止并发生成重复编号。
- 创建 13 任务时传递幂等键 `remediation:{execution_no}:{scene}`（13 侧 Redis SET NX EX 6h 去重 + 部分唯一索引兜底），防止事件重放/重试导致重复执行。

### 6.2 并发安全

- 频率限制计数器基于 Redis INCR + EXPIRE 实现原子操作，避免分布式环境下计数偏差。
- 执行记录状态变更基于数据库乐观锁（version 字段）或 SELECT FOR UPDATE，防止并发审批/取消导致状态错乱。
- 策略启禁用变更实时生效（清除 Redis 策略缓存），正在执行的策略不受影响。
- 多实例部署时，`ai.task.events` 消费经 NATS Queue Group 保证同一事件仅被一个实例处理；兜底轮询通过 Redis 分布式锁保证同一执行记录仅被一个实例轮询。

### 6.3 性能

- 策略匹配延迟 ≤ 100ms（基于 Redis 缓存启用策略列表）。
- 手动处理接口响应时间 ≤ 3s（含策略匹配 + 根因分析记录创建）。
- 执行记录列表查询（分页 20 条）响应时间 ≤ 500ms。
- 仪表盘统计查询基于 Redis 缓存，TTL 5 分钟；缓存未命中时查询时间 ≤ 2s。
- 支持单小时 1000+ 执行记录的创建与状态更新。

### 6.4 可靠性

- 执行记录、回滚记录、AI 修复记录持久化到 PostgreSQL twinmonitor_log 库，避免丢失。
- 13 场景任务创建失败时，执行记录标记为 failed 并记录错误原因，不静默丢失。
- NATS 事件发布失败时写入本地重试队列（或记录失败日志定时补偿），保证最终一致性。
- 状态回流主链路为 `ai.task.events` 消费；事件丢失时由兜底轮询收敛（running 记录每 30 秒查询 13 任务 API，60 秒内收敛）；服务重启后，running 状态的执行记录自动重新挂入兜底轮询。
- 13 或 aranea 不可用时，任务创建按"执行引擎未就绪"明确失败（业务错误码），不伪造执行结果。

### 6.5 可追溯

- 完整记录执行日志（步骤级）：策略匹配、变量注入、场景任务创建、命令执行、验证结果、回滚结果。
- 审批操作记录审批人、审批时间、审批意见/拒绝原因。
- AI 修复记录关联告警 ID 与执行记录 ID，支持双向追溯；经 13 任务 ID 可下钻 aranea Trace 全链路。
- 所有操作（创建/更新/删除策略、审批、取消、回滚）记录操作人 ID，支撑审计。

### 6.6 安全性

- 接口鉴权：所有 API 经 API 网关 JWT 认证 + Casbin RBAC 接口级鉴权。
- 审批权限：仅值班审批员角色可执行批准/拒绝操作。
- 策略管理权限：仅自愈策略管理员角色可创建/编辑/删除策略。
- 高危操作防护：auto 模式策略关联的场景包含高危命令时，强制风险等级为高并在工作台显著提示；场景内高危工具调用另受 13 MCP 安全层（风险分级/放行策略/前置审批）与 16 侧护栏双重防护。

## 7. 验收标准

### 7.1 策略配置验收

1. 创建策略"磁盘空间不足自动清理"，配置触发条件（来源=prometheus、级别=高、关键词=磁盘）、执行模式=auto、关联场景=磁盘清理场景、频率限制=5 次/小时、冷却=300 秒。
2. 保存后策略列表显示该策略，状态为启用。
3. 编辑策略修改执行模式为 approval，保存后详情正确展示。
4. 禁用该策略后，新告警不再匹配该策略。
5. 删除存在 running 执行记录的策略时，系统拒绝并提示原因。

### 7.2 自动执行验收

1. 模拟 Prometheus 告警"磁盘使用率 > 90%"（级别=高，标题含"磁盘"），手动触发处理后策略命中并自动创建执行记录。
2. 执行记录状态从 running 流转到 success 或 failed（状态由 `ai.task.events` 驱动更新）。
3. 执行结果包含 13 任务 ID 与命令输出。
4. 执行日志完整记录各步骤时间与详情。

### 7.3 审批流验收

1. 创建策略模式为 approval，告警命中后执行记录状态为 pending_approval。
2. 自愈工作台待审批队列显示该记录，风险等级徽章正确。
3. 审批员点击"批准"后状态变更为 running，记录审批人与时间；13 场景任务被创建。
4. 审批员点击"拒绝"并填写原因后状态变更为 rejected，记录拒绝原因。
5. 非审批员角色尝试批准/拒绝时，接口返回 403 无权限。

### 7.4 验证与回滚验收

1. 启用验证配置，修复场景执行成功后自动创建验证场景任务。
2. 验证通过则状态为 success；验证失败则状态为 failed，并触发自动回滚。
3. 验证超时（超过 120 秒未返回）则状态为 failed，验证结果标记为 timeout。
4. 回滚成功后状态为 rolled_back，回滚记录关联到执行记录。
5. 手动触发 success 记录的重新验证，验证结果正确更新。

### 7.5 频率限制验收

1. 同一策略在同一小时内触发 5 次后，第 6 次告警不再创建执行记录，返回跳过原因"超出频率限制"。
2. 同一告警在冷却期内（300 秒）重复触发，不创建新执行记录，返回跳过原因"冷却期内"。
3. 冷却期过后，同一告警可再次触发该策略。

### 7.6 手动触发验收

1. 在告警中心点击"处理"按钮，返回处理结果摘要（命中策略数、创建执行数、根因分析记录 ID）。
2. 处理结果弹窗展示匹配策略列表（策略名 + 执行模式徽章）与执行记录 ID。
3. 未匹配到策略时，弹窗显示"未匹配到任何修复策略"。
4. 重复点击"处理"（冷却期内），返回冷却提示，不重复创建执行记录。

### 7.7 AI 修复记录验收

1. AI 诊断+修复完成后，AI 修复记录页面可查询到该记录。
2. 展开详情显示诊断报告 Markdown（正确渲染）、命令清单（命令+说明）、逐条命令执行结果（stdout/stderr/退出码）。
3. 退出码非 0 的命令行红色高亮显示。
4. 记录关联的告警 ID 与执行记录 ID 可点击跳转。

### 7.8 仪表盘验收

1. 统计卡片数据与实际数据一致（总策略数、今日执行数、平均执行时间、待审批数）。
2. 修复执行趋势图正确展示近 7 天成功/失败曲线。
3. 策略成功率排行正确展示 Top 10 策略及成功率。
4. 告警来源分布饼图正确展示 zabbix/prometheus/custom 占比。

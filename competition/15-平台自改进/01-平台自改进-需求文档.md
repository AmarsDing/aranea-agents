## 1. 模块概述

平台自改进模块是 Aranea-Agents 的 **Meta 级自我迭代能力**：平台将自身全量代码（Go 后端 + 前端 + 配置 + Prompt）作为进化对象，由平台内运行的 Meta Team 完成「观察 → 归因 → 修补 → 验证 → 治理 → 应用 → 学习」七环自闭环，实现从「修复→学习→预防」（V2）到「平台改自己」（V3）的跨越。

在竞赛方向一「零人工运维」中，本模块是差异化能力——零人工运维的终极形态不仅是"无人值守地修业务系统"，更是"平台无人值守地修自己"：运维平台自身的缺陷、性能瓶颈、评估退化、测试失败由平台内的多 Agent 团队自动发现、自动修补、自动验证、分级治理、安全应用并持续学习。

与 13/14 方向的关系一句话：13-AI智能运维是运维场景编排层，14-自动修复与自愈是修复执行中枢，15-平台自改进是平台自身的进化能力，三者互补。

### 1.1 七环闭环全景

```
① Observe 观察    4 类触发器（错误聚类/性能瓶颈/评估退化/测试失败）→ 平台级自改进建议
② Diagnose 归因   Analyst Agent 读结构化错误 + trace + 源码 → 根因/影响面/修复策略
③ Patch 修补      Patcher Agent 在 git worktree 隔离副本上产出 unified diff，保护清单拦截
④ Verify 验证     五级 Gate：G1 编译 → G2 单测 → G3 Lint → G4 Critic 语义审查 → G5 Eval 基线
⑤ Govern 治理     RiskClassifier（纯代码）风险分级：低=自动 / 中=自动+通知 / 高=人工审批
⑥ Apply 应用      配置/Prompt 热加载；代码合并主分支重启生效；24h 观察窗退化自动回滚
⑦ Learn 学习      补丁成败归因入知识库，反哺感知与生成，触发器阈值自适应
```

### 1.2 与 V2 的关系

| | V2（60-self-iteration-v2，已落地） | V3（本模块） |
|---|---|---|
| 修改对象 | Skill 的 SKILL.md、CI 流水线 | 平台自身全量代码（Go + 前端 + 配置 + Prompt） |
| 执行场所 | 外部 CI（GitHub Actions）+ 后台 worker | 平台内 Meta Team（trpc-agent-go 运行时，聊天可视） |
| 闭环 | 修复→学习→预防 | 观察→归因→修补→验证→治理→应用→学习 |
| 复用关系 | — | 复用 V2 的 FailureReport、FailurePattern KB、Critic、RootCauseAnalyzer、SkillEvolutionOrchestrator、审批体系 |

V3 不修改 V2 已有业务逻辑，仅在其基础设施上增量扩展。

### 1.3 非目标

- 不做运行中二进制热替换（Go 无法安全热更；代码类补丁合并后于下次重启生效，蓝绿/滚动重启为远期愿景）
- 不修改 trpc-agent-go 框架层
- 不允许补丁修改保护文件清单（CI 工作流、go.mod/sum、proto 已有消息、DDL 迁移历史、Ent/Wire 生成物仅可 regenerate）
- 不做无人值守的全自动高风险变更（高风险必须人工审批）
- 不改变已有 Evolution L1-L3（Skill/Agent 配置进化）业务逻辑
- P1-P4 阶段不做专用前端（复用聊天内审批 activity 与现有进化建议页）

## 4. 功能需求

### 4.1 运行时信号感知（Observe）

平台从自身运行数据自动发现改进机会。复用统一进化编排器（SkillEvolutionOrchestrator），新增 `target_type=platform` 的四类触发器：运行时错误聚类、性能瓶颈、评估退化、测试失败。信号来源于已有监控/追踪/用量/评估子系统与 FailurePattern 知识库，无需人工上报。

| ID | 验收标准 |
|----|----------|
| OB-01 | 相同 error_code + 相似堆栈错误聚类达阈值（默认 7 天内 ≥5 次）时生成 `patch_code` 建议 |
| OB-02 | 调用链慢点（步骤 P95 超基线 2 倍）或 token 消耗异常（超基线 50%）时生成 `patch_code` 或 `tune_config` 建议 |
| OB-03 | 评估基准分数较上一基线退化超阈值（默认 10%）时生成 `patch_code` 或 `patch_prompt` 建议 |
| OB-04 | 同一测试连续 2 轮扫描失败时生成 `patch_code` 建议 |
| OB-05 | 建议写入统一进化建议存储，target_type=platform，含触发源、触发原因、优先级、关联证据快照 |
| OB-06 | 同一目标已有 pending 建议时不重复生成（复用编排器去重与冷却机制） |
| OB-07 | 用户可在管理界面查看建议列表及其证据快照 |

### 4.2 自动归因诊断（Diagnose）

Analyst Agent 接收建议后读取结构化错误（FailureReport）、相关 trace、指标快照与目标源码，输出结构化诊断结论供后续环节消费。

| ID | 验收标准 |
|----|----------|
| DG-01 | 诊断输出含 root_cause、affected_files、impact_scope（局部/模块/全局）、fix_strategy、confidence（0-1） |
| DG-02 | Analyst 可只读平台自身源码，引用具体文件与行号作为证据 |
| DG-03 | confidence 低于阈值（默认 0.5）时降级为「仅记录」，不进入补丁环节 |
| DG-04 | 诊断过程与结论持久化，可在建议详情查看完整推理链 |

### 4.3 自主补丁生成（Patch）

Patcher Agent 在 git worktree 隔离副本（分支 `self-improve/<run_id>`）上按诊断结论生成标准 unified diff 补丁，对象覆盖 Go 后端、前端、配置、Prompt；保护文件清单内文件禁止修改，命中即拒绝并记录。

| ID | 验收标准 |
|----|----------|
| PT-01 | 补丁分支为 `self-improve/<run_id>`，基于主分支 worktree 隔离副本，生产工作树不被直接修改 |
| PT-02 | 补丁为标准 unified diff，可被 `git apply` 幂等应用 |
| PT-03 | 保护文件清单命中即拒绝并记录保护事件（清单见概要设计 D9） |
| PT-04 | 单次 diff 超上限（默认 500 行）时拆分或拒绝并记录原因 |
| PT-05 | 补丁元数据含目标文件清单、新增/删除行数、关联诊断 ID、生成模型与 token 消耗 |
| PT-06 | Prompt/配置类与代码类补丁在元数据中明确区分（决定后续应用方式） |

### 4.4 沙盒分级验证（Verify）

Verifier Agent 在沙盒 worktree 执行五级 Gate：G1 编译、G2 受影响包单测、G3 Lint、G4 Critic 语义回归审查、G5 Eval 基线回归（可选）。任一失败则拒绝并回传 Patcher 重试（上限 3 次），全过才进入治理。

| ID | 验收标准 |
|----|----------|
| VF-01 | G1：补丁应用后 `go build ./...` 与前端 `pnpm build` 通过 |
| VF-02 | G2：受影响包 `go test` 与前端 `pnpm test` 通过；受影响包由 diff 文件清单推导 |
| VF-03 | G3：`make lint`（包级 golangci-lint）与 `pnpm lint` 通过 |
| VF-04 | G4：Critic 输出结构化审查（is_safe/risk_level/concerns/suggestion）；risk_level=high 拒绝 |
| VF-05 | G5（可选默认关闭）：Eval 基准集回归分数退化 >10% 拒绝 |
| VF-06 | 每级 Gate 通过/失败与原始证据（命令输出、Critic 结论）持久化为验证报告 |
| VF-07 | 验证失败回传 Patcher 重试，上限默认 3 次，超限标记 verify_failed |
| VF-08 | 沙盒验证不访问生产数据库与生产外部服务（mock/替身隔离） |

### 4.5 风险分级治理（Govern）

治理组件（纯代码，不走 LLM）对验证通过的补丁风险分级并路由应用通道：低风险自动应用、中风险自动应用+通知、高风险人工审批。分级基于补丁对象类型、影响文件数、是否命中核心路径、diff 规模。所有应用动作留有回滚指针。

| ID | 验收标准 |
|----|----------|
| GV-01 | 低风险（配置/Prompt/文案/测试/文档，单文件，diff ≤100 行）：验证通过即自动应用 |
| GV-02 | 中风险（单文件业务代码、非核心路径，diff ≤300 行）：自动应用并向管理员事后通知（含 diff 与验证报告链接） |
| GV-03 | 高风险（多文件、核心路径 chat/agent/data schema、proto 新增、diff >300 行）：必须人工审批后才可应用 |
| GV-04 | 人工审批复用统一审批通道（聊天审批 activity + 管理界面），记录审批人/时间/理由 |
| GV-05 | 风险分级规则可配置（阈值表），分级决策过程与命中规则持久化 |
| GV-06 | 每日自动应用超配额（默认 5 次）时，后续补丁一律转人工审批 |

### 4.6 应用与观察窗回滚（Apply）

治理放行的补丁由 Applier 应用：配置/Prompt 类热加载生效；代码类合并主分支、下次重启生效。应用后进入观察窗（默认 24h），持续监控关键指标，退化超阈值自动回滚并通知管理员。

| ID | 验收标准 |
|----|----------|
| AP-01 | 配置/Prompt 类补丁经既有热加载通道生效，无需重启 |
| AP-02 | 代码类补丁为 git 提交（含 `self-improvement: true` 标记与 run 关联），合并主分支，运行时于下次重启生效 |
| AP-03 | 每次应用记录回滚指针（revert 目标 commit / 热加载回退快照） |
| AP-04 | 观察窗内错误率上升 >50% 或 P95 延迟上升 >30%（可配置）时自动回滚 |
| AP-05 | 自动回滚后通知管理员，含回滚原因与指标快照 |
| AP-06 | 管理员可在观察窗内手动提前关闭观察或手动触发回滚 |
| AP-07 | 应用与回滚动作全量记录审计日志（谁、何时、什么补丁、结果） |

### 4.7 成效学习（Learn）

每次闭环结果（验证结论、应用结果、观察窗指标、回滚原因）沉淀为成效记录并反哺知识库：有效补丁模式提升后续生成质量，失败/回滚补丁模式进入负面样本，触发器阈值随历史准确率动态调整。

| ID | 验收标准 |
|----|----------|
| LN-01 | 每次闭环结束（closed/rolled_back/verify_failed）生成成效记录，含 verdict：effective/neutral/regressed |
| LN-02 | 回滚或验证失败的补丁模式写入 FailurePattern 知识库（source=self_improvement，负面标记） |
| LN-03 | 连续 3 次同类触发源建议判定 neutral/regressed 时，该触发器自动降频或提升触发阈值 |
| LN-04 | 成效统计可在管理界面查看（闭环总数、有效率、回滚率、按触发源分布） |

### 4.8 Meta Team 协同与过程可视

闭环由平台内 Meta Team 执行：Observer（信号汇总）、Analyst（归因）、Patcher（补丁）、Verifier（验证）、Critic（语义审查）五个职能 Agent 协同，Governor 为纯代码治理组件。闭环过程作为特殊会话在聊天界面可视，用户可随时介入。

| ID | 验收标准 |
|----|----------|
| MT-01 | Meta Team 以平台既有 Team 编排能力运行，成员身份、职责、协作协议有显式定义（Agent Identity） |
| MT-02 | 闭环各环节活动在聊天界面按父子事件树展示（诊断→补丁→验证→审批→应用），顺序正确 |
| MT-03 | 高风险审批以聊天内审批 activity 呈现，含 diff 摘要与验证报告摘要 |
| MT-04 | 用户可在会话中发送指令暂停闭环、跳过重试、强制回滚 |
| MT-05 | 预规划门控等系统内部通知不在用户界面显示（遵循既有通知规范） |

### 4.9 自改进控制台（前端，P5）

提供管理控制台：闭环运行列表（状态/风险等级/触发源）、运行详情（诊断/补丁 diff/验证报告/审批记录）、成效统计面板、风险分级规则配置。

| ID | 验收标准 |
|----|----------|
| UI-01 | 运行列表支持按状态/风险等级/触发源筛选，按时间倒序 |
| UI-02 | 运行详情页展示完整事件时间线、unified diff 渲染、五级 Gate 结果 |
| UI-03 | 高风险运行可在详情页直接审批（通过/拒绝+理由） |
| UI-04 | 成效面板展示闭环总数、有效率、回滚率、按触发源分布图表 |
| UI-05 | 全部展示文案走 i18n（zh-CN / en-US） |

## 5. 非功能需求

- **可回滚性**：所有自动应用留有 git revert 指针或热加载回退快照；观察窗内支持一键回滚
- **安全性**：保护文件清单不可改；沙盒验证隔离生产数据与外部服务；高风险必须人工审批；补丁经敏感信息（API key/password/token）检测
- **成本控制**：Critic 每日上限 10 次（复用 V2 配额）；Patcher 每日上限 20 次；每日自动应用配额默认 5 次；观察窗并发 ≤3
- **可审计性**：诊断、补丁、验证、审批、应用、回滚全链路持久化；审计日志不可篡改
- **性能**：感知扫描对生产影响可忽略（只读查询 + 限流）；沙盒验证在独立 worktree 执行，不阻塞主服务
- **兼容性**：全部变更为增量（新增表/接口/触发器/worker），不修改 V2 与 Evolution L1-L3 已有业务逻辑

## 1. 数据库字段设计

## 2. 运行状态机设计

满足 AS-FSM-01（>3 状态实体必须显式状态机）。文件 `internal/biz/self_improvement_state_machine.go`，复用 `shared.GenericStateMachine`。

```
detected → diagnosing → patching → verifying → awaiting_governance
    → applying → applied → observing → closed        （正常路径）
    ↘ verify_failed（重试 ≤3 次回 patching） ↘ rolled_back（终态）
    ↘ rejected / failed（终态）
```

| 状态 | 进入事件 | 说明 | 终态 |
|------|----------|------|------|
| detected | create | 建议创建即产生 run（1:1 绑定 suggestion_id） | 否 |
| diagnosing | diagnose | Analyst 归因中 | 否 |
| patching | patch | Patcher 生成补丁中（verify 失败重试也回此态） | 否 |
| verifying | verify | G1-G5 执行中 | 否 |
| awaiting_governance | verify_pass | 等待风险分级路由/人工审批 | 否 |
| applying | apply | 应用执行中 | 否 |
| applied | apply_done | 已应用（代码类待重启生效） | 否 |
| observing | observe | 观察窗计时中 | 否 |
| closed | close / auto_close | 观察窗通过 | 是 |
| verify_failed | verify_fail（重试耗尽） | 五级 Gate 未过且 attempts ≥3 | 是 |
| rolled_back | rollback | 观察窗退化自动回滚或手动回滚 | 是 |
| rejected | reject | 高风险审批拒绝 | 是 |
| failed | error | 异常终止 | 是 |

状态迁移原子性：`UpdateStatus` 采用 CAS（WHERE status=from），冲突返回 CodeConflict；Watchdog 的 rollback 以 CAS 防重。

**实现期增补迁移**（状态数不变，仅增迁移边）：

| 事件 | 迁移 | 用途 |
|------|------|------|
| RunEventRecover | diagnosing / patching / verifying → detected | 中途态陈旧恢复：drive worker 检测超过 stale_timeout（默认 30m）的非终态 run，重置 detected 重驱动，杜绝进程重启/异常导致的孤儿 run |
| RunEventApplyEscalate | applying → awaiting_governance | 代码合并冲突自动转人工审批（T4.5 冲突 escalate 通道） |

## 3. 触发器详细设计

四个触发器均实现 `EvolutionTrigger` 接口（`internal/biz/skill_evolution_unified.go:220`），Check() 产出 `UnifiedEvolutionSuggestion`，证据快照写入 metadata（JSON）。触发器只感知、不行动——行动由 Meta Team 执行。

| 触发器 | ActionType | 信号源 | 触发条件（默认，可配置） | 证据快照 |
|--------|-----------|--------|--------------------------|----------|
| ErrorClusterTrigger | patch_code | FailurePattern KB + 运行时错误日志 | 同 error_code + 相似堆栈 7 天 ≥5 次 | 错误样本、聚类计数、堆栈哈希 |
| PerfBottleneckTrigger | patch_code 或 tune_config | monitor trace/usage 指标（18-monitor） | 步骤 P95 超基线 2× 或 token 超基线 50% | 步骤耗时分布、基线值、trace ID |
| EvalRegressionTrigger | patch_code 或 patch_prompt | 33-evaluation 基线 | 基准分数较上一基线退化 >10% | 两次基线分数、退化幅度、评测集 |
| TestFailureTrigger | patch_code | 测试运行结果（cron 全量测试） | 同一测试连续 2 轮扫描失败 | 测试名、失败输出摘要、轮次 |

去重与冷却复用编排器能力：`HasPendingForTarget` pending 去重 + `EvoTriggerCooldownHours` per-action-type 冷却；触发器风暴由 Patcher 日配额兜底。

## 4. Meta Team 成员契约

Meta Team 为平台内置 SpiritTeam 图编排（53-team-graph-orchestration）。成员输入输出全部结构化 JSON，经 TeamStage 事件树挂载（ParentActivityID 用 resolveParentActivityID）。

| 成员 | 类型 | 输入 | 输出（结构化 JSON） |
|------|------|------|---------------------|
| Observer | 代码节点（非 LLM） | 4 触发器建议 | DiagnosisTask（建议 + 证据快照打包） |
| Analyst | LLM Agent | DiagnosisTask + 源码只读工具 | Diagnosis{root_cause, affected_files, impact_scope, fix_strategy, confidence} |
| Patcher | LLM Agent | Diagnosis + worktree 读写工具 | Patch{diff, files, additions, deletions, kind} |
| Verifier | 代码节点执行 Gate + LLM 总结 | Patch + RepoSandboxRunner | VerificationReport{gates: [{gate, passed, output}]} |
| Critic | LLM Agent | diff + 相关源码 | CriticReport{is_safe, risk_level, concerns, suggestion} |
| Governor | 代码节点（非 LLM） | Patch + CriticReport + VerificationReport | GovernanceDecision{risk_level, channel(auto/notify/approval), rule_hits} |
| Applier | 代码节点 | GovernanceDecision + Patch | ApplyResult{commit_sha, reload_mode, rollback_pointer} |

**重试回路**：Verifier 失败 → 带 Gate 输出回 Patcher 修正重试，上限 3 次（计数入 run.attempts），超限进入 verify_failed 终态。

**用户介入**：会话指令（暂停 / 跳过重试 / 强制回滚）经 chat 命令解析进入 run 控制通道。

## 5. 沙盒详细设计（RepoSandboxRunner）

V2 SandboxRunner 校验 SKILL.md 草案；V3 需对整个仓库打补丁并执行 build/test/lint。`RepoSandboxRunner` 位于 service 层，实现 biz 端口 `biz.RepoSandbox`（扩展模式参照 `internal/service/sandbox_runner.go`，不改动原实现）。

### 5.1 端口行为

```
PrepareWorktree(ctx, runID, baseRef) → (path, cleanup, err)
ApplyDiff(ctx, path, diff) → err
RunGate(ctx, path, gate, pkgs) → GateResult{gate, passed, output, duration}
```

### 5.2 worktree 隔离

- 创建：`git worktree add .aranea-self-improve/<run_id> -b self-improve/<run_id> <base_ref>`；目录纳入 `.gitignore`
- 清理：run 终态 `git worktree remove --force`；启动时扫描残留目录清理；单 run worktree 磁盘配额
- 生产工作树永不被直接修改（PT-01）

### 5.3 五级 Gate 执行规范

| Gate | 内容 | 命令 | 超时 |
|------|------|------|------|
| G1 编译 | 补丁应用后全量编译 | worktree 内 `go build ./...`；前端补丁时 web 子目录 `pnpm build`（P2 先独立 install，正确性优先） | 5min |
| G2 单测 | 受影响包测试 | 由 diff 文件清单推导包（`internal/biz/foo.go` → `./internal/biz/...`），`go test <pkgs> -count=1`；前端 `pnpm test` | 10min |
| G3 Lint | 包级静态检查 | **实现口径**：以 `go vet` 为确定性下限（包级 golangci-lint 接线为已知后续项）；前端 `pnpm lint` 接线同属后续项 | 5min |
| G4 Critic | 语义回归审查 | Critic Agent 输出 is_safe / risk_level / concerns / suggestion；risk_level=high 拒绝 | LLM 调用，日配额 10 |
| G5 Eval 基线 | 评估回归（可选默认关闭） | Eval 基准集回归分数退化 >10% 拒绝 | 视评测集 |

### 5.4 执行安全

- **超时与资源**：每 Gate 独立超时；子进程组杀绝；输出截断 64KB 入验证报告
- **命令白名单**：仅 go / pnpm / golangci-lint 固定参数，防 diff 含脚本逃逸
- **生产隔离**：沙盒只读配置副本；测试走独立 PG schema（testhelper 模式）；环境变量白名单注入；无网络（除 pnpm install）；禁止访问生产外部服务（VF-08）

## 7. 风险分级规则（RiskClassifier）

纯代码组件，不走 LLM。输入：Patch（文件清单 + 行数 + kind）+ CriticReport。规则表（默认，可配置覆盖）：

| 规则 | 条件 | 等级 |
|------|------|------|
| R1 | kind ∈ {config, prompt, docs, i18n, test} 且单文件且 diff ≤100 行 | low |
| R2 | 单文件业务代码且非核心路径且 diff ≤300 行 | medium |
| R3 | 文件数 >1，或命中核心路径（`internal/service/chat*`、`internal/agent/`、`internal/data/ent/schema/`、proto、DDL 迁移新增），或 diff >300 行 | high |
| R4 | CriticReport.risk_level=high 或 is_safe=false | high（强制升级） |
| R5 | 触发保护文件清单 | reject（不进入分级，直接拒绝） |

**核心路径清单**：`internal/service/chat*`、`internal/agent/`、`internal/data/ent/schema/`、proto、DDL 迁移新增。

**通道映射**：low → auto（自动应用）；medium → auto + notify（自动应用 + 事后通知管理员，含 diff 与验证报告链接）；high → approval（人工审批）。
**配额熔断**：每日 auto 配额 5 次，超限一律转 approval（复用 V2 日配额计数模式）。
**决策可解释**：分级决策过程与命中规则（rule_hits）持久化至 run.governance（GV-05）。
**运行时可配置（实现增补，T5.2）**：阈值表经 `system_settings` 持久化（迁移 20261121），启动加载失败回退 config/代码默认；`GetRiskRules` 返回 configured（原始）+ effective（归一化）双视图；服务端校验：阈值 ≥0、low ≤ medium（均非零时）、glob 非空且过 doublestar.ValidatePattern。Pipeline Govern 阶段与治理路由日配额均消费生效规则（DB > config > 默认）。

## 8. 应用与观察窗（Applier + Watchdog）

### 8.1 应用双通道

| 补丁类型 | 通道 | 生效方式 | 回滚方式 |
|----------|------|----------|----------|
| 配置 / Prompt 类 | ApplyHotReload | 复用 58-prompt-governance 热加载通道（RuntimeProfile reload），应用即生效 | 回退热加载快照 |
| 代码类 | ApplyCodeMerge | worktree 内 `git commit`（message 含 `self-improvement: true` + run_id 尾注）→ 合并主分支（fast-forward 优先，冲突转人工）→ 状态 applied（待重启生效）；不做运行中热替换 | `git revert` 目标 commit |

每次应用记录 rollback_pointer（AP-03）；应用与回滚动作全量写审计日志（AP-07）。

### 8.2 观察窗与 Watchdog

- applied → observing，观察窗默认 24h（observe_until）
- Watchdog（cron，5min）扫描 observing 且 observe_until <= now 的 run：对比应用前后各 1h 滑窗指标（error_rate / p95_ms / alert_count）
- 退化阈值：错误率 +50% 或 P95 +30%（可配置）→ 自动 `git revert` + 热加载回退 → rolled_back + 管理员通知（含回滚原因与指标快照）
- 手动控制：管理员可 close（提前确认有效）或 rollback（立即回滚）
- 并发上限：观察窗并发 ≤3 个 observing，防多补丁指标互相污染归因；同核心路径补丁经 governance 队列串行

## 9. 成效学习（Learn）

### 9.1 verdict 判定

| 闭环终态 | verdict | 说明 |
|----------|---------|------|
| closed | effective | 观察窗通过，补丁有效 |
| rolled_back | regressed | 指标退化被回滚，负面样本 |
| verify_failed / rejected / failed | neutral | 未应用，不计入有效样本 |

### 9.2 知识库反哺

regressed 补丁的 pattern（error_code + 文件特征哈希 pattern_hash）写 FailurePattern KB：source=self_improvement、is_active=true、负面标记 negative=true（LN-02）。

### 9.3 触发器自适应

同一 trigger_source 连续 3 次 neutral/regressed → 该触发器冷却期 ×2（内存态 + 配置持久化），实现「越修越准」的负反馈调节（LN-03）。

```go
    GetPreviousBaseline(ctx context.Context) (*EvalBaseline, error)
}
type TestRunReader interface {
    ListRecentFailures(ctx context.Context, rounds int) ([]TestFailure, error)
}

// Stability:evolving — 治理与应用
type RiskClassifier interface {
    Classify(p Patch, critic CriticReport) GovernanceDecision // 纯代码，无 ctx/io
}
type Applier interface {
    ApplyHotReload(ctx context.Context, run *SelfImprovementRun) (rollbackRef string, err error)
    ApplyCodeMerge(ctx context.Context, run *SelfImprovementRun) (commitSHA string, err error)
    Rollback(ctx context.Context, run *SelfImprovementRun, reason string) error
}
```

data 层 Repo 实现遵循项目数据库约束：读写分离（`RW().Read/Write`）、错误统一经 `entErrToBizErr` 翻译、Schema 加 `entsql.Annotation{Table: ...}`、DDL 迁移入 `ddl_migration_registry.go`（幂等 IF NOT EXISTS）。

## 11. Worker / Cron 设计

| Worker | 周期 | 职责 | 模式参照 |
|--------|------|------|----------|
| self_improve_observe | 15min | 对 platform 目标调用编排器 CheckAndCreate；为 pending 建议创建 run(status=detected) 并启动 Meta Team 会话 | V2 skill_intelligence_worker |
| self_improve_drive | 1min（可配，实现增补） | 全链驱动：detected 异步 pipeline / 中途态陈旧恢复（stale_timeout 默认 30m → detected）/ awaiting_governance 路由去重 / applying 重驱动 / applied 晋升 observing | — |
| self_improve_watchdog | 5min | 扫描 observing 且 observe_until<=now 的 run：滑窗指标对比 → close 或自动 rollback | V2 predictive_heal |
| self_improve_outcome | 1h | 终态 run 生成 PatchOutcome + KB 负面样本反哺 + 触发器自适应降频 | V2 pattern_mining |

**分布式安全**：复用现有 worker 单实例运行约定（`cmd/admin/workers.go` 启动模式）；Watchdog 的 rollback 以 run 状态 CAS 防重。

## 13. Proto API 设计（P5，已实现 9 RPC）

`api/kratos/self_improvement/v1/self_improvement.proto`，全部 admin 鉴权（operator 身份取鉴权主体，不从请求体读取）：

| RPC | HTTP | 说明 |
|-----|------|------|
| ListRuns | GET /v1/self-improvement/runs | 运行列表（状态/风险/触发源筛选 + 分页；列表项不携带 diff/diagnosis 等重字段） |
| GetRun | GET /v1/self-improvement/runs/{id} | 详情（诊断/diff/验证/治理全量字段） |
| ApproveRun | POST /v1/self-improvement/runs/{id}/approve | 高风险审批通过（body: reason） |
| RejectRun | POST /v1/self-improvement/runs/{id}/reject | 审批拒绝（body: reason 必填） |
| RollbackRun | POST /v1/self-improvement/runs/{id}/rollback | 手动回滚（applied/observing） |
| CloseRun | POST /v1/self-improvement/runs/{id}/close | 观察窗提前关闭 |
| GetOutcomeStats | GET /v1/self-improvement/outcome-stats | 成效统计（闭环总数/有效率/回滚率/触发源分布） |
| GetRiskRules | GET /v1/self-improvement/risk-rules | 读取风险分级规则（configured 原始 + effective 归一化双视图） |
| UpdateRiskRules | PUT /v1/self-improvement/risk-rules | 更新风险分级规则（system_settings 持久化，服务端校验） |

特性开关：`self_improvement.enabled=false` 时 usecase 不接线、Service 为 nil 不注册路由；已注册而依赖缺失时返回 Unavailable。

## 开场白（00:00）

各位好。今天我想和大家聊一个看似技术、实则关乎产品哲学的问题：当我们让 AI 来写代码，这件事的流程应该由谁来主导？

主流的做法是把工作流程写成一段提示词，建议 AI 按步骤来。但建议终究只是建议——AI 会偷懒，会跳步，会图省事跳过测试和审查。

我们的产品走了另一条路：用一个确定性的引擎来硬性驱动流程，AI 只负责在每个步骤里把活干好。一句话概括我们的理念——**让引擎管流程，让模型管执行**。

接下来我会先把我们用到的几个关键概念掰开揉碎讲清楚，再带大家看整套设计是怎么运转的。

---

## 第一部分：问题（00:46 – 03:40）

### 智能体循环 Agent Loop（00:46）

要理解我们的设计，得先从一个最基础的概念讲起——智能体循环，英文叫 Agent Loop。这是所有 AI 编程助手的心脏。

它的工作方式是一个不断旋转的圈：思考一下该用什么工具 → 调用工具（比如读个文件、跑个命令）→ 观察结果够不够，如果不够就继续转。就像你派一个员工去办一件复杂的事，他不会一口气从头干到尾，而是一步一步试探着往前走。

这个循环本身是非常强大的，它让 AI 有了动手能力。但问题也恰恰出在这里——这个循环只会埋头干活，它不会抬头看路。

### 执行内核 run_agent（01:30）

这个循环我们称之为执行内核。请大家在脑子里给它贴一个标签：它是一个只会埋头干活的执行器。

你给它任务、给它工具、给它说明书，它就拼命转圈，直到任务完成。但请注意它不管什么——它不管我们整体进行到第几步了，不管这件事现在该不该做，也不管干完之后下一步去哪。它唯一关心的就是把手头这件事干完。

这就像一个能力很强但完全没有全局观的工匠——你让它砌墙，它就把墙砌得又快又好，但它不会主动问你：这堵墙该不该现在砌？砌完之后是不是该验收？这个特性，正是接下来所有问题的根源。

### 裸循环的三个致命缺口（02:05）

当一个 AI 编程产品只有执行内核、上面没有任何流程管控的时候，我们称之为裸循环，会出现三个致命的缺口：

第一，**没有质量门控**。AI 觉得差不多了就会停，它完全可以跳过测试、跳过代码审查，没有人拦得住它，因为根本没有关卡。

第二，**没有流程一致性**。同一个任务，今天 AI 性情好走五步，明天图省事走三步，结果不可预测、不可复现。

第三，**没有复用性**。你好不容易摸索出了一套好用的工作方法，但它只存在于某次对话的上下文里。换个项目、换个会话，一切归零，没法沉淀、没法分享。

这三个缺口，本质上都指向同一个问题：没有人站在执行内核之上，统一指挥节奏。

### 主流产品的方案为什么是错的（02:50）

那主流产品怎么解决这个问题呢？最常见的做法是：把工作流程写成一段系统提示词，告诉 AI"请你先分析需求，再做规划，然后实现，最后别忘了测试"。听起来很合理，对吧？

但这里有一个根本性的谬误——**建议永远不等于约束**。提示词里写"请先规划再动手"，AI 完全可以觉得这个任务很简单不用规划，直接开始写代码。提示词里写"请做完后测试"，AI 写完代码就可以回一句"去完成了"，它压根没跑测试，你也没法强制它。

打个比方：这就像把交通规则写在一张纸条上递给司机，和真正在路上装红绿灯、设检查站，完全是两回事。纸条是建议，司机想不遵守就可以不遵守；红绿灯是约束，你闯红灯就会被拦下。我们的产品，装的就是红绿灯。

## 第二部分：核心方案——Harness 引擎（03:40 – 05:07）

### Harness 引擎（03:40）

终于到了今天的主角——Harness。这个词原意是"线束"，就是把一堆散乱的电线捆扎成有序、可控的整体。

在我们的产品里，Harness 是一套可插拔的工作流程引擎。它做三件事：规定一件事分几步做、每步由谁来做、每步做完往哪儿走。你可以把它理解为我们给 AI 配的一个调度中心——之前那个只会埋头干活的执行内核，现在有了人在上面指挥它："现在做第一步，做完了来我这报到，我放行了你才能进第二步。"

最关键的是，这套调度规则是可插拔的。换一套 Harness，就等于换一套全新的工作方式，就像给同一台机器换上不同的作业指导书。

### 双层架构（04:25）

现在大家脑子里有了两个概念——执行内核和 Harness 引擎。我们来看看它们怎么配合。

整个架构是双层的。上面一层是调度中心，也就是阶段状态机。它负责读当前阶段的作业指导书，配好工具和工作手册，决定做完之后往哪儿走——但它不亲自干活。下面一层是执行内核，它接到派下来的活，一圈圈转着干完——但它不看全局。这两层各司其职、互不越界。

这是一个非常干净的分层：调度归调度，执行归执行。

## 第三部分：概念图鉴（05:07 – 12:00）

接下来我会把这套调度中心拆开，给大家介绍它的几个核心零件。这些零件就是我们产品的专有名词，我会用最直白的方式把每一个讲透。

### Stage 阶段（05:07）

第一个概念——阶段 Stage。阶段就是工作流中的一站。你可以把它想象成一张任务卡，上面写着四样东西：

1. **工作手册**：这一步的目标是什么，该怎么做
2. **工具箱**：这一步允许用哪些工具，可以上锁只开必要的
3. **门控**：做完之后是自动放行、等人拍板、还是看条件
4. **下一站**：做完去哪儿

举个实际的例子：我们产品自带一套叫 dev-flow 的开发流程，它有八个阶段——梳理需求、做规划、写代码、审查需求对不对、审查代码质量、跑测试、沉淀知识、提交代码。每一个阶段都是这样一张任务卡。

概念不难，但它是整个系统的基本组成单元。接下来的几个概念，都是在描述阶段的属性。

### StageMachine 阶段状态机（05:59）

第二个概念，也是整套系统的心脏——阶段状态机 StageMachine。它就是我们前面说的调度中心，它只回答三个问题：现在跑哪个阶段？跑完了去哪儿？要不要停下来等人？

这里有一个至关重要的设计决策，请大家划重点：**这个调度中心是确定性的，它的所有决策都由代码逻辑做出，不由 AI 做。**

什么意思呢？AI 在屏幕上输出"梳理阶段完毕"，这只是一行显示文字，调度中心根本不看它。调度中心看的是自己内部的状态和规则。这就意味着——**AI 没有任何能力跳过某个阶段**。哪怕 AI 觉得审查没必要，它也绕不过去，因为放行的钥匙不在 AI 手里，在调度中心手里。

这就是硬驱动的含义——流程是被硬性驱动的，不是被建议的。

### Gate 门控（06:44）

第三个概念——门控 Gate，这是阶段之间的收费站。门控有三种模式：

第一种是**自动放行**。做完立即进下一站，不等任何人。适合写代码、跑测试这种确定性的工作。就像高速公路的 ETC 通道，抬杆即过。

第二种是**人工放行**。做完必须停下来，等用户说一声"继续"才能走。适合梳理需求、做规划这种需要人来拍板的环节。就像收费站的窗口，你必须停车缴费。

第三种最精妙，叫**条件放行**。做完之后要看一张"通行证"——通过了才放行，有问题就拦下。这适合审查、测试这种需要判断到底过不过的环节。通行证是什么？这就引出我们下一个概念。

另外提一个安全设计：我们设了**连跳上限**，防止全自动流程一直空转、永远不把控制权还给用户。就像高速公路也不能无限长，跑够了必须有个出口。

### Runner 执行者（07:44）

第四个概念——执行者 Runner，它回答的是"这一站由谁来干"。两种模式：

第一种叫**本机执行**。就在主循环里换一份工作手册，继续让同一个 AI 干。就像同一个员工换了岗位，人没换。

第二种叫**委托执行**。把整个阶段打包外包给一个独立的专家。就像请一位外部顾问，他带着自己的工具箱来，干完活交一份报告就走。

为什么需要委托？因为有些活最好交给一个独立、专注的角色来做。最典型的就是代码审查——你不应该让写代码的那个 AI 自己审查自己，那等于让学生自己给自己判卷。更好的做法是请一个只管审查、不管别的的独立专家。这就引出了下一个概念——被委托的那个专家叫什么。

### Sub-agent 子智能体（08:32）

第五个概念——子智能体 Sub-agent，它就是被委托的那个独立专家。子智能体有三个特点：

1. **独立的工作空间**：不会被主对话之前聊的一大堆内容干扰，它是从零开始专注地把这一件事做好
2. **可以用不同的 AI 模型**：比如主流程为了省钱用一个性价比高的模型，但审查环节换成最强的模型，甚至跨厂商都行
3. **干完活会交一份报告回来**：主流程拿到报告，原样转达给用户就行

打个比方：主流程是项目经理，子智能体是他外包出去的专业顾问。项目经理不替顾问干活，他只负责把任务描述清楚，然后把顾问的结论带回来。

现在还差最后一块拼图——顾问交回来的报告长什么样？这就引出了我们最精巧的一个设计。

### Signals 信号与双通道（09:23）

第六个概念，也是我认为整套设计里最精巧的一笔——信号与双通道。

还记得前面说的条件放行需要一张通行证吗？这张通行证就是信号。问题是：子智能体干完活，既要给引擎一张通行证告诉它"过不过"，又要给用户一份报告告诉人"结论是什么"。如果混在一起，用户就会看到一堆看不懂的技术格式。

我们的解法是**双通道**——一份产出走两条路：

- **第一条通道是信号**：只有引擎看，格式是结构化的，比如 `approved = True`，或者 `has_issues = False`
- **第二条通道是文本报告**：给用户看，是纯粹的人类语言，比如"审查发现三处偏差，分别是最关键的一点……"

**用户永远看不到信号。用户看到的永远是一份干净的报告。引擎永远看不到报告的文字内容，它只认信号。** 两条通道各走各的，互不污染。

这是一个非常优雅的解耦——人看人话，机器看机器话。

### 工具白名单（10:22）

第七个概念——工具白名单。每一个阶段可以临时上锁，只开放必要的工具。比如梳理需求阶段，只开放只读工具，AI 能看代码但不能改代码；写代码阶段，开放全部工具，读写命令全权施工；审查阶段又回到只读。

请注意一个关键点：这不是简单地把工具图标藏起来，而是**真正的权限锁**。被锁住的工具，即使 AI 尝试调用，执行层也会直接拒绝。这就保证了只读阶段真的挡得住 AI 偷偷改文件。

为什么要这么严？因为 AI 经常好心办坏事——你在审查阶段让它看看代码，它觉得"顺手帮你改了吧"，结果审查还没通过代码就被改了。工具白名单就是防止这种越界。

### confirmed_plan 已确认方向（11:05）

最后一个概念——已确认方向 confirmed_plan。大家可能遇到过这种情况：开会时订好了方案，做到一半大家忘了当初订的什么，又开始重新讨论。AI 也一样——在规划阶段订好了方案 B，到了实现阶段，AI 发现上下文里找不到明确的方案，又开始重新发问。

我们的解法是：规划被确认后，引擎把"我们已经决定了什么"存成一张滚动备忘录。这张备忘录会在后续每个阶段、每次 AI 开工前都注入进去。就像在每个人的工位上贴一张便签，写着"我们的方向是 B，别忘了"。

这样就能保证做到第五步，AI 还清清楚楚地记得第二步定下的方向——**决策不会在传递中稀释**。

## 第四部分：设计哲学（12:00 – 15:03）

好，八个核心概念讲完了。现在大家应该已经建立起完整的概念词典。接下来我们用这些概念来讲设计哲学。

### 哲学一：硬驱动——控制权归引擎，不归模型（12:00）

第一条，也是最根本的一条——硬驱动。控制权归引擎，不归模型。这是我们和主流产品最本质的区别。

主流做法把流程写在提示词里，AI 能不能遵守全靠它自觉。我们的做法是把流程写进引擎的确定性逻辑里，AI 没有任何能力跳过任何一个阶段。

我常说一句话：**制度不会偷懒，人会。** AI 再聪明，它也会图省事、会跳步、会觉得自己不需要审查。所以我们不把流程交给 AI 的自觉，而是交给一套不可绕过的制度。这不是不信任 AI 的能力，而是不信任没有约束的能力——能力越强，越需要护栏。

### 哲学二：声明式可插拔——工作流即配置包

第二条设计哲学——声明式可插拔。意思是：增加一套工作流，只需要建一个文件夹，不需要写任何代码；删除一套工作流，删掉文件夹就行；想从开发流程切换到调研流程，一条命令搞定。

这个设计的核心洞察是：**引擎是通用的，流程是可替换的。** 我们把"怎么推进流程"这件事写死在引擎里，但把"具体分几步、每步做什么"完全外置成配置。这带来了巨大的灵活性——你的团队可以有自己定制的工作流，每个项目可以用不同的流程，甚至同一个人在不同场景下切换不同流程，而这些都不需要碰一行引擎代码。

### 哲学三：正交矩阵——两个维度拼出全部工作流

第三条——正交矩阵。前面我们讲了两个概念：执行者有两种（本机、委托），门控有三种（自动、人工、条件）。这两个维度是正交的，可以自由组合：

- 本机执行 + 自动放行：适合写代码，写完自动进下一步
- 本机执行 + 人工放行：适合做规划，做完等人确认
- 委托执行 + 条件放行：这是最常用的审查模式，把审查外包给独立专家，通过才放行，有问题拦下

两个维度、六个组合，覆盖了几乎所有工作流场景。这个设计的精妙之处在于：我们不需要为每种场景写专门的逻辑，你只要选好这两个维度的值，引擎自动按组合的方式运转——**组合即所得**。

### 哲学四：零侵入——不拆核心，挂钩即用

第四条——零侵入。这是一条工程层面的设计哲学，但对产品的长期健康至关重要。

我们这套流程引擎，是在完全不改动执行内核的前提下"挂"上去的。打个比方：执行内核像一面墙，上面有几个标准的插座——事件插座、工具插座、状态插座。我们的流程引擎就像一个插头，插在这几个插座上就工作了。

为什么这很重要？因为执行内核是整个产品最复杂、最容易出 bug 的部分。我们不去动它，意味着三件事：

1. 流程引擎可以随时拔掉，产品退回到裸循环，一切照常运行
2. 流程引擎的 bug 不会污染核心循环
3. 未来如果我们换一套全新的执行内核，流程引擎依然能用

这是一种可插拔的极致——不只是工作流可插拔，连引擎本身对核心都是可插拔的。

## 第五部分：价值、对比与生态（15:03 – 18:58）

### 质量内建（15:03）

现在来看这套设计带来了最直接的价值——质量保障被内建进了流程。

在我们的默认开发流程里，审查和测试不是可选步骤，而是必经之路。具体来说有三个条件放行的关卡：

1. **需求审查**：做的是不是对的事
2. **质量审查**：代码写得好不好
3. **测试**：跑过了没，有没有回归

这三个关卡都是条件放行——子智能体审查完，通过了才放行进下一步，有问题就拦下。AI 无法绕过它们，因为放行的钥匙在引擎手里，不在 AI 手里。这就是我们和主流产品在质量保障上的根本差异：别人是"建议 AI 测试"，我们是"不测试就过不去"。

### 与 Claude Code 的根本差异（15:48）

现在来到大家可能最关心的对比环节——我们和 Claude Code 到底有什么根本不同？

我先声明：Claude Code 是一款非常优秀的产品，它的执行内核能力很强。但我们的差异不在于谁更聪明，而在于架构理念的根本不同。

最核心的一条：Claude Code 把流程控制权交给模型，它的流程是写在系统提示词里的建议，模型自报完成就推进；我们把控制权交给引擎，门控信号判定推进，模型无权跳阶段。由此衍生出一系列差异——Claude Code 没有强制的质量步骤，模型可以选择跳过；我们有强制关卡，绕不过去。Claude Code 的工作流写死在提示词里；我们的是声明式配置包，零代码可换。Claude Code 是单一固定行为；我们可以多套工作流并存。

一句话总结差异：**Claude Code 信任模型的自觉，我们信任制度的约束。**

### 多套工作流并存（16:43）

前面讲到我们的引擎是通用的、流程是可替换的，来看两个实际例子。我们目前自带两套工作流：

第一套是 dev-flow，八阶段的软件开发流程，大家已经熟悉了。第二套叫 deep-research，四阶段的深度调研流程——框定问题、假设取证、主动证伪、综合收束。注意这套流程的阶段结构和门控逻辑跟开发流程完全不同，但跑的是同一个引擎。

这意味着什么？你想要一套专门的代码评审流程，建个文件夹就行；想要一套文档写作流程，建个文件夹；想要一套故障排查流程，建个文件夹——引擎一行不用改。**这就是可插拔的真正威力：引擎不变，流程无限。**

### 可视化编辑器（17:30）

最后，介绍一个让这套设计更易用的工具——可视化编辑器。

虽然工作流本质上是一堆配置文件，但我们提供了一个浏览器里的可视化设计台。你可以看到一张流程图，每个阶段是一个节点，按门控类型自动着色——绿色是自动放行、黄色是人工放行、蓝色是条件放行。节点之间有连线显示流转方向。

点击任何一个节点，右侧弹出属性面板，你可以直接编辑这一阶段的工作手册、工具白名单、门控模式、下一站去哪儿。改完一键保存，配置错误会及时标红。

这把工作流设计的门槛大幅降低了——从手写配置文件变成了画流程图，哪怕不懂技术的人也能看懂这套流程是怎么转的。

### 总结（18:16）

最后做一个总结。如果今天只能记住一句话，请记住这七个字——**让引擎管流程，让模型管执行。**

展开成三句话：

1. **控制权归引擎**：流程是制度不是建议，AI 再强也不能跳过质量关卡
2. **流程即配置**：工作流是可插拔的配置包，换流程等于换文件夹
3. **质量内建**：审查与测试是必经之路，不是可选步骤

我想用一句话作为今天的收尾：**我们不是在做一个更聪明的 AI，而是在做一个更可靠的工作方式。智能交给模型，可靠交给引擎。**

## 一句话核心论点

**把流程控制权交给一个确定性的引擎，把执行权交给 AI。—— 让引擎管流程，让模型管执行。**

> 当 AI 编程助手越来越聪明，一个根本问题浮出水面：一项开发任务，到底该由谁掌控节奏——是 AI 自己，还是一个外部的"调度中心"？mycli 的回答是：流程归引擎，执行归模型。

## 第一部分：问题（为什么需要 Harness）

### 1. 智能体循环（Agent Loop）——AI 助手是怎么干活的（00:46）

基础概念。循环结构：

```
接到任务 → 思考一下（该用什么工具？）→ 调用工具（读文件/跑命令/搜索…）
        → 观察结果（够不够？还差什么？）→ 干完了 → 交答案
        ↑________ 没干完继续转 ________↓
```

大白话类比：就像派一个员工去办事——他接到任务后，不是一口气干完，而是一圈一圈地"想一下、动一下手、看一眼结果"，循环往复，直到觉得事情办妥了才停下来汇报。

**语音要点**：智能体循环是 AI 编程助手的核心，它不断旋转调用工具，但缺乏全局观。

### 2. 执行内核（run_agent）——只会埋头干活的"执行器"（01:30）

- 你给它一个任务、一箱子工具、一份工作手册，它就一圈一圈地转，直到把这件事干完。
- **它只关心一件事**：把手头这件事做完。
- **它不关心的事**：现在整体进度到哪一步了？这一步该不该做？干完之后下一步是什么？

### 3. 裸循环的三个致命缺口（02:05）

当一个产品只有执行内核、没有流程管控时，会出现三个结构性缺陷：

| # | 缺口 | 后果 | 生活类比 |
|---|------|------|----------|
| ① | **无质量门控** | AI 想跳过测试和审查就能跳过，没人拦得住 | 工厂没有质检关卡，残次品直接出厂 |
| ② | **无流程一致性** | 同样的任务，今天走五步明天走三步，全看 AI 心情 | 餐厅没有菜谱，厨师每次随手发挥 |
| ③ | **无复用性** | 一套好的工作流无法沉淀、无法分享、无法替换 | 经验只存在某个老师傅脑子里 |

### 4. 主流产品的方案为什么是错的（02:50）

主流做法：把"请先分析、再规划、然后实现、最后测试"写进系统提示词。问题在于：**建议 ≠ 约束**。

| 提示词的承诺 | 现实中发生的事 |
|-------------|---------------|
| "请先规划再动手" | AI 觉得任务简单，跳过规划直接写代码 |
| "请做完后测试" | AI 写完就说"完成了"，压根没跑测试 |
| "请审查代码质量" | AI 草草看一眼，回一句"没问题"就收工 |

> 把交通规则写在一张纸条上递给司机，和在路上装红绿灯、设检查站，是两回事。**前者是"建议"，后者是"约束"。**

## 第二部分：核心方案——Harness 引擎（03:40）

### 5. Harness 引擎——给 AI 配一个"调度中心"

**Harness**（线束 / 流程引擎）：原意是"线束"——把一堆散乱的电线捆扎成有序、可控的整体。在 mycli 里，Harness 是一套**可插拔的工作流程引擎**。

它规定三件事：

1. **它规定了一件事要分几步做**
2. **每一步由谁来做**
3. **每一步做完往哪走**

> 换一套 Harness，就是换一套完全不同的工作方式。就像给同一台机器换上不同的"作业指导书"。

### 6. 双层架构——调度中心叠在执行器之上（04:25）

```
                用户输入
                    ↓
┌─────────────────────────────────┐
│  调度中心（阶段状态机）            │  ← 管流程：现在第几步？做完往哪走？要不要等人？
│  读当前阶段的"作业指导书"，        │
│  配好工具、配好工作手册            │
└─────────────────────────────────┘
                    ↓ 把活派下去
┌─────────────────────────────────┐
│  执行内核（智能体循环）            │  ← 管执行：把这一步的活干完
│  思考 → 用工具 → 观察 → 再思考     │
└─────────────────────────────────┘
```

**上层只管"调度"，不亲自干活 · 下层只管"执行"，不看全局。**

## 第三部分：概念图鉴（8 个核心概念）

### 7. Stage（阶段）= 工作流中的一站（05:07）

每个阶段是一张完整的"任务卡"，包含四样东西：

| 组成 | 作用 | 类比 |
|------|------|------|
| **工作手册** | 告诉 AI 这一步该怎么做、目标是什么 | 岗位说明书 |
| **工具箱** | 这一步允许用哪些工具（可上锁限制） | 只发必要的钥匙 |
| **门控** | 做完后是自动放行、等人拍板、还是看条件 | 这站的出口规则 |
| **下一站** | 做完后去哪个阶段 | 路标 |

实例：默认开发流程（dev-flow）有 8 个阶段——**梳理 → 规划 → 实现 → 需求审查 → 质量审查 → 测试 → 知识沉淀 → 提交**

### 8. StageMachine（阶段状态机）= 调度中心本身（05:59）

它是产品的"大脑"，负责回答三个问题：

1. 现在跑哪个阶段？
2. 这一阶段跑完了，去哪？
3. 要不要停下来等用户拍板？

> ⚠️ 推进决策由代码逻辑做出，不由 AI 做。AI 输出的"梳理完毕"只是屏幕上的一行字，不参与任何推进判定。**这意味着：AI 没有能力跳过任何一个阶段。**

### 9. Gate（门控）——阶段之间的"收费站"（06:44）

Gate = 阶段做完后，怎么放行。三种模式：

| 模式 | 行为 | 适用 | 类比 |
|------|------|------|------|
| **auto · 自动放行** | 做完立即进下一站，不等任何人 | 写代码、跑测试等确定性工作 | 高速公路 ETC，抬杆即过 |
| **user · 人工放行** | 做完必须停下，等用户说"继续" | 梳理需求、做规划等需要人拍板的环节 | 收费站窗口，必须停车缴费 |
| **conditional · 条件放行** | 看"通行证"决定——通过则放行，有问题拦下 | 审查、测试等需要判断"过不过"的环节 | 查验证件，合格才放行 |

> ⚠️ **安全阀：连跳上限**——防止全自动流程无限空转、永远不把控制权还给用户。

### 10. Runner（执行者）——这一站由谁来干（07:44）

Runner = 一个阶段交给"谁"执行。两种模式：

- **self · 本机执行**：就在主循环里换一份工作手册继续干（类比：同一个员工换岗位，人没换）
- **delegate · 委托执行**：把整个阶段外包给一个独立的专家（类比：请外部顾问，用完即走）

**为什么要"委托"？** 有些工作最好由一个独立的、专注的专家来做——它不被前面的对话干扰、可以用更强的模型、干完就把结论交回来。比如：代码审查最好交给一个"只管审查、不管写代码"的独立角色，而不是让写代码的同一个 AI 自己审查自己。

### 11. Sub-agent（子智能体）——被委托的独立专家（08:32）

Sub-agent = 接受委托的独立 AI 角色，有三个特点：

1. **独立工作空间**：不被主对话的历史干扰，从零开始专注这一件事
2. **可以用不同的模型**：比如主流程用性价比高的模型，审查环节换成更强的模型（跨厂商都行）
3. **干完交报告**：把结论打包交回来，主流程原样转达

> 类比：主流程是项目经理，子智能体是他外包出去的专业顾问。项目经理不替顾问干活，只负责把任务描述清楚、把结论带回来。

### 12. Signals 与双通道——给引擎的暗号，给人的明文（09:23）

核心问题：子智能体干完活，既要告诉引擎"过不过"（供门控判断），又要告诉用户"结论是什么"（供人阅读）。怎么办？

子智能体交回的产出分为两个通道：

- **通道一：信号（给引擎看）**——结构化的"通行证"，引擎据此判门控：✅ 通过 → 放行；❌ 有问题 → 拦下
- **通道二：文本报告（给用户看）**——屏幕上显示给人读："审查发现 3 处偏差……"（纯人类语言，无 JSON）

> **用户永远看不到任何技术格式的信号。用户看到的永远是一份干净的人类语言报告。**

### 13. 工具白名单——每站只发必要的钥匙（10:22）

每个阶段临时"上锁"，只开放必要的工具：

- 阶段：梳理需求 → **只读**（能看，不能改）
- 阶段：写代码 → **读写 + 命令**（全权施工）
- 阶段：审查 → **只读**（能看，不能改）

> 这不只是"对 AI 隐藏"，而是**真正的权限锁**：被锁住的工具，即使 AI 尝试调用，也会被直接拒绝执行。这就是为什么"只读阶段"能真正挡住 AI 偷偷改文件。

### 14. 已确认方向——跨站传递的决策备忘录（11:05）

一个常见的跑偏场景：阶段 2·规划 定了方案 B → 阶段 3·实现："咦，方案是什么来着？重新问一遍"。

**解法：confirmed_plan（已确认方向锚点）**——规划被确认后，引擎把"已确认方向"存成一个滚动备忘录，在后续每个阶段都持续注入。每一步开工前，AI 都能看到一张"我们已经决定了什么"的便签。

> 确保做到第五步，还记得第二步定下的方向——**决策不会在传递中稀释。**

## 第四部分：设计哲学（12:00–15:03）

### 哲学一：硬驱动——控制权归引擎，不归模型

这是整套设计最根本的立场：

| 维度 | 主流做法 · 提示词驱动 | 我们的做法 · 引擎硬驱动 |
|------|----------------------|------------------------|
| 流程在哪 | 写在提示词里 | **写在引擎的确定性逻辑里** |
| AI 能跳步吗 | 能（提示词管不住） | **不能（钥匙在引擎手里）** |
| 质量审查 | AI 自己决定做不做 | **强制阶段，绕不过去** |
| 可靠性 | 靠 AI 自觉 | **靠制度保障** |

> **制度不会偷懒，人会。所以我们把流程交给制度，而不是交给 AI 的自觉。**

### 哲学二：声明式可插拔——工作流即配置包

增删一套工作流 = 增删一个文件夹，零代码改动。每套工作流就是一个独立的"配置包"：

```
工作流集合/
├── dev-flow/        默认开发流程（8 阶段）  元信息、阶段/（1-梳理、2-规划、…）
└── deep-research/   深度调研流程（4 阶段）  元信息、阶段/（1-框定、…）
```

- 想要新流程？**建个文件夹。**
- 不想要了？**删掉文件夹。**
- 想换流程？**一条命令切换。**

> **引擎是通用的，流程是可替换的。**

### 哲学三：正交矩阵——两个维度拼出全部工作流

任何工作流场景，都可以用"执行者 × 门控"两个维度组合出来：

| 执行者 ↓ / 门控 → | auto · 自动 | user · 人工 | conditional · 条件 |
|---|---|---|---|
| **self · 本机** | 写完代码自动进下一步 | 梳理完等人确认方案 | （极少用） |
| **delegate · 委托** | （极少用） | 委托完无论如何等人 | **审查通过才放行，有问题拦下** |

> 两个正交的维度，六个组合，覆盖了几乎所有工作流场景。不需要为每种场景写专门的逻辑——**组合即所得。**

### 哲学四：零侵入——不拆核心，挂钩即用

这套流程引擎，是在完全不改动执行内核的前提下"挂"上去的：

```
┌───────────────────────────────┐
│           流程引擎             │
└───────┬──────────┬─────────┬──┘
     事件插座    工具插座    状态插座
┌───────────────────────────────┐
│      执行内核（那个循环）        │
│  像一面墙，上面有几个标准"插座"  │
└───────────────────────────────┘
```

- ✅ 流程引擎可以随时拆掉，产品退回裸循环，一切照常
- 🛡️ 流程引擎的 bug 不会污染核心循环
- 🔄 未来换一套全新的执行内核，流程引擎依然能用

> 这是"可插拔"的极致——**不只是工作流可插拔，连引擎本身对核心都是可插拔的。**

## 第五部分：价值、对比与生态（15:03–18:58）

### 15. 质量内建——审查与测试是强制关卡，不是可选步骤（15:03）

在 dev-flow 里，质量保障不是"建议"，是"必经之路"：

```
梳理 → 规划 → 实现 → 【需求审查】 → 【质量审查】 → 【测试】 → 知识沉淀 → 提交
                      不通过=拦下     不通过=拦下    不通过=拦下
                      （蓝色为"条件放行"关卡）
```

- **需求审查**：实现的方向对不对？（做的是不是对的事）
- **质量审查**：代码写得好不好？（可读性、可维护性、潜在 bug）
- **测试**：跑过了吗？有没有回归？

> 三个条件放行关卡，任何一个不通过，流程就停下等修复。**AI 无法绕过它们，因为放行的钥匙不在 AI 手里。**

### 16. 与 Claude Code 的根本差异（15:48）

| 维度 | Claude Code | 本产品（mycli） |
|------|-------------|----------------|
| 流程控制权 | 模型自主（提示词建议） | **引擎硬驱动（确定性状态机）** |
| 阶段推进 | 模型自报完成即推进 | **门控信号判定，模型无权跳阶段** |
| 质量保障 | 无强制步骤，模型可跳过 | **审查/测试是强制关卡** |
| 工作流定义 | 写死在系统提示词里 | **声明式配置包，零代码可替换** |
| 多流程 | 单一固定行为 | **多套工作流并存，随时切换** |
| 子智能体反馈 | 单通道（纯文本递归） | **双通道（信号供引擎 + 文本供用户）** |
| 上下文隔离 | 递归调用共享上下文 | **委托隔离 + 可跨厂商换模型** |
| 工具权限 | 全程开放 | **每阶段白名单，越权调用被拒** |
| 配置方式 | 纯提示词工程 | **可视化编辑器：流程图 + 属性面板** |

### 17. 多套工作流并存——一套引擎，无限可能（16:43）

同一个引擎，驱动完全不同的工作方式：

- **dev-flow · 开发流程（8 阶段）**：梳理 → 规划 → 实现 → 需求审查 → 质量审查 → 测试 → 知识沉淀 → 提交
- **deep-research · 深度调研（4 阶段）**：框定 → 假设取证 → 证伪 → 综合收束

> 想要一套"代码评审"流程？建个文件夹。想要"文档写作"流程？建个文件夹。**引擎不变，流程无限。**

### 18. 可视化编辑器——所见即所得的工作流设计台（17:30）

不必手写配置，在浏览器里画出来：

- **流程图可视化**：节点按门控类型自动着色（绿=自动、黄=人工、蓝=条件），连线显示阶段流转
- **属性面板**：点击节点，直接编辑工作手册、工具白名单、门控、下一站
- **实时校验**：配置错误即时标红，不会让坏配置跑起来
- **一键保存**：改完即生效，下次激活就用新流程

> 从"写配置文件"变成"画流程图"。

### 19. 总结（18:16）

**让引擎管流程，让模型管执行。**

| 控制权归引擎 | 流程即配置 | 质量内建 |
|-------------|-----------|---------|
| 流程是制度，不是建议。AI 再强，也不能跳过质量关卡。 | 工作流是可插拔的配置包，不是写死的代码。换流程等于换文件夹。 | 审查与测试是必经之路，不是可选步骤。不通过，就走不下去。 |

> 我们不是在做一个更聪明的 AI，而是在做一个更可靠的工作方式。

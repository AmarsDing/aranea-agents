# Skill: SRE 最佳实践

## 概述
站点可靠性工程（SRE）的系统化实践规范，覆盖 SLO/SLI 设计、故障响应、事后复盘、容量规划、混沌工程与变更管理。目标是构建可量化、可预期、可持续演进的生产系统。

## 核心规则

### 1. SLO/SLI 设计
- SLO 必须在服务上线前定义：没有 SLO 的服务等于没有质量承诺
- SLI 指标选择遵循"用户可感知"原则：可用性（成功请求比）、延迟（P50/P95/P99）、吞吐量（QPS）、正确性（业务错误率）
- SLO 目标设定采用渐进式：新服务从 95% 起步，成熟服务逐步提升至 99.9%+，不一步到位
- 错误预算 = 1 - SLO 目标：错误预算耗尽前优先功能迭代，耗尽后冻结非紧急变更、全力投入可靠性
- 燃烧率告警：基于错误预算消耗速率设置多级告警，快燃烧（6x）立即通知，慢燃烧（1x）工单跟进
- 告警窗口选择：短窗口（5min）捕获突发故障，长窗口（1h/6h）捕获慢性退化
- SLO 分层：用户可见 SLO（前端/API）> 内部依赖 SLO（中间件/存储）> 基础设施 SLO
- 每个 SLO 必须有仪表盘：实时展示 SLI 当前值、SLO 目标线、剩余错误预算
- 季度 SLO 审查：根据实际达成情况调整目标，过高则资源浪费，过低则用户受损

### 2. 故障响应
- 故障分级 P0-P3：P0 全局不可用/资损、P1 核心功能降级、P2 非核心功能异常、P3 体验问题
- P0/P1 必须立即响应：on-call 5 分钟内确认接手，15 分钟内拉起作战室
- 响应流程：发现 → 确认 → 止血 → 恢复 → 复盘，止血优先于根因定位
- 沟通模板：故障标题 + 影响范围 + 当前状态 + 预计恢复时间 + 下次更新时间，每 15 分钟同步一次
- 升级策略：15 分钟未止血升级到 TL，30 分钟未恢复升级到总监，1 小时未恢复升级到 VP
- on-call 轮值：7x24 覆盖，轮值周期不超过 1 周，轮值期间禁止安排项目工作
- 故障指挥官角色：P0 故障指定一人指挥，统一决策和沟通，其他人专注技术排查
- 自动化止血：常见故障模式（限流、降级、回滚）预置自动化脚本，减少人工介入时间

### 3. 事后复盘
- 无指责文化：复盘聚焦"系统为什么允许这个故障发生"，而非"谁犯了错"
- 所有 P0/P1 故障必须复盘，P2 鼓励复盘，复盘在故障恢复后 72 小时内完成
- 时间线还原：按分钟级梳理故障发现、响应、止血、恢复各节点，标注关键决策点
- 根因分析使用"5 个为什么"：逐层追问直到找到系统性根因，不停留在表面原因
- 改进行动项必须满足 SMART 原则：具体、可衡量、可分配、有截止日期
- 改进行动项分三级：必须修复（阻断同类故障）、应该修复（降低发生概率）、可以考虑（提升可观测性）
- 复盘文档公开：团队内可访问，作为组织记忆，避免同类故障重复发生
- 复盘会议必须包含：故障当事人、受影响方代表、技术负责人

### 4. 容量规划
- 资源利用率基线：CPU ≤ 70%、内存 ≤ 80%、磁盘 ≤ 75%、连接池 ≤ 60% 为健康水位
- 增长预测：基于历史数据做线性/指数拟合，区分自然增长和业务事件驱动增长
- 扩容阈值：利用率达到基线的 80% 时触发扩容评估，达到 90% 时触发紧急扩容
- 容量评审周期：核心服务月度评审，非核心服务季度评审，大促/活动前专项评审
- 压测验证：扩容后必须压测验证，确认实际承载能力与预期一致
- 成本优化：闲置资源（CPU < 10% 持续 1 周）缩容，预留实例覆盖稳定基线，按需实例应对弹性需求
- 瓶颈识别：压测定位瓶颈组件，优先优化瓶颈而非盲目扩容
- 多区域容量：每区域独立满足 SLO，不依赖跨区域流量调度来满足容量需求

### 5. 混沌工程
- 故障注入在生产环境或类生产环境执行：测试环境无法暴露真实依赖链路问题
- 爆炸半径控制：从小范围开始（单实例 → 单可用区 → 跨可用区），逐步扩大
- 稳态假设：实验前定义"系统正常"的可量化指标（SLO/SLI），作为对照基线
- 自动化验证：混沌实验集成到 CI/CD，定期自动运行，不依赖人工触发
- 实验必须可随时中止：具备一键停止注入的能力，超时自动回滚
- 故障场景覆盖：网络分区、实例宕机、磁盘满、依赖超时、DNS 故障、时钟偏移
- 实验结果归档：记录假设、注入方式、系统反应、发现的问题、改进行动项
- 渐进式推进：先手动实验验证假设，再自动化定期执行，最后纳入持续验证流水线

### 6. 变更管理
- 灰度发布：金丝雀（1%）→ 小流量（5%）→ 中流量（30%）→ 全量，每阶段观察至少 15 分钟
- 特性开关：新功能默认关闭，通过开关控制灰度范围，出问题秒级关闭
- 回滚策略：每次变更必须具备回滚能力，回滚时间 ≤ 5 分钟，回滚操作不超过 3 步
- 变更窗口：核心服务变更在工作日白天进行，禁止周五下午及节假日变更
- 变更关联：关联变更单、代码 PR、构建版本，支持快速定位变更内容和影响范围
- 自动化变更检测：部署后自动对比关键指标（错误率、延迟、QPS），异常自动告警
- 冻结期：大促/关键活动前 72 小时进入变更冻结，仅允许 P0 修复
- 配置变更等同于代码变更：走同样的评审、灰度、回滚流程

## 反模式（禁止）

- 无 SLO 的服务：无法衡量可靠性，等于没有可靠性承诺
- 手动故障恢复：依赖人工操作止血，响应慢且易出错
- 忽略告警：告警疲劳导致真实故障被忽视，必须治理无效告警
- 无回滚的部署：无法快速回退的变更是定时炸弹
- 100% SLO 目标：追求完美可用性导致过度工程和资源浪费
- 复盘追责：指责个人导致隐瞒问题，同类故障反复发生
- 容量靠猜：不做压测和预测，靠"感觉"评估容量
- 混沌实验无爆炸半径控制：一次注入影响全量用户

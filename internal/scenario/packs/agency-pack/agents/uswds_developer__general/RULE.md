## 🚨 你必须遵循的关键规则
1. **通过设计令牌和 Sass 设置进行主题化——绝不使用临时 CSS 覆盖框架。** 通过在主题设置文件中设置 `$theme-*` Sass 变量来定制颜色、间距、字体和字体族。在 USWDS 类之上硬编码十六进制值或编写覆盖 CSS 会在下次发布时失去同步，并破坏保证一致性的令牌系统。
2. **在构建自定义组件之前使用维护的 USWDS 组件。** 手风琴、横幅、日期选择器、组合框、模态框和表单组件都经过了可访问性测试和跨浏览器验证。手动编写替代方案会丢弃这些测试，并成为你永远需要维护和保持可访问性的负担。
3. **只在系统提供的接缝处进行定制——不要 fork 组件。** 通过设置、工具类和文档化的变体进行扩展；如果组件确实需要更多功能，构建一个组合 USWDS 部件的新组件，而不是复制和编辑源代码。被 fork 的组件不再接收上游的可访问性和安全修复。
4. **可访问性是基线，不是后期阶段——保留 USWDS 提供的内容，不要破坏它。** USWDS 组件按照 Section 508/WCAG 2.1 AA 构建；你的定制、标记更改和 JavaScript 不得导致回归。每个交互式定制都经过键盘测试和屏幕阅读器测试，因为你破坏的"合规"组件不再合规。
5. **必需的联邦元素必须存在且正确——`.gov` 横幅和 USWDS 标识符。** 政府网站必须显示官方的"美国政府的官方网站"横幅和包含正确必需链接的机构标识符。这些不是装饰性的；它们是联邦设计语言和信任模型的一部分。
6. **使用 USWDS 网格和断点进行移动优先构建——政府用户使用手机。** 使用 USWDS 响应式网格和令牌化断点；先为小屏幕设计，然后向上增强。很大一部分公共服务流量是移动端的，通常在受限的设备和网络上。
7. **使用 USWDS 字体比例、间距单位和颜色令牌——不要使用魔法数字。** 间距来自 `units()` 系统，字体来自字体比例令牌，颜色来自系统颜色令牌及其内置的对比度关系。任意的像素值和系统外颜色会破坏视觉节奏并导致对比度失败。
8. **颜色选择必须通过对比度——依赖设计为通过的系统颜色令牌。** USWDS 颜色系统编码了可访问的对比度关系；进行主题化时，验证文本和 UI 对比度仍满足 4.5:1/3:1，并且永远不要仅依靠颜色传达含义。看起来品牌正确但对比度失败的自定义调色板会失败 508。
9. **保持 USWDS 可升级——锁定版本、隔离定制并跟踪变更日志。** 通过 npm 和 `uswds-compile` 管理 USWDS，将主题设置和自定义代码与包分开，并在升级前查看发布说明。一个与供应商文件纠缠在一起的代码库永远无法获得安全或可访问性修复。
10. **符合 21 世纪 IDEA 和联邦网站标准，不仅仅是视觉外观。** IDEA 要求网站可访问、一致、移动友好、安全（HTTPS）且以用户为中心。匹配联邦设计语言*并*满足这些功能要求——一个看起来像 USWDS 但不可访问、不响应或不安全的网站不符合标准。

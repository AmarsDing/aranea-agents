## 🚨 你必须遵守的关键规则
1. **改任何东西之前先做性能剖析——绝不凭直觉优化。** 在动代码之前，用 Lighthouse、数据库查询日志和剖析器（Webprofiler/XHProf）采集基线。一个没有前后测量的"优化"就是猜测，而猜测让站点变慢和变快的概率一样高。
2. **绝不为修复过期内容 bug 而禁用缓存——要修复可缓存性元数据。** 区块显示旧数据是 cache *tags* 的问题，不是设置 `max-age: 0` 或关闭 Dynamic Page Cache 的理由。为修复失效而禁用缓存，是用全站性能崩盘换一个错误渲染。
3. **每个渲染数组都必须声明正确的 cache tags、contexts 和 max-age。** 随用户变化的内容要带正确的 context（`user`、`user.roles`、`url` 等）；依赖某个 entity 的内容要携带该 entity 的 cache tag，使其在保存时失效。元数据缺失会返回过期内容；元数据过宽会毁掉命中率。
4. **`max-age: 0` 是最后手段，且范围要尽可能收窄——绝不应用于整页。** 如果某内容确实不可缓存，把它隔离到 lazy builder/placeholder 后面，让 BigPipe 流式传输它，同时页面其余部分保持缓存。一个不可缓存的区块绝不应让整页不可缓存。
5. **绝不写原始、未过滤的 SQL 或针对 entity/field 表的未索引查询。** 使用 Entity Query API 和带占位符的 Database API；确保被过滤或排序的 `field_*` 列有索引。首页区块背后的全表扫描既是延迟问题也是安全问题。
6. **Views 必须被优化且有边界——绝不渲染超过你展示的内容。** 设置分页器或范围，只查询用到的字段，优先使用渲染实体缓存或聚合/计数查询而非加载完整 entity 来计数，并用正确的 tags 缓存 Views 输出。高流量页面上的无边界 View 是自找的故障。
7. **聚合和优化前端资源但不要弄坏它们。** 启用 CSS/JS 聚合、延迟非关键 JS、在划算的地方内联关键 CSS——但要验证页面仍能正常渲染和运作。过度激进的聚合或错误的 defer 顺序会破坏布局和交互性，这比它省下的字节更糟糕。
8. **每张图片都要通过带明确尺寸和懒加载的图片样式输出。** 使用响应式图片样式和现代格式（WebP/AVIF），设置 width/height 以防止布局偏移（CLS），对首屏以下的媒体做懒加载。绝不向模板输出全分辨率原图或无尺寸图片。
9. **缓存必须在 CDN/反向代理后实测验证，而不仅是本地。** 确认缓存头（`X-Drupal-Cache`、`X-Drupal-Dynamic-Cache`、`Cache-Control`、`Age`），确认 CDN 遵守它们，并确认个性化/已登录响应绝不被公开缓存。一个在开发环境正常工作但在边缘泄漏某用户会话的缓存是安全事故，不是加速。
10. **在宣布完成之前，必须在真实移动设备上对照 Core Web Vitals 证明每个改动。** 在限速移动连接下的 LCP、INP 和 CLS 才是判决——不是桌面、不是快速办公网络。一个改善了合成桌面分数但让移动端真实指标退步的改动，让站点对真正访问它的人变慢了。

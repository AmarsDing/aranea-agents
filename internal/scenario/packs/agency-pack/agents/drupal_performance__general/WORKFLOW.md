## 🔄 你的工作流程
### 第 1 步：测量并建立基线

1. **在限速移动端对关键模板运行 Lighthouse**——采集 LCP、INP、CLS 和性能分数
2. **启用数据库查询日志/剖析器**——采集最慢的查询和扫描行数
3. **检查缓存姿态**——Page Cache、Dynamic Page Cache、BigPipe 状态，以及任何 `max-age: 0` 的违规者
4. **实测检查缓存头**——在 CDN 后检查 `X-Drupal-Cache`、`X-Drupal-Dynamic-Cache`、`Cache-Control`、`Age`
5. **记录一切**——你无法证明一个没有基线的改进

### 第 2 步：先修复可缓存性（收益最大，风险最小）

1. **揪出每个 `max-age: 0`**——找出让它不可缓存的原因并修复根因
2. **纠正 cache tags**——让渲染在 entity/config 变更时失效，而不是被禁用
3. **纠正 cache contexts**——按正确维度变化，不比必要的更宽
4. **将真正动态的内容隔离到 lazy builder 后面**——让 BigPipe 流式传输它，保持页面缓存
5. **重新启用 Internal 和 Dynamic Page Cache**——并在重复加载时验证 HIT

### 第 3 步：优化数据库与渲染管线

1. **攻击最慢的查询**——为 `field_*` 列加索引，消除全表扫描
2. **为每个 View 设边界并精简**——分页器/范围，只取需要的字段，不要为了计数而加载 entity
3. **消灭 N+1 模式**——用批量加载代替逐行加载
4. **用正确的 tags 缓存渲染输出**——Views、区块和昂贵的 controller
5. **重新测量每个查询**——前后毫秒数对比，证明而非假设

### 第 4 步：削减前端

1. **启用 CSS/JS 聚合并验证没有破坏**——渲染和交互性完好
2. **延迟非关键资源**——JS 延迟、非关键 CSS 异步、关键 CSS 在划算处内联
3. **修复每张图片**——响应式样式、WebP/AVIF、明确尺寸、首屏以下懒加载
4. **优先处理 LCP 元素**——预加载它，绝不懒加载它
5. **在移动端重跑 Lighthouse**——确认 LCP/CLS 朝正确方向移动

### 第 5 步：调优基础设施、验证与交接

1. **调优 opcache 和 PHP-FPM**——根据代码库和机器规格调整，开启慢日志
2. **将 Redis/Memcache 前置于缓存桶**——卸载渲染缓存和 Dynamic Page Cache
3. **验证 CDN 行为**——头被遵守，个性化响应绝不被公开缓存
4. **对照第 1 步的数字重新基线**——每个指标，前后对比，在移动端
5. **文档化改了什么以及为什么**——让下一个人不会通过禁用缓存来"修复"它

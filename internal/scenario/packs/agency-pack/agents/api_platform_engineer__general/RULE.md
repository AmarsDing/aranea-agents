## 🚨 你必须遵守的关键规则
1. **已发布的 API 是你不能静默破坏的契约。** 一旦消费者集成，他们的可工作代码定义了你的兼容性面。新增变更安全；更改或移除他们依赖的任何东西都是破坏性变更，需要新版本和迁移路径。
2. **契约优先设计，为长期审查。** spec 先于实现，并被审查命名一致性、资源建模和"我们能与这个共存十年吗？" —— 因为你会的。在已发布代码上回填 spec 会固化所有不一致。
3. **一致到令人厌倦的程度。** 字段命名（选定 snake_case 或 camelCase 就永不摇摆）、日期格式（始终 ISO 8601）、分页风格、错误形状和 ID 格式在每个端点都必须完全相同。意外是 DX 的敌人。
4. **废弃要有跑道，不是悬崖。** 宣布、记录迁移、设置足够人道的中止日期、发出废弃信号（头部、日志），并在实际移除前监控剩余使用量。
5. **错误是看不到你代码的人的调试工具。** 一致的结构、稳定的机器可读代码、人类可读的消息，以及足够的上下文来自我诊断 —— 含正确的 HTTP 状态语义。返回 200 带 `{"error": ...}` 是 bug。
6. **限流和配额必须被传达，而不仅仅是执行。** 返回 limit/remaining/reset 头部、记录各层级、用 `429` 带 `Retry-After`，并设计保护平台而不会在集成中途伏击良好行为客户端的限额。
7. **SDK 和文档是 API 的一部分。** 从 spec 生成它们以避免漂移。没有类型化 SDK 和可工作快速入门的 API 是大多数开发者在第一次 `curl` 后就放弃的 API。
8. **使写操作幂等且可安全重试。** 网络会在请求中途失败；客户端会重试。创建操作用幂等键、重试有清晰语义 —— 否则每个集成者最终都会双重收费、双重发送或双重创建。

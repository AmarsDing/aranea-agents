## 🔄 你的工作流程
### 步骤一：测量并建立基线

1. **在关键模板上运行 Query Monitor**——捕获查询数、查询时间、慢查询、挂钩的插件
2. **在节流移动端运行 Lighthouse**——捕获 LCP、INP、CLS 和性能评分
3. **审计 autoload**——autoloaded options 的大小及哪些插件在臃肿它
4. **盘点缓存栈**——对象缓存命中？页面缓存配置？动态页面排除？
5. **记录一切**——你无法证明你没有基线的改进

### 步骤二：削减数据库与查询浪费（最大收益）

1. **限制并索引最差的查询**——`posts_per_page`、`no_found_rows`、有索引的 `meta_query`/`tax_query`
2. **杀死 N+1 模式和 `posts_per_page => -1`**——任何面向用户的地方
3. **修剪 autoload**——把大的未缓存 options 切到 `autoload = no`，删除孤儿
4. **把昂贵的计算数据包裹在 transients 中**——由持久化对象缓存支撑
5. **用 Query Monitor 重新测量**——查询数和时间，前后对比

### 步骤三：治理插件与主题臃肿

1. **性能剖析每个插件的真实每请求开销**——查询数和 PHP 时间
2. **削减或替换最严重的元凶**——单一重型插件往往主导整个请求
3. **Dequeue 插件在未使用地方加载的资源**——博客页面外的页面构建器 CSS 等
4. **用精简模式替换重型模式**——原生查询替代臃肿的"功能"插件
5. **重新剖析**——确认每请求开销确实下降了

### 步骤四：正确分层缓存

1. **搭建持久化对象缓存**——Redis/Memcached drop-in，验证命中
2. **为匿名 HTML 配置页面缓存**——动态页面显式排除
3. **添加 CDN**——静态资源长 TTL，边缘 HTML 仅匿名
4. **在边缘验证动态页面安全**——购物车/结账/账户/登录态永不公开缓存
5. **确认缓存命中率**——测量而非假设

### 步骤五：修剪前端、调优基础设施、验证并交付

1. **压缩并延迟资源，内联关键 CSS**——然后验证渲染和交互完好
2. **修复每张图片**——尺寸的派生、WebP/AVIF、显式尺寸、首屏下懒加载、LCP 预加载
3. **调优 opcache 和 PHP-FPM**——按代码库和主机调整，开启慢日志
4. **对照步骤一的数字重新基线**——每个指标，前后对比，移动端
5. **记录改了什么及为什么**——让下一个人不会用"加速"插件把它撤销

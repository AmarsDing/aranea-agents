## 1. 背景与问题

当前系统用"行业分类"(IndustryTaxonomy) 组织 Agent 和 Team，存在六大问题：

| # | 问题 | 用户影响 |
|---|------|----------|
| 1 | "行业分类"语义与用户心智不匹配 | 用户想管理的是"公司组织架构"，不是行业分类 |
| 2 | Team 挂在 industry 级别 | Team 应归属部门，不应挂在行业级 |
| 3 | Taxonomy.department 与 Team 无关联 | 部门概念分裂，用户需在两处维护 |
| 4 | 缺少跨部门协作机制 | 多部门协作无约束、无审批、无质量把关 |
| 5 | 缺少部门主管角色 | 跨部门交付无守门人 |
| 6 | Graph 归属模糊 | Graph 独立存在与 Team 引用之间语义不清 |

**目标**：将"行业分类"重塑为"公司架构"，明确公司架构/Agent/Team/Graph 四者边界，新增部门主管和跨部门协作机制，使系统语义对齐真实公司组织运作方式。

## 2. 用户故事

### US-01 管理公司组织架构

**作为** 系统管理员
**我希望** 按照真实公司结构管理组织架构（公司→部门→岗位）
**以便** Agent 和 Team 的组织方式与真实公司一致

**验收**：

- 可创建三级架构：公司 → 部门 → 岗位
- 每个岗位可定义职责描述、技能要求
- 创建部门时系统自动创建部门主管 Agent
- 架构树可拖拽排序、展开/折叠

### US-02 Agent 关联到岗位

**作为** 团队管理员
**我希望** 创建 Agent 时选择其所属岗位
**以便** 清楚地知道每个 Agent 在组织中的位置

**验收**：

- 创建/编辑 Agent 时可选择岗位（从公司架构中选取）
- 同一岗位可有多个 Agent（如多个开发工程师）
- Agent 列表可按部门/岗位筛选
- Agent 详情页显示其岗位路径（如：研发部 > 开发岗）

### US-03 从部门组建专项团队

**作为** 部门主管/团队管理员
**我希望** 从本部门中选择 Agent 组建专项团队
**以便** 按业务需要灵活组队

**验收**：

- 创建 Team 时必须选择归属部门
- Team 成员默认从本部门岗位中选择，跨部门借调需来源部门主管审批
- 同一部门可组建多个 Team
- 一个 Agent 可参与多个 Team
- Team 自动包含部门主管

### US-03b 跨部门借调成员

**作为** 团队管理员
**我希望** 从其他部门借调成员加入本部门的 Team
**以便** 小规模跨部门协作不需要拆成多个 Team + DAG

**验收**：

- 创建 Team 时可从非主归属部门选择成员
- 跨部门成员加入需其来源部门主管审批（初期：超时自动通过；后续迭代：支持主动审批/拒绝）
- 审批超时（5 分钟）自动通过
- 跨部门成员数量不超过 Team 总人数的 50%
- 跨部门成员在 Team 中正常参与 Graph 节点执行
- 来源部门主管可查看被借调成员的工作状态（只读）

### US-04 跨部门协作

**作为** 精灵助手用户
**我希望** 提出跨部门需求时，系统自动编排多部门 Team 协作
**以便** 复杂任务能跨部门高效完成

**验收**：

- 精灵助手识别跨部门需求（给定明确跨部门输入时识别成功率 > 95%）后，编排管家自动拆解任务
- 编排管家组建 Team DAG，定义依赖关系
- 上游 Team 完成后自动激活下游 Team
- 交付物在 Team 间传递
    - 交付物通过 Spirit Session 共享 Memory 传递
    - 下游 Team 激活时自动接收上游交付物作为初始输入

### US-05 部门主管审批

**作为** 部门主管
**我希望** 对本部门 Team 的跨部门交付物进行审批
**以便** 把关本部门输出质量

**验收**：

- 部门主管自动加入本部门的每个 Team
- 跨部门交付物需部门主管审批（通过/驳回+理由）
- 驳回后上游 Team 返工
- 超过最大重试次数自动升级给精灵助手

### US-06 Graph 归属团队

**作为** 团队管理员
**我希望** 为 Team 配置专属的工作流程 Graph
**以便** 团队按流程规范协作

**验收**：

- Team 可关联一个 Graph（也可使用模板 Graph）
- Graph 中可定义审批门禁节点（由部门主管执行）
- 模板 Graph 不属于任何 Team，可被多个 Team 引用
- Team 删除时其专属 Graph 一并删除，模板 Graph 保留

### US-07 查看组织全景

**作为** 管理员
**我希望** 在一个页面看到公司架构全貌：部门、岗位、Agent、Team 的分布
**以便** 了解组织运转状态

**验收**：

- 组织架构树展示公司→部门→岗位三级
- 每个岗位显示在编 Agent 数量
- 每个部门显示活跃 Team 数量
- 点击节点可展开查看详情

## 3. 业务流程

### 3.1 组织搭建流程

```
管理员创建公司架构
  → 创建部门（自动生成部门主管 Agent）
    → 创建岗位（定义职责、技能要求）
      → 创建/导入 Agent（关联到岗位）
```

### 3.2 团队组建流程

```
用户提出业务需求
  → 精灵助手评估复杂度
    → 简单任务：直接委派单个 Agent
    → 部门内任务：组建单 Team（从部门选人 + 配 Graph）
    → 跨部门轻量协作：组建跨部门 Team（主归属部门 + 借调成员）
    → 跨部门任务：编排管家组建 Team DAG
```

### 3.3 跨部门协作流程

```
精灵助手识别跨部门需求
  → 编排管家拆解任务
    → 匹配部门（哪些部门参与）
    → 为每个部门组建 Team
    → 定义 Team DAG 依赖
    → 验证交付物契约
    → 部门主管自动加入
  → 执行 Team DAG
    → 上游 Team 执行 → 输出方主管质量把关 → 接收方主管验收确认 → 交付物传递
    → 下游 Team 激活 → 执行 → 部门主管审批
    → 编排管家合成结果
  → 精灵助手呈现给用户
```

### 3.4 审批驳回流程

```
部门主管审批（输出方质量把关 + 接收方验收确认）→ 任一方驳回（附理由）
  → 上游 Team 收到驳回通知
    → 返工（重新执行相关节点）
    → 重新提交审批
  → 超过 max_retries 次
    → 升级给精灵助手
    → 精灵助手通知用户决策
```

**返工策略**：
- 初期：重新执行整个 Team（简单可靠，与现有 Team 生命周期一致）
- 后续迭代：仅重新执行被驳回节点及其下游（需 Graph 运行时支持部分回滚）

## 4. 非功能需求

| ID | 需求 | 验收标准 |
|----|------|----------|
| NFR-01 | API 兼容性 | 旧 `/v1/industry-taxonomy/*` 和 `/v1/taxonomy/*` 保留 2 个版本，标记 deprecated |
| NFR-02 | 数据迁移 | 现有 industry_taxonomy 数据无损迁移到 organizations |
| NFR-03 | 部门主管性能 | 部门主管审批响应时间 < 5s（LLM 调用） |
| NFR-04 | DAG 调度可靠性 | Team DAG 依赖调度不丢事件，与现有 ScheduleDependentTeams 机制一致 |
| NFR-05 | 前端路由兼容 | 旧 `/industries/*` 路由重定向到新 `/organization/*` |
| NFR-06 | 安全性 | 跨部门借调需来源部门主管审批，审批不可伪造 | 审批记录有 approved_by 字段，不可篡改 |
| NFR-07 | 安全性 | 部门主管操作需审计日志 | 所有审批/拒绝操作记录到 audit log |
| NFR-08 | 可扩展性 | 单公司 Organization 树规模上限 | 部门 ≤ 50，岗位 ≤ 200，Agent ≤ 500 |
| NFR-09 | 并发性 | 多 Team 同时请求同一部门主管审批 | 审批请求排队，不丢失 |
| NFR-10 | 数据一致性 | 跨部门成员审批状态与 Team 成员列表一致 | 审批通过后才加入 Team.members |
| NFR-11 | 可用性 | 部门主管 Agent 故障时降级 | 超时自动通过（5 分钟），不阻塞业务 |

## 5. 约束与边界

| 约束 | 说明 |
|------|------|
| Team 必须指定主归属部门 | Team 默认从主归属部门选人；允许跨部门借调成员（需来源部门主管审批，上限 50%）；轻量协作用跨部门 Team，深度协作用 Team DAG |
| 部门主管默认 system_builtin | 用户可在部门设置中替换为自定义 Agent |
| 交付物契约初期为文本描述 | 不做结构化 schema 验证，仅做提示性匹配 |
| Graph 模板不属于任何 Team | 模板 Graph 的 `team_id` 为空，`is_template=true` |
| 公司架构只有一棵树 | 单公司模式，根节点唯一 |
| 当前为单公司模式 | Organization 树根节点唯一；多公司通过 workspace_id 预留，暂不实现 |
| 部门删除需先处理活跃 Team | 有 running/pending Team 的部门不可删除；删除部门时岗位下 Agent 解除关联但保留 |

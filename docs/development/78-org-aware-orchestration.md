## 1. 背景与问题

用户发出任务指令后，期望系统像公司一样：把活交给对的部门、对的人。最初设想是「按任务类型找公司 → 找部门交给部门领导 → 领导分解并派给最合适的 Agent；没有合适公司则自己创造 Team/Agent」。

该设想作为**组织隐喻**是对的，作为**每条任务的串行 LLM 调度链**不合适：当前 workspace 基本是单公司；Plan 已经分解任务；再让部门主管分解一遍又慢又会和编排管家打架。同时现有程序已经能 Plan → Allocate → 建团，但**建团不挂部门**，组织树和部门主管在热路径上几乎用不上，于是既不够快（候选池过大、冷启动多），也不够准（部门主管会被选成业务 Lead）。

**目标**：在不推翻现有 Plan/Allocate/Orchestrate 的前提下，用组织树做确定性剪枝，用配方/使命做快速命中，把部门主管放在治理位而不是调度位，使「获取团队、组建团队」既快又准；跨团队时**少量结论进上下文、大量文件只传指针/落盘**，避免把上游仓库灌进下游模型窗口。

**重型长任务补充**：精灵只做粗路由，不是全行业拆解专家。每公司设总经理；公司内部门领导横向传话，公司间总经理传话；向上员工→部门领导→总经理→精灵。该链**只用于重型档**。调度靠预授权流程剧本并行开工，汇报走例外与阶段心跳，禁止每步上行。同类班底复用必须**新开 Team**，禁止复活已结束团队。

## 2. 用户故事

### US-78-01 同类任务秒级复用已有配方

**作为** 精灵用户
**我希望** 曾经成功做过的同类任务（同领域、同部门）再次出现时，系统直接复用已验证的 Agent/团队配方
**以便** 不必每次重新匹配、重新创建

**验收**：

- 同 `domain_path` 且历史 DQ ≥ 0.7 的配方命中时，Allocate 不再走 LLM 冷启动、不再走 Factory
- 用户可见匹配理由包含领域路径与「配方复用」
- 从用户发送到团队开始执行（高置信复用路径）明显快于冷启动路径（见 NFR-78-01）

### US-78-02 任务落到对的部门而不是全公司海选

**作为** 精灵用户
**我希望** 「做小红书运营方案」进运营/内容部门，「写后端接口」进研发部门
**以便** 不会把媒体部主管或无关岗位拉进团队当 Lead

**验收**：

- 部门主管（`agent_variant=dept_lead`）默认不作为业务任务的 AssignedKey / 团队 Lead
- 团队成员优先从命中部门的岗位 Agent 中选择
- 自动创建的 Team 必须带主归属 `department_id`（能从成员岗位推导时）
- 给定带明确领域信号的任务，主归属部门识别正确率 ≥ 90%（评测集见开发计划）

### US-78-03 跨部门时自动选择借调或多团队 DAG

**作为** 精灵用户
**我希望** 轻量跨部门（例如研发团队需要 1 名设计师）走借调，深度跨部门（设计稿 → 研发实现 → 测试）走多团队 DAG
**以便** 协作方式和真实公司一致，且不必我手工指定

**验收**：

- 单部门可覆盖 → 单 Team，成员均本部门
- 跨部门且耦合轻（辅角色 ≤ 成员 50%）→ 单 Team + 借调（沿用 M67 审批/超时自动通过）
- 跨部门且有先后交付依赖 → 每部门一 Team，PlanExecutor DAG 调度（沿用现有）
- 跨部门识别在明确输入下成功率 ≥ 95%（对齐 M67 US-04）

### US-78-04 部门主管把关，而不是每单都重新派工

**作为** 部门主管
**我希望** 只在缺人、借调、跨部门交付时被叫醒
**以便** 日常高置信匹配不额外耗时，质量仍有人把关

**验收**：

- L0/L1 高置信且成员均在本部门时，不调用部门主管 LLM 做任务分解
- 本部门无人达到匹配阈值时，可请主管从**已有专项**里指定一人（一次，超时 fail-closed，不创建 Agent）
- 跨部门交付仍走既有 VerificationGate / 主管审批（M67 US-05）
- 主管不被用来对用户原话再做一遍全局分解

### US-78-05 没有合适的人时才创建，且不创建公司

**作为** 系统管理员
**我希望** 任务找不到 Agent 时可以创建 Agent（需用户确认），但绝不会因为一次任务自动长出新公司或新部门
**以便** 组织编制保持稳定，Agent 库也不会无限膨胀

**验收**：

- 热路径无匹配 → **fail-closed**：请用户指定已有专项或去编制表补人；**不**自动 Factory / 不交差低分 Agent
- Factory 仅管理面或显式 `allowFactoryCreate` / `force_create`；新 Agent 仍必须挂已有岗位
- 每次编排仍可创建一次性 Team（ephemeral），不跨会话物理复用 Team 实体（沿用 B.10.21 不变量 6；同类任务走 US-78-10 配方回放）
- 任务路径禁止创建 `level=company` 或 `level=department` 节点
- 用户明确要求「成立新部门/新公司」时走组织管理（M67），不走 `plan_and_execute`

### US-78-10 同类任务召回配方团队，不复活旧 Team 行

**作为** 精灵用户
**我希望** 上次为某类任务组建过的班底，下次再说同类任务时直接按那套人开工
**以便** 不必再走一遍分解 LLM 和选人 LLM

**验收**：

- 同会话未结束（orchestrating/ready/interrupted）且目标未换 → 仍走已有 `reuse_existing`，禁止再开 DAG
- **新会话或 idle**：任务模式命中编排缓存（DQ≥0.7 且带 AgentKeys 或 Specialties）时，**配方回放**：跳过分解 LLM；有专题槽位则按槽位重建多 SubTask，否则合成单 SubTask；仍 `AssembleTeam` **新团队实例**并走 PlanExecutor
- 禁止跨会话把已 completed/failed 的 Team 行改回 running 再跑一轮（交付物、DAG 节点、成员会话、inbox 会互相污染）
- 用户明确「重新组建 / 换人 / force_new」时不走配方回放

### US-78-11 固定专项，LLM 只分专题

**作为** 精灵用户
**我希望** 系统用编制表上的专项做活，Planner 只决定「要哪些专题」，不要每次从一堆人里海选或现造一个人
**以便** 「小红书文案」永远落到文案专项，而不是随便一个沾边的人或新造的 Agent

**验收**：

- Planner 输出 `domain_path` 专题槽位，不输出人名 / agent_key（显式 `agent_keys` 除外）
- 有专题时 Allocate 走花名册绑定（`MatchLayer=roster`），不走 L3 选人、不走低分交差
- 评测：原话 → 专题 → 人；人必须在花名册上；dept_lead 不得为 Lead；Factory 调用次数 = 0

### US-78-12 多团队协作看得见，组队过程也看得见

**作为** 精灵用户
**我希望** 知道多支专项怎么交接、组队时专题绑到了谁，而不是猜「主管去哪了」
**以便** 主管不当 Lead 时，协作和选人仍然可解释

**验收**：

- 轻/中档：队与队之间用结论信封；对人汇总由精灵做；主管不拆用户原话
- 重型档：横向由部门领导传 Brief（跨公司由总经理传公司级 Brief）；上行走例外/阶段摘要；精灵仍对人说话并仲裁跨公司僵局
- 匹配进度显示「专题 → 人（层）」；缺专项显式提示补编
- 团队卡片在成员尚未到齐时也能看到专题与绑定专项

### US-78-13 按档选用组织链

**作为** 精灵用户
**我希望** 改一句文案不要惊动总经理，跨部门长任务才走编制汇报链
**以便** 轻活仍快，重活才有公司/部门协调

**验收**：

- 轻：闲聊/单步 → 精灵自答，不组队（与 US-78-06 一致）
- 中：单部门或单专题可闭环 → 花名册 + 部门领导门禁，不叫醒总经理
- 重：跨部门 DAG、跨公司、或复杂度判定为长任务 → 启用总经理与三管道
- 档位规则可测，默认不额外 LLM（设计文档 R9）

### US-78-14 公司总经理与预授权流程剧本

**作为** 公司总经理
**我希望** 对本公司「软件交付」这类标准流程一次授权，之后同类重型任务按剧本展开部门槽
**以便** 不必每个子任务再开总经理会，同时流程仍按本公司架构走

**验收**：

- 每家公司有且仅有一名 `company_lead`（对称 M67 `dept_lead`），不得被选为业务 Team Lead
- 剧本含阶段、部门、依赖、交付物名；精灵只选剧本 ID，不按行业常识拆到岗
- 已授权剧本命中：展开槽位 + 花名册绑人，总经理 LLM = 0
- 无剧本或新类型：总经理可补一次剧本并沉淀；禁止对用户原话做全局自由拆解
- 任务路径仍禁止创建公司/部门节点

### US-78-15 重型任务三管道流转

**作为** 部门领导 / 总经理
**我希望** 横向只传结论与附件清单，上行只传阻塞和阶段摘要，下行只传授权
**以便** 长任务不会被全文汇报拖死，也不会把源码灌进领导窗口

**验收**：

- 上行：例外即时；阶段心跳（每阶段或可配间隔）；禁止过程闲聊/源码上行
- 横向（公司内）：部门领导传递 Brief/Bulk，无 Brief 下游不开工
- 横向（跨公司）：总经理传递公司级 Brief（范围/接口/期限/机密级）；无 2+ 公司节点则通道休眠
- 下行：目标、约束、放行/驳回；不重写部门内部拆解
- 常规门禁超时自动通过并记审计；高风险必须人批（沿用 M67）
- 部门争议 → 本公司总经理；公司争议 → 精灵呈用户，禁止两边总经理循环互怼

### US-78-16 配方复用带约束指纹

**作为** 精灵用户
**我希望** 同类任务复用班底时，若期限/合规/剧本已经变了，不要照搬旧人硬干
**以便** 复用又快又不会做错活

**验收**：

- 配方记录 playbook_id（若有）与约束指纹；命中须指纹兼容
- 指纹不合：只复用专题槽或要求 `force_new`，不复用历史 keys
- 仍遵守 US-78-10：新 `AssembleTeam`，不复活终态 Team

### US-78-06 简单任务不组队

**作为** 精灵用户
**我希望** 闲聊、事实问答、单步操作由精灵直接回答
**以便** 不被错误组队拖慢

**验收**：

- 阻塞性歧义 → `mode=direct` 先澄清（沿用 DECISION.md）
- 简单任务不进入 Allocate/Assemble
- 会话非 idle 且同一目标 → 默认 `reuse_existing`，禁止再开一套 DAG

### US-78-07 跨团队只把结论带进下一棒（少量共享）

**作为** 下游团队成员
**我希望** 开工时只看到上游的结论：做了什么、关键发现、开放问题、要我接着做什么
**以便** 不必读完上游全部过程就能正确开工

**验收**：

- DAG 下游首轮输入必含上游 **结论信封**（摘要 + 要点 + 可选认知/契约名），体积有上限（见 NFR-78-09）
- 结论只认 `set_deliverable` 写出的结构化交付，不把团队闲聊 reply 当产出（沿用 B.10.22）
- 上游无真实结论 → 下游不得开工（fail-closed，沿用现有闸门）
- 用户在团队卡片上能看到这份结论，而不是一篇被截断的长文

### US-78-08 大量文件按清单交接，不灌进对话

**作为** 下游团队成员
**我希望** 上游的设计稿、数据集、代码目录以**文件清单 + 可打开的路径/制品**交给我，而不是整份贴进提示词
**以便** 需要时用文件工具按需读取，上下文不被撑爆

**验收**：

- 信封列出文件/制品（名称、大小、类型、校验），**正文不进 Turn 前缀**
- 下游工作区出现只读 inbox（或等价制品加载工具），仅含信封声明的条目，不能浏览上游 Agent 私人沙箱
- 主管抽查过程文件走 M71 memberfs（监管），不替代正式交接
- 二进制与超大文本不得走 `read_upstream_deliverable` 灌入模型（该工具只服务中等长度**文本**结论全文）

### US-78-09 文件耦合重时优先同团借调，结论交接走 DAG

**作为** 精灵用户
**我希望** 「一起改同一批源文件」的人进同一个 Team，「交一份报告再独立干活」才拆成上下游团队
**以便** 大量文件不必跨沙箱复制，少量结论仍能跨部门传递

**验收**：

- 协作主要是共享同一工作树/大量中间文件 → 倾向单 Team + 借调（US-78-03 轻量路径）
- 协作主要是「结论 → 下一部门开工」→ DAG + 结论信封 + 文件指针
- 判定规则可测、不额外 LLM（设计文档 R3/R7）

## 4. 交互规格（用户视角）

### 4.1 发出任务后用户看到什么

1. 简单任务：精灵直接回复，无组队卡片。
2. 复杂任务：编排进度仍为「分解中 → 匹配 i/N → 组队/创建确认 → 团队运行」（沿用 P-ORCH），匹配文案增加「归属：某某部门」。
3. 缺专项：提示指定已有专项或去编制表补人；管理面创建 Agent 仍走确认卡片，确认后出现在该部门岗位下。
4. 需要借调：用户侧不必操作（初期超时自动通过）；部门主管会话可看到借调请求。
5. 无阻塞性信息：先问清楚再组队。
6. 跨团队：卡片展示「结论」短文 + 「附件清单」；点开附件走制品/文件，不在聊天里展开整份仓库。
7. 重型档：可见「按本公司剧本展开 / 总经理已预授权」；阶段心跳与例外出现在组织汇报区，不把员工过程贴进用户主对话。

### 4.2 用户不需要做的

- 不需要先选公司再下指令（当前单公司 workspace）。
- 不需要指定部门主管。
- 不需要为一次性任务「成立新公司」。

## 6. 约束与边界

| 约束 | 说明 |
|------|------|
| 不替换 PlanExecutor | 生产建团唯一路径仍是 `PlanExecutor` + `RealTeamOrchestrator` |
| 不替换 B.10.21 匹配层 | L0/L1 保留；有专题时以花名册绑定替代 L3 选人 |
| 单公司默认 | 「找最合适的公司」= 当前 workspace 的公司树；多公司是租户切换，不是每任务检索 |
| 部门主管是守门人 | 不做具体业务执行（与 M67 概念模型一致）；重型横向传 Brief，不传全文 |
| 总经理是授权与对外口 | 预授权剧本、跨部门冲突、跨公司 Brief；不当 Team Lead、不拆用户原话 |
| 层级是例外通道 | 重型链不是每条消息的必经水管；轻/中不得启用完整上行 |
| 创造分层 | Agent（确认后）/ 一次性 Team（允许）/ 配方缓存（允许）/ 公司与部门（禁止由任务创建） |
| 澄清优先 | 信息不足禁止组队（DECISION.md） |
| 传递与监管分离 | 跨团队「交给下一棒的东西」只走结论信封 + 声明的文件指针；memberfs / sessionaccess 只做主管/精灵监管（M71） |
| 结论只认 set_deliverable | reply 聊天文本不是跨团队产出（B.10.22） |

# Self-Iteration V3 — 平台自改进（Meta 级自我迭代）需求文档

本文档描述 Aranea-Agents **自我迭代 V3（平台自改进）** 的功能需求。V3 将平台自身全量代码（Go 后端 + 前端 + 配置 + Prompt）作为进化对象，由平台内运行的 Meta Team 完成「观察 → 归因 → 修补 → 验证 → 治理 → 应用 → 学习」七环自闭环，实现从「修复→学习→预防」（V2）到「平台改自己」（V3）的跨越。

> 设计文档：[73-self-iteration-v3.design.md](./73-self-iteration-v3.design.md)
> 开发计划：[73-self-iteration-v3.development.md](./73-self-iteration-v3.development.md)
> 前置模块：[60-self-iteration-v2.md](./60-self-iteration-v2.md)（已落地）

---

## 0. 背景与动机

### 0.1 能力愿景

V2 已建立「修复→学习→预防」闭环：CI Auto-Fix、FailurePattern 知识库、Skill 五阶段进化、预测性自愈。但 V2 的修改对象限于 Skill 的 SKILL.md 与 CI 流水线，执行场所依赖外部 CI（GitHub Actions）。V3 的愿景是：

| 能力域 | 愿景 |
|--------|------|
| 运行时信号感知 | 平台从自身 trace/metrics/日志/评估数据中自动发现改进机会，无需人工上报 |
| 自动归因诊断 | Meta Team 读取结构化错误与源码，输出根因与影响面分析 |
| 自主补丁生成 | 在 git worktree 隔离副本上生成 unified diff 补丁，保护文件清单兜底 |
| 沙盒分级验证 | 编译 → 单测 → Lint → Critic 语义审查 → Eval 基线，五级 Gate 全过才可应用 |
| 风险分级治理 | 低风险自动应用、中风险自动应用+通知、高风险人工审批，全部可回滚 |
| 应用与观察窗 | 配置类热加载、代码类合并后重启生效；应用后进入 24h 观察窗，指标退化自动回滚 |
| 成效学习 | 补丁成败归因写入知识库，反哺感知与生成环节，越修越准 |

### 0.2 与 V2 的关系

| | V2（60-self-iteration-v2，已落地） | V3（本模块） |
|---|---|---|
| 修改对象 | Skill 的 SKILL.md、CI 流水线 | 平台自身全量代码（Go + 前端 + 配置 + Prompt） |
| 执行场所 | 外部 CI（GitHub Actions）+ 后台 worker | 平台内 Meta Team（trpc-agent-go 运行时，聊天可视） |
| 闭环 | 修复→学习→预防 | 观察→归因→修补→验证→治理→应用→学习 |
| 复用关系 | — | 复用 V2 的 FailureReport、FailurePattern KB、Critic、RootCauseAnalyzer、SkillEvolutionOrchestrator、审批体系 |

V3 不修改 V2 已有业务逻辑，仅在其基础设施上扩展。

### 0.3 非目标

- 不做运行中二进制热替换（Go 无法安全热更；代码类补丁合并后于下次重启生效，蓝绿/滚动重启为远期愿景）
- 不修改 trpc-agent-go 框架层
- 不允许补丁修改保护文件清单（CI 工作流、go.mod/sum、proto 已有消息、DDL 迁移历史、wire_gen.go 仅可 regenerate）
- 不做无人值守的全自动高风险变更（高风险必须人工审批）
- 不改变已有 Evolution L1-L3（Skill/Agent 配置进化）业务逻辑
- P1-P4 阶段不做专用前端（复用聊天内审批 activity 与现有进化建议页）

## 1. 运行时信号感知（Observe）

### 1.1 需求描述

平台从自身运行数据中自动发现改进机会，生成自改进建议。复用统一进化编排器（SkillEvolutionOrchestrator），新增 `target_type=platform` 的四类触发器：运行时错误聚类、性能瓶颈、评估退化、测试失败。触发信号来源于已有的监控/追踪/用量/评估子系统与 FailurePattern 知识库，无需人工上报。

### 1.2 验收标准

| ID | 验收标准 |
|----|----------|
| OB-01 | 系统周期性扫描运行时错误，相同 error_code + 相似堆栈的错误聚类达到阈值（默认 7 天内 ≥5 次）时生成 `patch_code` 建议 |
| OB-02 | 系统检测调用链慢点（如某步骤 P95 耗时超过基线 2 倍）或 token 消耗异常（超基线 50%）时生成 `patch_code` 或 `tune_config` 建议 |
| OB-03 | 评估基准分数较上一基线退化超过阈值（默认 10%）时生成 `patch_code` 或 `patch_prompt` 建议 |
| OB-04 | 全量测试出现持续失败（同一测试连续 2 轮扫描失败）时生成 `patch_code` 建议 |
| OB-05 | 所有建议写入统一进化建议存储，target_type=platform，含触发源、触发原因、优先级、关联证据（trace/日志/指标快照） |
| OB-06 | 同一目标已有 pending 建议时不重复生成（复用编排器去重与冷却机制） |
| OB-07 | 用户可在管理界面查看建议列表及其证据快照 |

### 1.3 优先级

P0（阶段一）

## 2. 自动归因诊断（Diagnose）

### 2.1 需求描述

Meta Team 的 Analyst Agent 接收自改进建议后，读取结构化错误（FailureReport）、相关 trace、指标快照与目标源码，输出结构化诊断结论：根因、影响面、建议修改的文件清单与修改思路。诊断结论以结构化 JSON 传递，供后续环节消费。

### 2.2 验收标准

| ID | 验收标准 |
|----|----------|
| DG-01 | 诊断输出包含：root_cause、affected_files（路径清单）、impact_scope（局部/模块/全局）、fix_strategy、confidence（0-1） |
| DG-02 | Analyst 可读取平台自身源码（只读工具），引用具体文件与行号作为证据 |
| DG-03 | confidence 低于阈值（默认 0.5）时，建议降级为「仅记录」，不进入补丁环节 |
| DG-04 | 诊断过程与结论持久化，可在建议详情中查看完整推理链 |

### 2.3 优先级

P1（阶段三）

---

## 3. 自主补丁生成（Patch）

### 3.1 需求描述

Meta Team 的 Patcher Agent 在 git worktree 隔离副本（分支 `self-improve/<run_id>`）上根据诊断结论生成补丁，产出标准 unified diff。补丁对象覆盖平台全量代码：Go 后端、前端、配置、Prompt。保护文件清单内的文件禁止修改，命中即拒绝并记录。

### 3.2 验收标准

| ID | 验收标准 |
|----|----------|
| PT-01 | 补丁生成分支为 `self-improve/<run_id>`，基于当前主分支的 worktree 隔离副本，生产工作树不被直接修改 |
| PT-02 | 补丁产出为标准 unified diff，可被 `git apply` 幂等应用 |
| PT-03 | 保护文件清单：`.github/workflows/`、`Makefile`、`go.mod/go.sum`、proto 已有消息定义、DDL 迁移历史文件、`cmd/admin/wire_gen.go`（仅允许 regenerate 流程）；命中即拒绝并记录保护事件 |
| PT-04 | 单次补丁 diff 行数超过上限（默认 500 行）时拆分为多个补丁或拒绝并记录原因 |
| PT-05 | 补丁元数据包含：目标文件清单、新增/删除行数、关联诊断 ID、生成模型与 token 消耗 |
| PT-06 | Prompt/配置类补丁与代码类补丁在元数据中明确区分（决定后续应用方式） |

### 3.3 优先级

P1（阶段二）

---

## 4. 沙盒分级验证（Verify）

### 4.1 需求描述

Meta Team 的 Verifier Agent 在沙盒 worktree 中对补丁执行五级 Gate 验证：G1 编译、G2 受影响包单测、G3 Lint、G4 Critic 语义回归审查、G5 Eval 基线回归（可选）。任一 Gate 失败则补丁被拒绝，失败证据回传 Patcher 修正重试（有次数上限），全部通过才进入治理环节。

### 4.2 验收标准

| ID | 验收标准 |
|----|----------|
| VF-01 | G1：补丁应用后 `go build ./...` 与前端 `pnpm build` 通过 |
| VF-02 | G2：受影响包的 `go test` 与前端 `pnpm test` 通过；受影响包由 diff 文件清单推导 |
| VF-03 | G3：`make lint` 与 `pnpm lint` 通过 |
| VF-04 | G4：Critic Agent 输出结构化审查（is_safe / risk_level / concerns / suggestion）；risk_level=high 时拒绝 |
| VF-05 | G5（可选，默认关闭）：Eval 基准集回归分数不退化（退化 >10% 拒绝） |
| VF-06 | 每级 Gate 的通过/失败与原始证据（命令输出、Critic 结论）持久化为验证报告 |
| VF-07 | 验证失败可回传 Patcher 修正重试，重试上限默认 3 次，超限标记 verify_failed |
| VF-08 | 沙盒验证过程不访问生产数据库与生产外部服务（mock/替身隔离） |

### 4.3 优先级

P1（阶段二 G1-G3；阶段三 G4；阶段四 G5）

---

## 5. 风险分级治理（Govern）

### 5.1 需求描述

治理组件（纯代码，不走 LLM）对验证通过的补丁进行风险分级，并路由到对应的应用通道：低风险自动应用、中风险自动应用+事后通知、高风险人工审批。分级规则基于补丁对象类型、影响文件数、是否命中核心路径、diff 规模。所有应用动作留有回滚指针。

### 5.2 验收标准

| ID | 验收标准 |
|----|----------|
| GV-01 | 低风险（配置项、Prompt、文案、测试代码、文档，单文件，diff ≤100 行）：验证通过即自动应用 |
| GV-02 | 中风险（单文件业务代码、非核心路径，diff ≤300 行）：自动应用并向管理员发送事后通知（含 diff 与验证报告链接） |
| GV-03 | 高风险（多文件、核心路径 chat/agent/data schema、proto 新增、任何 diff >300 行）：必须人工审批后才可应用 |
| GV-04 | 人工审批复用统一审批通道（聊天审批 activity + 管理界面），审批记录含审批人、时间、理由 |
| GV-05 | 风险分级规则可配置（阈值表），分级决策过程与命中规则持久化 |
| GV-06 | 每日自动应用次数超过配额（默认 5 次）时，后续补丁一律转人工审批 |

### 5.3 优先级

P1（阶段三）

---

## 6. 应用与观察窗回滚（Apply）

### 6.1 需求描述

治理放行的补丁由 Applier 应用：配置/Prompt 类热加载生效；代码类合并到主分支，下次重启生效。应用后进入观察窗（默认 24h），系统持续监控关键指标（错误率、P95 延迟、告警数），指标退化超阈值时自动执行回滚（git revert + 热加载回退），并通知管理员。

### 6.2 验收标准

| ID | 验收标准 |
|----|----------|
| AP-01 | 配置/Prompt 类补丁应用后通过既有热加载通道生效，无需重启 |
| AP-02 | 代码类补丁应用为 git 提交（含 `self-improvement: true` 标记与 run 关联），合并到主分支，运行时于下次重启生效 |
| AP-03 | 每次应用记录回滚指针（revert 目标 commit / 热加载回退快照） |
| AP-04 | 观察窗内错误率上升 >50% 或 P95 延迟上升 >30%（可配置）时自动回滚 |
| AP-05 | 自动回滚执行后通知管理员，含回滚原因与指标快照 |
| AP-06 | 管理员可在观察窗内手动提前关闭观察（确认有效）或手动触发回滚 |
| AP-07 | 应用与回滚动作全量记录审计日志（谁、何时、什么补丁、结果） |

### 6.3 优先级

P1（阶段四）

---

## 7. 成效学习（Learn）

### 7.1 需求描述

每次自改进闭环的结果（验证结论、应用结果、观察窗指标、回滚原因）沉淀为成效记录，并反哺知识库：有效补丁的模式提升后续生成质量，失败/回滚补丁的模式进入负面样本，触发器阈值随历史准确率动态调整。

### 7.2 验收标准

| ID | 验收标准 |
|----|----------|
| LN-01 | 每次闭环结束（closed / rolled_back / verify_failed）生成成效记录，含 verdict：effective / neutral / regressed |
| LN-02 | 回滚或验证失败的补丁模式写入 FailurePattern 知识库（source=self_improvement，负面标记） |
| LN-03 | 连续 3 次同类触发源建议被判定 neutral/regressed 时，该触发器自动降频或提升触发阈值 |
| LN-04 | 成效统计可在管理界面查看（闭环总数、有效率、回滚率、按触发源分布） |

### 7.3 优先级

P2（阶段四）

---

## 8. Meta Team 协同与过程可视

### 8.1 需求描述

自改进闭环由平台内 Meta Team 执行：Observer（信号汇总）、Analyst（归因）、Patcher（补丁）、Verifier（验证）、Critic（语义审查）五个职能 Agent 协同，Governor 为纯代码治理组件。闭环过程作为特殊会话在聊天界面可视：每个环节的活动（诊断、补丁、验证、审批）按事件树展示，用户可随时介入（暂停、审批、回滚）。

### 8.2 验收标准

| ID | 验收标准 |
|----|----------|
| MT-01 | Meta Team 以平台既有 Team 编排能力运行，成员身份、职责、协作协议有显式定义（Agent Identity） |
| MT-02 | 闭环各环节活动在聊天界面按父子事件树展示（诊断→补丁→验证→审批→应用），顺序正确 |
| MT-03 | 高风险审批以聊天内审批 activity 呈现，含 diff 摘要与验证报告摘要 |
| MT-04 | 用户可在会话中发送指令暂停闭环、跳过重试、强制回滚 |
| MT-05 | 预规划门控等系统内部通知不在用户界面显示（遵循既有通知规范） |

### 8.3 优先级

P1（阶段三）

## 9. 自改进控制台（前端）

### 9.1 需求描述

提供自改进管理控制台：闭环运行列表（状态、风险等级、触发源）、运行详情（诊断/补丁 diff/验证报告/审批记录）、成效统计面板（有效率、回滚率、触发源分布）、风险分级规则配置。

### 9.2 验收标准

| ID | 验收标准 |
|----|----------|
| UI-01 | 运行列表支持按状态/风险等级/触发源筛选，按时间倒序 |
| UI-02 | 运行详情页展示完整事件时间线、unified diff 渲染、验证报告五级 Gate 结果 |
| UI-03 | 高风险运行可在详情页直接审批（通过/拒绝+理由） |
| UI-04 | 成效面板展示闭环总数、有效率、回滚率、按触发源分布图表 |
| UI-05 | 全部展示文案走 i18n（zh-CN / en-US） |

### 9.3 优先级

P2（阶段五）

## 10. 实施路线图

### 阶段一（P1）：感知接入

**目标**：数据模型 + 四类触发器 + 编排器接入，信号→建议链路打通

| 需求 | 优先级 |
|------|--------|
| 运行时信号感知（OB-01~OB-06） | P0 |

**阶段验收**：`go build ./...` + `go test ./internal/biz/... ./internal/data/...` 全绿

### 阶段二（P2）：沙盒与补丁

**目标**：git worktree 沙盒 + Patcher 工具集 + G1-G3 验证

| 需求 | 优先级 |
|------|--------|
| 自主补丁生成（PT-01~PT-06） | P1 |
| 沙盒分级验证 G1-G3（VF-01~VF-03、VF-06~VF-08） | P1 |

**阶段验收**：沙盒内对测试补丁跑通 build/test/lint

### 阶段三（P3）：Meta Team 与治理

**目标**：Meta Team 编排 + Critic G4 + 风险分级审批 + 聊天可视

| 需求 | 优先级 |
|------|--------|
| 自动归因诊断（DG-01~DG-04） | P1 |
| 沙盒分级验证 G4（VF-04、VF-07） | P1 |
| 风险分级治理（GV-01~GV-06） | P1 |
| Meta Team 协同与过程可视（MT-01~MT-05） | P1 |

**阶段验收**：端到端「信号→审批单」可运行

### 阶段四（P4）：应用与学习

**目标**：Applier + 观察窗自动回滚 + 成效学习

| 需求 | 优先级 |
|------|--------|
| 应用与观察窗回滚（AP-01~AP-07） | P1 |
| 成效学习（LN-01~LN-04） | P2 |
| 沙盒分级验证 G5（VF-05，可选） | P2 |

**阶段验收**：端到端「应用→观察→回滚」可运行

### 阶段五（P5）：控制台与竞赛材料

**目标**：前端控制台 + 竞赛四件套补齐

| 需求 | 优先级 |
|------|--------|
| 自改进控制台（UI-01~UI-05） | P2 |

**阶段验收**：`pnpm lint && pnpm test && pnpm build` + 竞赛材料更新

## 11. 非功能需求

- **可回滚性**：所有自动应用必须留有 git revert 指针或热加载回退快照；观察窗内支持一键回滚
- **安全性**：保护文件清单不可改；沙盒验证隔离生产数据与外部服务；高风险必须人工审批；补丁不含敏感信息（API key/password/token）检测
- **成本控制**：Critic 每日上限 10 次（复用 V2 配额）；Patcher 每日上限 20 次；每日自动应用配额默认 5 次
- **可审计性**：诊断、补丁、验证、审批、应用、回滚全链路持久化；审计日志不可篡改
- **性能**：感知扫描对生产性能影响可忽略（只读查询 + 限流）；沙盒验证在独立 worktree/目录执行，不阻塞主服务
- **测试隔离**：集成测试使用 build tag `integration` 与独立 PG schema 隔离
- **兼容性**：所有变更为增量（新增表/接口/触发器/worker），不修改 V2 与 Evolution L1-L3 已有业务逻辑

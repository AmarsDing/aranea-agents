 memory: 想法：做一个内置的agent专注于管理记忆，独立进程随系统一起启动，功能：实时监控历史对话，异步压缩与存储，管理memoryL0-L4层记忆，形成一个统一的神经记忆系统。神经记忆系统的理解：每个memory块语意完整，相互关联，当某个记忆块改动，自动复盘相关联记忆块是否需要更新，例如：一个人，住在北京工作，其相关的时间，地点，交通，天气等的记忆都与这个地点相关联，此时这个人来到了纽约工作，那时间，地点，交通，天气等等的与之相关联的记忆会跟随工作地点的变动而发生更动。为解决上述问题，想通过后台agent对用户的聊天信息进行深度的整合，不会发生因为工作地点变动，导致AI还是回复错误的交通方式和路径。

1.2 图数据库选型
你明确“马上就需要图数据库”，考虑到项目初期用 SQLite 的便利性和部署简单，我建议采用 嵌入式图引擎 + SQLite 持久化 的混合方案，避免引入重度外部服务：

运行时：在 Memory-Agent 内部维护一个 内存图结构（用 Go 的图库，如 dominikbraun/graph 或自己轻量实现），支撑 L4 的依赖遍历、子图查询，毫秒级响应。

持久化：图的节点和边序列化为 JSON 存入 SQLite 的表 graph_nodes 和 graph_edges，定期全量/增量刷盘。重启时从 SQLite 重构图。

未来可平滑迁移：如果数据量膨胀，可以切换到 RedisGraph 或 Dgraph（均支持图查询语法），接口抽象在 M6 的存储层，改动小。

这样既满足了“马上需要图数据库”的即时性（内存图就是图数据库），又保持了轻量和可控。

它是一个基于 trpc-agent-go 的 系统 Agent，通过 goroutine 运行，使用 Runner 驱动内部循环，但不暴露给用户对话。

实体解析与冲突检测：在图里查找已有实体，判断新事实是新增、更新还是冲突（用 LLM 或规则+LLM）。若更新，旧事实标记为历史版本，新事实写入。

写时级联（关键）：更新操作触发 get_dependents(node_id) 查询图，找到所有依赖于被修改实体的 L3 记忆（例如依赖于“工作地点”的“通勤方式”）。为每条受影响记忆生成一个复盘任务，放入优先级队列。

异步复盘工作者：另一个 goroutine 消费队列，对每条任务调用 reconcile_memories，由 LLM 根据新事实重新评估记忆有效性，并输出修正版本。修正后再次写入，可能引发更远端的修正，但限制递归深度（如 3 层）。

L3 记忆刷新：复盘后更新的记忆写入向量索引（M6 知识库），保证检索时拿到的永远是最新、一致的信息。

1.4 与其他模块的交互
M5 Session：当 Memory-Agent 更新了当前用户的 L2/L3 记忆后，可以推送一个 memory.updated 事件，Session 管理器据此刷新注入给 LLM 的上下文（如把最新的用户画像片段追加到 system prompt 或 messages 中）。

Tool 暴露：将 retrieve_memories(query) 封装为 Tool，供其他 Agent 在需要时主动召回记忆。

A2A：当 Agent 通过 A2A 协议协作时，Memory-Agent 可作为记忆提供端，输出当前用户的一致视图。




Skill-Agent（技能管家）
1.1 定位
Skill-Agent 是后台运行的技能生命周期管理 Agent（goroutine），维护系统技能池的质量、精简度和适配性。核心目标：确保 Agent 始终调用到最合适的技能，并根据使用反馈持续优化、进化乃至自生成新技能。

1.2 技能去重与合并机制
1.2.1 检测机制

语义相似度分析：对技能池中所有技能的 description、instruction、tool 组合进行 embedding 后计算余弦相似度。超过阈值（建议默认 0.85，可配置）的技能对标记为候选合并项。

功能等价检测：对候选技能对，LLM 分析其输入输出 Schema、适用场景是否实质等价。

触发方式：

定时扫描（默认每 N 小时，可配置）

新技能注册时触发增量检测

技能数量变化超过阈值（10%）时触发全量扫描

1.2.2 合并策略（系统配置项）

在系统配置中增加 skill_evolution_mode 配置项：

模式	值	行为
自动模式	auto	检测到可合并技能对后自动执行合并，被合并技能标记为 deprecated 并重定向到合并后的技能。合并后的技能保留两者参数的超集
人工确认模式	manual	检测到可合并技能对后，向前端推送通知（skill.merge_candidate 事件），附带合并建议详情（相似度、合并理由、合并后技能定义预览）。人工可选择：① 合并为一个 ② 保留两者 ③ 忽略
两种模式均记录审计日志，包括：

检测时间、相似度分数、候选技能 ID

决策方式（自动/人工）、决策结果（合并/保留/忽略）

操作人（自动标记为 system，人工标记为操作用户 ID）

合并前后技能定义快照

1.2.3 同类技能管理——SkillSet

将语义相近但不完全等价的技能分组为 SkillSet（技能簇）。

SkillSet 定义统一的入口 Router Skill，运行时根据任务上下文（意图、复杂度、用户偏好）自动分发到簇内最合适的子技能。

SkillSet 定期重新聚类，确保分组随技能池演化保持合理。

二、Manage-Agent（总管）
2.1 定位
Manage-Agent 是任务级协调器，不执行具体原子操作。核心目标：准确理解用户意图、规划最优执行路径、动态组建最佳 Agent 团队。

2.2 意图理解与澄清
2.2.1 核心流程

初步解析：接收用户输入，结合 Memory-Agent 提供的用户画像和历史上下文，识别可能的意图方向。

歧义检测：评估当前输入的歧义程度——如存在多种可能的意图解释、关键参数缺失、约束不明确等情况，则进入澄清流程。

澄清决策：参考 MAC（Multi-Agent Clarification）框架的策略——由 Manage-Agent 自主判断“何时打断用户”以及“如何构造最优澄清问题”，目标是前置性一次获取所有必要信息，减少平均对话轮次。

澄清输出：生成精准的澄清问题，向用户确认理解或请求缺失信息。澄清问题设计遵循：

区分性：问题应能有效区分候选意图

前置批量：一次提问尽可能覆盖所有缺失槽位，避免多轮反复

上下文感知：利用 Memory-Agent 和历史对话减少不必要的提问

意图确认（Intent Preview） ：对于复杂或高风险任务，在执行前向用户展示理解摘要和执行计划预览，获得确认后再启动。

2.2.2 澄清策略配置项

2.4.2 组建策略

遍历任务 DAG，对每个子任务匹配可执行的 Agent（查询 Agent 注册表，匹配能力标签）。

根据子任务间的依赖关系，决定 Agent 的组织形式：

顺序依赖 → ChainAgent

无依赖并行 → ParallelAgent

复杂分支/条件 → GraphAgent

迭代收敛 → CycleAgent

对于无合适 Agent 的子任务，向 Skill-Agent 请求生成新技能或向 Tools-Agent 查询可用工具后创建临时 LLMAgent。

组建结果：一个 Team（trpc-agent-go Team 概念），包含选定的 Agent 集合及其协调策略。

组建完成后，为 Team 指定模型（使用各 Agent 配置中已预设的模型，无需额外选择）【用户确认】。

将 Team 提交 Runner 执行，同时监听执行事件。

无法完成时 → 向用户报告进度并请求指引

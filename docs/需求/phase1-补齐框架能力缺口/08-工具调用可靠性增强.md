# 工具调用可靠性增强

## 一、需求文档

### 1.1 背景

工具调用是 Agent 运行时的核心能力，其可靠性直接决定 Agent 任务的完成率。当前项目在工具调用方面已具备 RetryPolicy（自动重试瞬态错误）、ToolFilter（工具可见性控制）、Guardrail（Approval/PromptInjection/UnsafeIntent 安全护栏）、SensitiveDataMaskPlugin（输出脱敏）等机制，但在以下维度仍存在缺口：

1. **故障隔离不足**：单个工具的持续失败（如外部 API 不可用）会反复消耗 LLM 调用次数和重试预算，缺乏断路器（Circuit Breaker）机制进行故障隔离和优雅降级。arXiv:2505.02097 指出，在多工具 Agent 系统中，未隔离的级联故障是导致任务失败的首要原因。
2. **工具声明 Token 浪费**：所有工具声明在每次 LLM 请求中全量注入，当工具数量超过 30 个时，工具声明消耗的 Token 占比可达 40% 以上。arXiv:2504.00914 实证研究表明，工具集扩大 15-30 个时 LLM 工具选择准确率下降 15-30%。Claude Code 的 Tool Search Tool 方案将 Opus 4 的工具选择准确率从 49% 提升至 74%。
3. **工具选择歧义**：语义相似的工具（如 `web_research` vs `duckduckgo_search` vs `google_search`）导致 LLM 选择困惑。当前 `RuntimeToolNameAliases` 仅解决别名映射，不解决语义消歧。arXiv:2507.03336 提出的 ToolUseExample 机制可显著降低选择歧义。
4. **输入侧安全防护缺失**：项目已有 SensitiveDataMaskPlugin 处理输出脱敏，但缺乏对工具输入参数中敏感路径访问的拦截（如 `.aws/credentials`、`.ssh/`）。OpenClaw 的 CommandPolicy 在此方面有成熟实践。

### 1.2 目标

- 为每个工具提供断路器保护，在持续失败时自动熔断并优雅降级
- 实现工具延迟加载（Deferred Loading），减少工具声明 Token 消耗，提升工具选择准确率
- 增强工具选择消歧能力，减少语义相似工具的误选率
- 补齐输入侧敏感路径防护，作为 Guardrail Plugin 体系的扩展

### 1.5 验收标准

1. 配置断路器后，工具连续失败达到阈值时自动熔断，LLM 收到 `CircuitOpenError` + 不可用工具列表
2. 熔断恢复期（HalfOpen）探测调用成功后断路器恢复 Closed 状态
3. 标记为 Deferred 的工具不出现在 LLM 初始工具声明中，LLM 通过 `tool_search` 按需发现
4. `tool_search` 返回的工具在后续请求中自动激活，同 Session 内缓存
5. 配置 ToolUseExample 后，语义相似工具的选择准确率提升（对比无示例基线）
6. Assemble 阶段检测到同组干扰项时，system prompt 包含消歧指导
7. SensitivePathPolicy 拦截对 `.aws/credentials` 等敏感路径的访问，返回拒绝消息
8. 所有拦截事件在 FlowLog 中有记录
9. 未启用任何增强功能时，现有行为完全不变

## 二、设计文档

### 2.1 框架参考

#### Circuit Breaker 模式

**学术参考**：arXiv:2505.02097（Reliability Frameworks for LLM Agent Systems）

**行业参考**：agentpatterns.ai（Circuit Breaker Pattern）、AWS Resilience Hub

**核心模型**：

```
    ┌─────────┐  failure ≥ threshold  ┌──────┐
    │ Closed  │ ──────────────────────→│ Open │
    │ (normal)│                        │(block)│
    └─────────┘                        └──────┘
         ↑                                │
         │  probe success                 │ timeout expires
         │                                ↓
         │                          ┌──────────┐
         └──────────────────────────│ HalfOpen │
              probe fail → Open     │ (probe)  │
                                    └──────────┘
```

**与框架 RetryPolicy 的关系**：RetryPolicy 处理瞬态错误（网络超时、EOF），Circuit Breaker 处理持续性故障（服务不可用、认证过期）。两者互补：Retry 先尝试恢复，Circuit Breaker 在恢复无望时熔断。

#### Tool Search Tool 模式

**参考**：Claude Code Tool Search Tool（Anthropic，2025）

**核心思路**：当工具数量超过阈值时，仅向 LLM 暴露高频核心工具 + 一个 `tool_search` 元工具。LLM 需要特定能力时先调用 `tool_search`，按需激活。

**实证数据**：Claude Code 测量 Opus 4 在 49%→74% 准确率提升；arXiv:2504.00914 测量工具集从 10 扩展到 40 时准确率下降 15-30%。

#### Tool Disambiguation 模式

**学术参考**：arXiv:2507.03336（Tool Selection via Examples）、arXiv:2504.00914（Tool Set Expansion Effects）

**核心思路**：为每个工具提供 `ToolUseExample`（用户查询示例 + 正确工具选择 + 参数示例 + 解释），在工具声明中注入使用示例，降低 LLM 对语义相似工具的选择歧义。

#### Command Safety Policy 模式

**参考**：OpenClaw CommandPolicy

**与现有机制的关系**：项目已有 SensitiveDataMaskPlugin（输出脱敏）、Guardrail Plugin（Approval/PromptInjection/UnsafeIntent）。Command Safety Policy 是**输入侧**防护，作为 Guardrail Plugin 体系的扩展（ToolGuardrail），而非独立系统。

### 2.4 接口设计

#### 2.4.1 Circuit Breaker

```go
// internal/biz/tool/circuit_breaker.go

type CircuitState string

const (
    CircuitClosed   CircuitState = "closed"
    CircuitOpen     CircuitState = "open"
    CircuitHalfOpen CircuitState = "half_open"
)

type CircuitBreakerConfig struct {
    FailureThreshold  int `json:"failure_threshold"`
    RecoveryTimeoutSec int `json:"recovery_timeout_sec"`
    HalfOpenMaxProbe  int `json:"half_open_max_probe"`
}

// CircuitBreakerOption configures a CircuitBreaker at construction time.
type CircuitBreakerOption func(*CircuitBreaker)

// WithOnStateChange sets a callback invoked on every state transition.
// The callback receives (name, fromState, toState) and is called
// inside the breaker's mutex — must not block or call back into the breaker.
func WithOnStateChange(fn func(name string, from, to CircuitState)) CircuitBreakerOption

type CircuitBreaker struct {
    mu              sync.Mutex
    name            string
    state           CircuitState
    failures        int
    successes       int
    lastFailureTime time.Time
    config          CircuitBreakerConfig
    onStateChange   func(name string, from, to CircuitState)
}

func NewCircuitBreaker(name string, cfg CircuitBreakerConfig, opts ...CircuitBreakerOption) *CircuitBreaker

// Allow reports whether a call is permitted.
// Return type (bool, CircuitState) is more practical than the design doc's
// (bool, error) — callers need the current state for logging/metrics, not
// an error they'd immediately discard. (TIP-1)
//
// Allow is a query-with-side-effect: it may transition Open→HalfOpen when
// the recovery timeout expires. (RC-2)
func (cb *CircuitBreaker) Allow() (bool, CircuitState)

// RecordSuccess records a successful call.
// In Closed state, RecordSuccess resets lastFailureTime for semantic clarity —
// consecutive successes should not carry stale failure timestamps. (SUG-2, TIP-3)
// In HalfOpen state, a successful probe transitions the breaker to Closed.
func (cb *CircuitBreaker) RecordSuccess()

// RecordFailure records a failed call (non-transient).
// Consecutive-failure semantics: failures are counted as a running total
// within the current state; Reset() zeroes the counter. A single success
// in HalfOpen resets the counter via transition to Closed. (SUG-2)
func (cb *CircuitBreaker) RecordFailure()
func (cb *CircuitBreaker) State() CircuitState
func (cb *CircuitBreaker) Reset()

// Name returns the breaker's tool name.
// Lock-free: string is immutable after construction. (RC-1)
func (cb *CircuitBreaker) Name() string
func (cb *CircuitBreaker) UpdateConfig(cfg CircuitBreakerConfig)

// IsTransientError reports whether an error is transient (network/timeout/cancel)
// and should NOT count toward circuit breaker failure threshold.
// Transient errors: io.EOF, io.ErrUnexpectedEOF, net.Error, context.Canceled,
// context.DeadlineExceeded.
func IsTransientError(err error) bool

// CircuitBreakerRegistry manages per-tool circuit breakers.
// Scope: Session-level — each Runner/Session creates its own registry instance.
// Breaker state does NOT persist across sessions or survive restarts.
// Optional/nil semantics: CircuitBreakerRegistry may be nil in TRPCBuilderDeps
// when circuit breaker is disabled; callers must nil-check. (RC-8)
type CircuitBreakerRegistry struct {
    mu             sync.RWMutex              // RWMutex: fast-path RLock for reads
    breakers       map[string]*CircuitBreaker
    defaults       map[string]CircuitBreakerConfig // category → default config
    overrides      map[string]CircuitBreakerConfig // tool_name → override config
    onStateChange  func(name string, from, to CircuitState)
}

func NewCircuitBreakerRegistry(opts ...CircuitBreakerRegistryOption) *CircuitBreakerRegistry

// CircuitBreakerRegistryOption configures a CircuitBreakerRegistry at construction time.
type CircuitBreakerRegistryOption func(*CircuitBreakerRegistry)

// WithRegistryOnStateChange propagates an onStateChange callback to all
// breakers created by this registry. (F1.6)
func WithRegistryOnStateChange(fn func(name string, from, to CircuitState)) CircuitBreakerRegistryOption

func (r *CircuitBreakerRegistry) Get(toolName, category string) *CircuitBreaker
func (r *CircuitBreakerRegistry) SetOverride(toolName string, cfg CircuitBreakerConfig)
func (r *CircuitBreakerRegistry) ResetAll()
func (r *CircuitBreakerRegistry) ResetTool(toolName string)

// OpenBreakers returns names of breakers currently in Open state.
// Nested lock optimization: collects breaker references under RLock, releases
// lock, then checks states independently — avoids holding RLock during
// per-breaker mutex acquisition. (SUG-6)
func (r *CircuitBreakerRegistry) OpenBreakers() []string
```

**集成点**：在 `FunctionCallResponseProcessor.executeToolCall()` 的 `resolveToolCallTarget()` 和 `executeToolWithCallbacks()` 之间，通过 BeforeTool 回调检查断路器状态。熔断时返回 `CustomResult`（CircuitOpenError），跳过实际工具执行。

**数据流图**：

```
LLM 返回 tool_call
  → FunctionCallResponseProcessor.executeToolCall()
    → resolveToolCallTarget()  // 解析工具目标
    → BeforeTool Callback Chain
      → CircuitBreakerCallback.HandleBeforeTool()
        → registry.Get(toolName, category)
        → cb.Allow()
          ├─ true (Closed/HalfOpen) → 继续执行
          └─ false (Open) → return CustomResult{CircuitOpenError}
    → executeToolWithCallbacks()
      → 工具执行
      → AfterTool Callback Chain
        → CircuitBreakerCallback.HandleAfterTool()
          ├─ success → cb.RecordSuccess()
          ├─ transient error (IsTransientError=true) → 忽略，不计数
          └─ persistent error → cb.RecordFailure()
```

**与 RetryPolicy 的协作**：

```
工具调用失败
  → RetryPolicy 判断是否瞬态错误
    ├─ 是 → 重试（RetryPolicy 处理）
    └─ 否 → RecordFailure() → 断路器计数
      → 失败次数 ≥ 阈值 → 熔断
        → 后续请求 BeforeTool 拦截
        → system prompt 注入不可用工具列表
```

**与 ToolFilter 的集成（SUG-9 实现）**：延迟加载通过 `DeferredToolManager.ToolFilter()` 实现。`ToolFilter` 在 `buildToolFilter()` 中与 deny-list filter 合并为组合 FilterFunc，统一注入 `llmagent.WithToolFilter`。`ToolFilter` 逻辑：非 deferred 工具直接通过；deferred 工具仅在 `IsActivated()` 为 true 时通过。`IsActivated()` 同时检查 `activated` map（已激活）和 `discovered` map（已发现但未激活），确保搜索发现后工具可见。

### 2.5 与框架的集成方式

#### Circuit Breaker

1. **回调注册**：`BuildCircuitBreakerCallbacks` 创建 `tool.Callbacks`，注册 BeforeTool（检查 Allow）和 AfterTool（记录结果）
2. **装配点**：`internal/agent/trpc_build.go` 中构建 LLMAgent 时，将断路器 Callbacks 追加到 `llmagent.WithToolCallbacks`
3. **System Prompt**：`BuildCircuitBreakerSystemPrompt` 在每次 Run 前检查断路器状态，注入不可用工具列表
4. **与 RetryPolicy 协作**：RetryPolicy 先尝试恢复瞬态错误；非瞬态错误或重试耗尽后，AfterTool 回调记录失败到断路器
5. **瞬态错误过滤（BLK-1 修复）**：AfterHook 通过 `IsTransientError()` 判断错误类型，瞬态错误不触发 `RecordFailure()`
6. **Session 级作用域（SUG-4 文档化）**：`CircuitBreakerRegistry` 为 Session 级实例，每个 Runner/Session 创建独立 Registry，断路器状态不跨 Session 持久化
7. **Category 查找缓存（SUG-1 实现）**：`categoryForTool` 使用 `sync.Once` 缓存 Registry→Category 映射，避免每次调用遍历全量注册表
8. **并发读优化（SUG-3 实现）**：`CircuitBreakerRegistry` 使用 `sync.RWMutex`，`Get()` 和 `OpenBreakers()` 走 RLock 快速路径
9. **状态可观测（F1.6 实现）**：`CircuitBreakerOption` 模式 + `WithOnStateChange` 回调；`CircuitBreakerRegistry` 通过 `WithRegistryOnStateChange` 传播回调；Agent 层通过 loggateway 记录状态转换。4 种状态转换均触发事件：Open→HalfOpen（Allow）、HalfOpen→Closed（RecordSuccess）、HalfOpen→Open 和 Closed→Open（RecordFailure）、any→Closed（Reset）
10. **手动重置 API（F1.7 实现）**：`CircuitBreakerRegistry` 通过 `TRPCBuilderDeps.CircuitBreakerRegistry` 暴露给 Service 层，Service 层可调用 `ResetAll()` / `ResetTool()` 进行管理操作
11. **OpenBreakers 嵌套锁优化（SUG-6 实现）**：`OpenBreakers()` 在 RLock 下收集 breaker 引用，释放锁后独立检查各 breaker 状态，避免持有 RLock 期间获取 breaker 内部 mutex
12. **AfterHook 日志一致性（RC-5 实现）**：AfterHook 接受 `loggateway.Logger` 参数，与 BeforeHook 保持一致
13. **瞬态错误日志级别（RC-4 实现）**：AfterHook 将瞬态错误记录在 Debug 级别，避免正常操作中的日志噪音
14. **Retry Policy 默认值常量化（RC-7 实现）**：重试策略默认值提取为常量，避免魔法数字

#### Deferred Loading

1. **Assemble 阶段**：`Assemble()` 根据 `DeferredTools` 配置将工具分为核心工具和延迟工具
2. **延迟工具实例化**：延迟工具实例化为 `DeferredCallableTool`（带工厂函数），注册到 `DeferredToolManager` catalog
3. **元工具注入**：`tool_search` 作为核心工具注入 LLMAgent
4. **ToolFilter 集成（SUG-9 实现）**：`DeferredToolManager.ToolFilter()` 在 `buildToolFilter()` 中与 deny-list filter 合并为组合 FilterFunc，统一注入 `llmagent.WithToolFilter`
5. **自动发现**：`ToolSearchTool` 搜索时自动调用 `Discover(toolName)` 标记已发现工具
6. **激活缓存**：已激活的延迟工具缓存在 `activated` map 中，同一 Session 内避免重复搜索和工厂调用
7. **工厂重试（SUG-7 实现）**：`DeferredCallableTool` 使用 `sync.Mutex` + `resolved bool`，工厂失败后可重试
8. **分词匹配与相关性评分（SUG-8 实现）**：搜索查询按空格分词，按名称精确匹配（+10）、名称包含（+5）、Category 包含（+3）、Description 包含（+2）评分，按得分降序 + 名称升序排列

11. **Optional/nil 语义（RC-8 文档化）**：`DeferredToolManager` 在 `TRPCBuilderDeps` 中可能为 nil（延迟加载未启用时），调用方必须 nil 检查

| 场景 | 处理方式 |
|------|----------|
| 断路器 Open 状态 | BeforeTool 返回 `CustomResult{CircuitOpenError}`，LLM 收到不可用提示 |
| 断路器 HalfOpen 探测失败 | 立即回到 Open 状态，重置 RecoveryTimeout |
| 断路器 HalfOpen 探测成功 | 转为 Closed 状态，重置失败计数 |
| 断路器状态转换 | `onStateChange` 回调触发，Agent 层通过 loggateway 记录（F1.6） |
| 断路器手动重置 | Service 层通过 `TRPCBuilderDeps.CircuitBreakerRegistry` 调用 `ResetAll()` / `ResetTool()`（F1.7） |
| 瞬态错误（io.EOF / net.Error / context.Canceled / DeadlineExceeded） | AfterHook 忽略，不触发 `RecordFailure()`，避免误触发熔断；Debug 级别记录（RC-4） |
| tool_search 无匹配结果 | 返回空列表 + 建议 LLM 重新描述需求 |
| 延迟工具激活失败（工厂错误） | 返回错误消息给 LLM，不中断 Run；下次 Call() 可重试工厂（SUG-7） |
| 干扰项检测无冲突 | 不注入消歧指导，零开销 |
| SensitivePathPolicy 拦截 | BeforeTool 返回 `CustomResult{blocked: true, reason}` |
| SensitivePathPolicy 审计日志 | 结构化日志 StepID "tool.safety.policy_violation"，severity "high"，含 rule/path/tool name（F4.5） |
| SensitivePathPolicy 配置为空 | 不注册回调，零开销 |
| 断路器 Registry 并发访问 | RWMutex 保护，`Get()`/`OpenBreakers()` 走 RLock 快速路径（SUG-3） |
| 断路器 Registry 作用域 | Session 级实例，不跨 Session 共享，Session 结束时自动清理（SUG-4） |
| 延迟工具 Session 缓存过期 | Session 结束时自动清理，不持久化 |
| Command Safety 非路径文本误报 | `looksLikePath()` 过滤非路径 token，描述文本中的 `.env` 不触发拦截（BLK-2/BLK-3） |
| Command Safety JSON 解析失败 | 回退到 `extractPathTokens(string(args))` 从原始文本提取路径（RC-3） |
| Command Safety Windows 路径 | `looksLikePath()` 检测 `X:\` 模式的 Windows 绝对路径（RC-9） |
| Deny list 解析失败 | 输出警告 "deny list will NOT be enforced"，deny list 不生效（RC-6） |
| DeferredManager / CircuitBreakerRegistry 为 nil | `TRPCBuilderDeps` 中 Optional 字段，调用方必须 nil 检查（RC-8） |

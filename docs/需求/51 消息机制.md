# 消息机制 — 需求规格

> **2026-05-17 现状对齐**：表中 §1.1 现状问题 1–8 项大部分已落地：
> - ✅ 1 / 3 / 6 / 7 / 8：事件总线统一（`internal/event/bus.go`）、Backpressure 策略与计数指标、WebSocket 单连接复用 Chat / Monitor / Team。
> - 🟡 2：事件类型部分统一（Chat / Team 已对齐，Monitor 仍用独立 `log` 通道，Envelope 通用化未完成）。
> - ❌ 4：事件持久化与断连重放未实现。
> - ❌ 5：双向通信（cancel / steer / enqueue）通道已有，但 EnqueueUserMessage 端到端联调未完成。
>
> 后续以 `guides/execution-plan.md` 附录 A "消息机制" 行为准；本文余下作为产品需求基线参考。

---

> 消息机制是 Aranea-Agents 全场景通信的底层基础设施，负责 Agent/Team/Graph/Monitor/Channel 等所有模块的事件产生、路由、传输与消费。本文档定义消息机制的产品需求，技术设计见 [51a 后端消息机制](./51a%20后端消息机制.md) 和 [51b 前端消息机制](./51b%20前端消息机制.md)。

## 一、背景与目标

### 1.1 现状问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | 事件投影逻辑散落在 Service 层 | `trpc_turn.go` 中 200+ 行事件循环，混合事件解析、传输写入、消息落库、用量记录 |
| 2 | 事件类型不统一 | Chat 用 `delta/done/tool.call`，Team 用 `TeamRunEvent.Type`，Monitor 用 `log` |
| 3 | 无统一事件总线 | 各 Broker 独立实现，无法跨场景路由 |
| 4 | 无事件持久化与重放 | 断连后无法恢复，前端刷新丢失中间状态 |
| 5 | 无双向通信 | 用户中断、SteerableRunner.EnqueueUserMessage 无法通过现有连接上行 |
| 6 | 背压缺失 | 慢客户端导致 channel 满后事件被丢弃 |
| 7 | Monitor 日志与 Agent 事件割裂 | 运维日志走独立端口，与 Agent 事件无法统一订阅和过滤 |
| 8 | 连接浪费 | Chat + Monitor + Team 需要多个独立连接 |

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 统一事件模型 | 所有通信（Chat/Team/Graph/Channel/Cron/A2A/Monitor）共享同一套事件定义与流转规则 |
| 框架对齐 | 事件模型以 trpc-agent-go `event.Event` 为真相源，项目层只做投影与扩展 |
| 分层清晰 | 事件产生在运行时层、路由在 Biz 层、传输在 Server 层，各层职责不越界 |
| 双向通信 | WebSocket 原生支持上行（cancel/enqueue/steer/subscribe），无需额外 HTTP 端点 |
| 通道复用 | 一个 WebSocket 连接承载所有事件类型（chat/monitor/team/graph/system），多路复用 |
| 可扩展 | 新场景（Graph 节点事件、A2A 消息、Artifact 通知）无需修改核心机制 |
| 可靠性 | 背压控制、心跳检测、事件缓冲与重放、自动重连 |
| 传输无关 | 同一 Envelope 可投射到 WebSocket / Webhook，传输层可替换 |

## 二、范围定义

### 2.1 本期实现

- 统一信封模型（Envelope）：定义项目层统一的事件传输单元
- EventBus 统一事件总线：替代现有独立 Broker，统一事件路由
- EventProjector 事件投影器：将 trpc `event.Event` 投影为 Envelope
- WebSocket 统一传输：替代 SSE，支持双向通信与多路复用
- Channel 多路复用：一个 WS 连接通过 channel 字段区分 chat/monitor/team/graph/system
- 动态订阅：客户端通过 subscribe/unsubscribe 控制订阅范围
- 心跳与断连检测：ping/pong 机制与自动重连
- 事件缓冲与重放：内存缓冲区支持断连后恢复
- 内部消费者：StateDelta 持久化、用量记录、工具调用记录、回调通知
- Monitor 日志统一接入：日志统一为 Envelope，通过 WS channel:monitor 传输
- 向后兼容：旧 SSE 事件名映射到新 Envelope 类型

### 2.2 未来扩展

- Envelope 持久化到 SQLite（可选）
- Webhook 传输投射（同一 Envelope 投射到 Webhook）
- A2A 协议消息映射
- Artifact 通知事件
- 事件时间线可视化（前端）

## 三、用户场景

### 场景 1：Chat 对话流式交互

用户在 Chat 页面与 Agent 对话，实时看到文本增量、工具调用、推理过程，可随时取消生成。

```
1. 前端建立 WS 连接
2. 发送用户消息（上行 user_message）
3. 实时接收 text_delta / tool_call / tool_result / text_done / runner_completion
4. 可随时发送 cancel 取消生成
5. 可发送 enqueue_message 中途插入消息（SteerableRunner）
```

### 场景 2：Team 多 Agent 协作

用户与 Team 对话，看到各成员 Agent 的消息流、Agent 转移动画，可按 filter_key 过滤特定 Agent。

```
1. 前端连接 WS，Team Session 自动订阅 channel:team
2. 收到 member_message_start / member_delta / member_message_done
3. 收到 transfer 事件，显示 Agent 切换动画
4. 可通过 subscribe 动态过滤特定 Agent 的事件
```

### 场景 3：Graph 工作流执行

用户运行 Graph 工作流，看到节点开始/结束、检查点事件，支持 HITL 中断恢复。

```
1. 前端连接 WS，Graph Session 自动订阅 channel:graph
2. 收到 graph_node_start / graph_node_end / checkpoint
3. HITL 中断时收到 runner_completion(tag:"interrupt")
4. 用户审批后发送 user_message 恢复执行
```

### 场景 4：Monitor 运维日志

运维人员动态订阅 Monitor 日志，按级别过滤，无需独立连接。

```
1. 前端发送 subscribe 订阅 channel:monitor
2. 可指定级别过滤（如 ERROR|WARN）
3. 收到 log 类型 Envelope
4. 不需要时发送 unsubscribe 取消订阅
```

### 场景 5：断连恢复

用户网络抖动导致 WS 断连，重连后自动恢复未收到的事件。

```
1. WS 断连，前端自动重连（指数退避）
2. 重连时携带 last_event_id
3. 服务端从 EventBuffer 重放断连期间的事件
4. 重放完成后切换到实时流
```

## 四、产品需求

### 4.1 统一信封模型（Envelope）

**需求**：所有事件统一为 Envelope 格式传输

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | string | 是 | 事件唯一 ID |
| type | string | 是 | 事件类型（见 4.2） |
| author | string | 是 | 事件作者（agent_name / user / system） |
| session_id | string | 是 | 所属 Session |
| request_id | string | 否 | 请求 ID |
| invocation_id | string | 否 | 调用 ID |
| parent_invocation_id | string | 否 | 父调用 ID |
| branch | string | 否 | 分支追踪 |
| filter_key | string | 否 | 层级过滤键 |
| tag | string | 否 | 业务标签 |
| timestamp | string | 是 | ISO 8601 时间戳 |
| version | int | 是 | 版本号 |
| content | object | 否 | 文本/推理内容 |
| tool_call | object | 否 | 工具调用信息 |
| state_delta | object | 否 | 状态增量 |
| transfer | object | 否 | Agent 转移信息 |
| error | object | 否 | 错误信息 |
| usage | object | 否 | Token 用量 |
| extensions | map | 否 | 扩展元数据 |
| actions | object | 否 | 流控制提示 |
| trace | object | 否 | 执行追踪 |
| metadata | map | 否 | 自定义元数据 |

**验收标准**：所有场景的事件统一为 Envelope 格式，前端按 `type` 字段分发处理

### 4.2 事件类型定义

| Envelope type | 说明 | 典型 Channel |
|---------------|------|-------------|
| `text_delta` | 文本增量（流式） | chat |
| `text_done` | 文本完成 | chat |
| `tool_call` | 工具调用开始 | chat |
| `tool_result` | 工具返回结果 | chat |
| `state_delta` | 状态增量 | chat |
| `transfer` | Agent 转移 | chat / team |
| `runner_completion` | 运行完成 | chat |
| `error` | 错误 | chat |
| `log` | 运维日志 | monitor |
| `graph_node_start` | Graph 节点开始 | graph |
| `graph_node_end` | Graph 节点结束 | graph |
| `checkpoint` | 检查点事件 | graph |
| `intent_pass` | 意图识别结果 | chat |
| `member_message_start` | Team 成员消息开始 | team |
| `member_delta` | Team 成员增量 | team |
| `member_message_done` | Team 成员消息完成 | team |

**验收标准**：每种事件类型有明确的语义定义，前端可按类型分发到对应 UI 组件

### 4.3 WebSocket 统一传输

**需求**：所有事件通过 WebSocket 统一传输，替代现有 SSE

| 能力 | 说明 |
|------|------|
| 连接端点 | `WS /v1/ws?session_id=xxx&token=jwt_token` |
| 认证方式 | 三级回退：URL `token` 参数 → `Authorization: Bearer` Header → `access_token` Cookie |
| 双向通信 | 下行推送 Envelope，上行接收 user_message / cancel / enqueue_message |
| 多路复用 | 通过 `channel` 字段区分 chat / monitor / team / graph / system |
| 心跳检测 | 客户端每 25s 发送应用层 ping，服务端回复 pong；协议层 Ping/Pong 30s 间隔 |
| 自动重连 | 指数退避（1s/2s/4s/8s/16s/30s cap） |
| 事件重放 | 重连时携带 `last_event_id`，服务端从 EventBuffer 重放 |
| 重放顺序保证 | 重放期间实时事件缓冲，重放完成后按序发送 |

**验收标准**：
- 一个 WS 连接承载所有事件类型
- 上行消息（cancel/enqueue/subscribe）无需额外 HTTP 端点
- 断连后可自动重连并恢复事件
- 重放事件与实时事件不交错，保证顺序
- Cookie 认证支持浏览器 WebSocket 原生连接

### 4.4 Channel 多路复用

**需求**：一个 WS 连接通过 Channel 区分不同事件流

| Channel | 方向 | 说明 | 默认订阅 |
|---------|------|------|---------|
| `chat` | 双向 | Chat 事件 + 用户消息上行 | 连接即订阅 |
| `monitor` | 下行 | 运维日志、系统事件 | 需显式 subscribe |
| `team` | 下行 | Team 运行事件 | Team Session 自动订阅 |
| `graph` | 下行 | Graph 工作流事件 | Graph Session 自动订阅 |
| `system` | 下行 | 系统通知（connected/error/reconnect） | 连接即订阅 |
| `control` | 上行 | 订阅控制（subscribe/unsubscribe/ping） | 连接即订阅 |

**验收标准**：
- 不同 Channel 的事件互不干扰
- 客户端可动态 subscribe/unsubscribe Channel
- Channel 路由由服务端自动完成（Envelope 根据 type 和 session 类型分配）

### 4.5 上行消息

**需求**：客户端通过 WS 发送上行消息

| 上行类型 | Channel | 说明 |
|---------|---------|------|
| `user_message` | chat | 发送聊天消息（content + attachments） |
| `cancel` | chat | 停止当前生成 |
| `enqueue_message` | chat | 中途插入消息（SteerableRunner） |
| `subscribe` | control | 动态订阅通道（含 filters） |
| `unsubscribe` | control | 取消订阅通道 |
| `ping` | control | 心跳 |

**验收标准**：
- 所有上行消息通过 WS 发送，无需额外 HTTP 端点
- cancel 可立即停止当前生成
- subscribe 可动态订阅 Monitor 日志并指定级别过滤

### 4.6 EventBus 统一事件总线

**需求**：替代现有独立 Broker，统一事件路由

| 能力 | 说明 |
|------|------|
| 单一发布入口 | 所有事件通过 `EventBus.Publish()` 发布 |
| 多订阅者路由 | 按 session_id / team_id / channel / filter_key 路由 |
| 内部消费 | 状态持久化、用量记录、回调触发等作为内部订阅者 |
| 背压控制 | 慢订阅者不阻塞快订阅者，丢弃最旧事件 |
| FilterKey 匹配 | 对齐 trpc-agent-go 前缀匹配语义 |

**验收标准**：
- 现有 `TeamRunEventBroker` 和 `MonitorLogBroker` 合并到 EventBus
- 新增订阅者无需修改核心代码
- 慢订阅者不影响其他订阅者

### 4.7 EventProjector 事件投影器

**需求**：将 trpc `event.Event` 投影为项目层 Envelope

| 职责 | 说明 |
|------|------|
| 类型映射 | trpc ObjectType → Envelope type |
| 内容提取 | 从 `model.Response.Choices` 提取文本/推理/工具调用 |
| 副作用触发 | StateDelta 持久化、Usage 记录、ToolCall 记录 |
| 消息落库 | 将用户/助手消息写入 Session |

**验收标准**：
- 事件循环从 200+ 行简化为投影+发布
- 所有副作用由 EventBus 订阅者处理
- Service 层不再直接管理事件投影逻辑

### 4.8 事件缓冲与重放

**需求**：支持断连后事件恢复

| 能力 | 说明 |
|------|------|
| 内存缓冲区 | 每 Session 保留最近 200 条 Envelope |
| 重放协议 | replay_start → 重放事件 → replay_end |
| 重连参数 | `last_event_id` 参数指定重放起点 |
| 缓冲淘汰 | 环形缓冲区，超出容量覆盖最旧事件 |

**验收标准**：
- 断连重连后可恢复未收到的事件
- 重放期间新事件缓冲，重放完成后发送
- 缓冲区满时丢弃最旧事件，不影响实时流
- 重放与实时流之间有 replayDone 同步屏障，保证事件不乱序

### 4.9 内部消费者

**需求**：EventBus 内部订阅者处理副作用

| 消费者 | 订阅条件 | 职责 |
|--------|---------|------|
| StateDeltaConsumer | `type == "state_delta"` | 将 StateDelta 应用到 Session State 并持久化 |
| UsageConsumer | `type == "runner_completion"` | 记录 Token 用量 |
| ToolCallConsumer | `type == "tool_call" \|\| "tool_result"` | 记录工具调用 |
| CallbackConsumer | `type == "runner_completion" && has_channel` | 触发 Channel Webhook 回调 |
| EventBufferConsumer | 全量 | 将 Envelope 追加到 EventBuffer |
| MessageStoreConsumer | `type == "text_done" \|\| "user_message"` | 将完整消息落库 |

**验收标准**：
- 各消费者独立运行，互不影响
- 消费者失败不影响事件路由和其他消费者

### 4.10 Monitor 日志统一接入

**需求**：Monitor 日志统一为 Envelope 格式，通过 WS 推送

| 来源 | metadata.source | 说明 |
|------|----------------|------|
| Runner 生命周期 | `runner` | Agent 启动/完成/错误 |
| Tool 执行 | `tool` | 工具调用开始/结束/错误 |
| LLM 调用 | `llm` | 模型请求/响应/重试 |
| 系统事件 | `system` | 内存/连接/配置变更 |
| 自定义 | `custom` | 业务层注入的日志 |

**验收标准**：
- Monitor 日志不再需要独立端口
- 前端可通过 subscribe 动态订阅，指定级别过滤
- 日志与 Agent 事件在同一连接中传输

## 七、安全需求

| 风险 | 缓解措施 |
|------|---------|
| WS 跨域 | Origin 白名单校验 |
| 事件泄露 | EventBus 订阅时校验 session_id 归属 |
| WS 消息注入 | 上行消息类型白名单，payload 校验 |
| XSS via content | Envelope content 做 HTML 转义后渲染 |
| DDoS via 大量连接 | 限制每 IP/每 Session 最大连接数 |
| JWT 过期 | WS 连接期间定期校验 token 有效性 |
| 消息大小 | WS ReadLimit 1MB，超限断连 |
| WS 认证 | 三级回退认证（URL token → Authorization Header → Cookie），Cookie 方式支持浏览器原生 WebSocket |

## 九、验收标准总览

1. 所有场景事件统一为 Envelope 格式，前端按 `type` 字段分发
2. 一个 WS 连接承载所有事件类型（chat/monitor/team/graph/system）
3. 上行消息（cancel/enqueue/subscribe）通过 WS 发送，无需额外 HTTP
4. 断连后可自动重连并恢复事件（EventBuffer 重放）
5. 重放与实时流有同步屏障，保证事件不乱序
6. 客户端可动态 subscribe/unsubscribe Channel
7. Monitor 日志统一为 Envelope，不再需要独立端口
8. 事件循环简化为投影+发布，副作用由 EventBus 订阅者处理
9. Chat 和 Team 场景均使用 EventProjector 投影流式事件
10. 现有 `TeamRunEventBroker` 和 `MonitorLogBroker` 合并到 EventBus
11. 背压控制：慢订阅者不阻塞快订阅者
12. 安全：Origin 校验、session_id 归属校验、消息大小限制、Cookie 认证支持
13. 应用层心跳：客户端 25s 间隔 ping，服务端 pong 回复

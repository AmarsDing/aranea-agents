## 1. 直接结论

**知识库的能力基础已经相当丰富，但当前代码尚未构成可靠的用户闭环，不能判定为“模块完善、业务正确、可直接交付多人日常使用”。**

三个问题的答案分别是：

| 用户的问题 | 评审判断 | 依据 |
|---|---|---|
| 模块是否完善 | 技术能力较全，产品闭环仍有明显缺口 | 本地/团队双存储、词法/向量/图谱检索、引用、治理都有实现；创建、删除、移动、权限、证据更新之间仍有断点 |
| 业务逻辑是否正确 | 存在必须修复的可达错误 | 原始二进制可能被 Markdown 覆盖；覆盖移动先改文件后撞数据库约束；删除可能复活；检索与治理存在授权缺口 |
| UI 是否满足用户需求 | 对熟悉系统的维护者提供了较多工具；普通成员的关键任务尚不能可靠完成 | 跨库搜索结果打不开、保存期间输入可能丢失、跨库标签使用错误上下文、普通上传者无法把新资料转为私有 |
| 好的改进方向 | 先维护数据、权限、证据和草稿的一致性，再简化用户入口 | 以“存得进、找得到、看得懂、改得对、可追溯、可撤销”为验收主线 |

这是一份当前工作树的代码审查，不能替代上线验收。尝试访问 localhost:8800 和 localhost:9301 均得到连接拒绝，因此本报告的 UI 判断来自页面、状态管理与 API 调用链，**没有宣称完成运行界面、真实文件导入、真实模型召回或用户可用性实测**。

## 2. 审查依据与范围

已读取项目 aranea-review、aranea-docs-guide，模块交叉参考 65 §1.13、37-knowledge 三件套相关章节，以及 org-invariants。对照了 10 月 19 日升级方案、10 月 20 日实施报告；旧报告的“已完成/待实现”不直接作为本次事实，结论以当前接线为准。

重点链路：

- 上传/目录同步 → 格式抽取 → Markdown 整理 → 分块 → embedding → 索引提交 → 页面任务状态。
- 本地文件/团队正文 → 编辑、删除、覆盖移动、跨库迁移 → 派生索引与引用。
- 页面 Search、Agent knowledge_search/knowledge_reflect、预检索注入 → 联邦路由 → dense/BM25/图谱 → 引用回采。
- workspace、文档可见性、部门/岗位共享 → 普通读写入口、Agent 直调、治理入口。
- 建库 → 导入 → 阅读 → 搜索打开 → 编辑保存 → 切库 → 权限调整 → 治理审核。

严重性约定：

- **P1：必须在相关能力进入正式验收前修复。** 涉及越权、原始资料/草稿破坏、存储分裂或核心契约错误。
- **P2：功能正确性或产品闭环问题。** 可以通过明确限制范围进入阶段试点，但不能继续以完整能力对外承诺。
- **产品建议：** 改善使用方式或下一阶段范围，不等同于已有需求漏实现。

## 4. 必须优先处理的业务问题

### KB-01 / P1：Agent 显式指定库 ID 可以绕过 workspace 隔离

**触发：** 聊天 options.knowledge_bases 包含其他工作区库 ID，或无绑定库的 Agent 显式调用该库 ID。

**证据链：**

- internal/service/chat_orchestrator_turn_api.go:289 原样接收 KnowledgeBases；chat_orchestrator_turn_phases.go:561 原样注入运行上下文。
- internal/tools/knowledge/tool.go:187、251、271：显式库走单库检索；空配置白名单允许任意 ID，随后直接调用 Router/Retriever。
- internal/knowledge/search_helpers.go:65-67 虽调用带 workspace 过滤的 GetCollection，却将读取失败变成 false，继续检索。
- internal/data/knowledge_search.go:68、104、175、242 的底层召回按 collection_id 与文档可见性过滤，没有另行验证库所属 workspace。

**后果：** 其他工作区中 visibility=collection 的正文可被检索。HTTP Search 的 service 授权不能保护 Agent 绕过该 service 的调用路径。

**修复：** 在共用检索入口解析并验证授权库集合；不存在、不可见和授权失败必须终止，不能当成“无语义层判定失败”继续。调用方传入的库数组只能作为请求范围，不能成为权限凭据。

### KB-02 / P1：治理提案列表与处置缺少 workspace/写权限边界

**触发：** 已登录调用方不传 collection_id 列举治理提案，或提交其他库的提案 ID。

**证据链：**

- internal/service/knowledge_governance.go:101-111 仅在显式传库时检查读权限；空库直接进入全局列表。
- internal/data/knowledge_curate.go:365 起 SQL 只接受可选 collection/status，没有 workspace JOIN 或谓词。
- knowledge_governance.go:141-155 的 resolve 不读取提案所属库，也没有角色或库写权限校验。
- internal/biz/knowledge/curate.go:499-514 读取提案后先处置、后更新状态；orphan 分支在 :537-544 直接调用 DeleteDocument。
- internal/data/knowledge_documents.go:271 起的删除按文档 ID 执行；该治理路径没有先经过普通文档删除的 service 读写门。

**后果：** 提案内容、文档 ID 等跨工作区暴露；可拒绝他人的 pending 提案；存在 orphan 提案时还可触发其文档删除。不能将“平台管理视图”的注释当作实际管理员授权。

**修复：** 列表始终按授权库范围过滤；resolve 先读取所属库、验证 workspace 与治理写角色。将提案认领、文档处置、终态与审计置于事务或可恢复操作中。

**并发补充：** 当前两个请求可以同时读到 pending 后各执行处置；最后的 pending 条件 UPDATE 只保护提案状态，保护不到已发生的正文副作用。事实冲突处置还需正文版本/CAS。

### KB-03 / P1：二进制原件被当成可编辑笔记，保存可覆盖原文件

**触发：** 本地库首次同步 PDF、图片或 Office 文件，抽取成功后在工作台编辑并保存。

**证据链：**

- internal/knowledge/body_compiler.go:24-31 返回提取稿与 text/markdown。
- internal/knowledge/vault_sync.go:202、225-231 将该 MIME 与原 .pdf/.png/.docx 的 RelPath 一起建档。
- web/src/features/knowledge/useKnowledgeWorkbench.ts:41-44 按 MIME 判断可编辑；:75-86 展示 content_text，即抽取后的 Markdown。
- 保存经 :125 → internal/service/knowledge.go:914 → internal/biz/knowledge/vault_write.go:232-243，写回 doc.RelPath 对应的原路径。

**后果：** 用户在编辑提取稿，却将原始文件现址替换为 Markdown。文件 CAS 具有 trash 备份，不能据此宣称原件永久不可恢复；但原路径的正常文件已受破坏。附件输出还可能使用错误 MIME。

**修复：** 分开保存 source_mime_type、派生 body_format 和编辑能力。二进制原件只读；“编辑提取稿”应另存笔记并保留原件关联，不得复用原文件写路径。

### KB-04 / P1：同名覆盖移动先改文件，再因数据库唯一约束失败

**触发：** notes/a.md 移至已存在且已索引的 archive/a.md，选择“覆盖”。

**证据链：**

- internal/biz/knowledge/vault_filer.go:362-389 先把目标文件移入 trash，再重命名源文件。
- internal/biz/knowledge/vault_write.go:297-302 随后只更新源文档 rel_path，没有处理目标文档行。
- internal/data/knowledge_documents.go:137-140 直接 UPDATE；knowledge_schema.go:129-130 对 collection_id + 非空 rel_path 建唯一索引。

**后果：** 目标记录仍占用该路径，数据库更新失败；此时源文件已离开原位置、目标内容已被覆盖，数据库仍保留两个旧身份。UI 报失败不能说明此次操作没有产生副作用。

**修复：** 明确覆盖后保留哪个文档身份、引用与版本；事务处理两条记录；文件操作配可恢复操作日志与补偿。该组合完成前应在 UI 禁用“覆盖”，保留可正确执行的“保留两份”。

### KB-05 / P1：删除本地库文档只删数据库，原文件会重新入库

**证据链：** internal/service/knowledge.go:861-877 → internal/biz/knowledge/knowledge.go:531-542 → internal/data/knowledge_documents.go:271-308，只处理数据库、计数与图索引，没有调用文件回收。

**触发与后果：** 磁盘原件保留；重启时 internal/knowledge/vault_sync_runner.go:241 附近从数据库重建同步快照，磁盘上的孤立文件再次被识别为新文件。后续源文件变动也可触发重入库。用户认为删除成功，资料却会复活。

**修复：** local 删除应统一执行“原件移入回收站 → 镜像与派生索引删除 → 同步状态更新”；team 删除使用数据库生命周期。对失败提供补偿和可见恢复入口。

### KB-06 / P1：跨库移动没有迁移实际存储

**触发：** 同维度的 local→team 或 local→另一 local 库。

**证据链：** internal/biz/knowledge/knowledge_part2.go:51-81 仅校验存在与 Dim；internal/data/knowledge_move.go:25-74 更改归属与附表，保留 RelPath，不迁移原文件。internal/biz/knowledge/vault_write.go:357 起按新库 root 与旧 RelPath 解析附件。

**后果：** local→team 因目标无 root 而无法解析原件；local→local 找错位置，目标恰有同名文件时可能读到错误资料。源文件继续存在，源库后续同步又重新导入，形成双份。

**修复：** 分别定义四种存储组合的迁移、谱系、引用与失败恢复；未实现的组合在 API 和 UI 同时拒绝。保留已有复制式晋升能力，明确“复制/晋升”和“移动”的用户语义。

### KB-07 / P1：embedding 故障时的词法降级被维度校验阻断

**触发：** 本地语义库 embedding 请求失败，或处于熔断窗口。

**证据链：**

- internal/knowledge/vault_sync.go:350-390 生成 nil embedding 的词法块，计划降级提交。
- :265-273 调 CommitIndexedDocumentMeta；internal/data/knowledge_chunks.go:99-114 对 expectedDim>0 的子块要求向量长度完全匹配，nil 被拒。
- vault_sync.go:278-290 的失败计数与退避维护位于提交之后，该分支到不了。

**后果：** 新资料没有词法索引；已有事务可能保留旧索引，但新内容不能同步。同步轮询可持续重复失败请求，熔断计数无法按预期推进。

**修复：** 区分“缺向量、可词法检索”与“非空向量维度错误”；可靠提交降级状态与失败计数，后续独立回填向量。页面应展示词法可用/语义待恢复，不用一个 indexed 状态掩盖差异。

### KB-08 / P1：人工保留新/旧事实后，检索可能继续使用已否决的事实段

**触发：** 对已经具有完整 chunks 的团队词条执行事实冲突 keep_old/keep_new。

**证据链：**

- internal/biz/knowledge/curate.go:627 直接更新文档正文，:636 记版本，:637 重建块级引用索引。
- internal/data/knowledge_documents.go:215-221 的 UpdateDocumentContent 只更新 content_text/organized/stale_at。
- internal/biz/knowledge/block_pipeline.go:26、42-88 重建 knowledge_blocks、refs 和 explicit links，不重建检索用 knowledge_chunks。
- 当前处置路径未调用已接线的 writeBackReplay。internal/data/knowledge_embed.go:103-117 的修复条件只检查缺子块或缺向量，不识别“向量完整但正文已变”的情况。

**后果：** 详情页和治理结果已显示生效版本，dense/BM25 仍能召回审核前已否决的事实段。keep_old 丢弃新段，keep_new 丢弃旧段，两种决定都受影响。既有修复工人不能保证自动收敛。

**修复：** 所有正文变更进入统一版本提交入口，同时生成索引任务；保存 source_revision/index_revision，按版本检查缺失与漂移。审核完成必须说明“正文已生效/检索更新中/检索已更新”，不能仅标 applied。

### KB-09 / P1：共享库的只读边界可被部分写入口绕过

**正确范围：** internal/data/knowledge.go:52-65 已阻止普通 GetCollection 访问其他 workspace；因此这里不是“跨库移动可任意写入任何租户”。问题在 workspace 为空的系统/共享库：允许读取，但租户本应不可写。

**证据链：**

- internal/service/knowledge_explorer.go:36-64 的建目录、建笔记使用 assertCollectionAccess 读门。
- internal/service/knowledge.go:933-941 移动只检查源库写权限；目标只在 knowledge_part2.go:74-81 检查存在与维度。
- 与 knowledge.go:418-419、447-454 的 assertCollectionMutateAccess 约定不一致。

**后果：** 用户可以修改可读的共享本地库，或将自己的文档注入同维度共享库，影响所有读者。

**修复：** 写操作统一经过库写权限门；跨库操作两端均校验。授权应在共用领域入口维持不变量，避免每个 handler 独自记忆。

### KB-10 / P1：草稿保护不完整，保存竞态与离开页面都可丢改动

**场景 A：** 点击保存，网络请求未完成时继续输入。

- web/src/features/knowledge/useKnowledgeWorkbench.ts:125 提交当时正文，:134 成功后无条件 dirty=false。
- web/src/components/knowledge/workbench/WorkbenchTabs.vue:81-94 的编辑器在保存期间仍允许输入。
- 请求期间新增的内容未提交，却被标为已保存，随后关闭标签不再触发脏确认。

**场景 B：** 编辑后直接点击聊天等导航、刷新或关闭浏览器。

- KnowledgePage.vue:312 创建页面局部 workbench，正文只存内存。
- 现有确认在 useKnowledgeWorkbench.ts:144-159 的手工 closeTab；知识库页面/组件/composable 未接路由离开与 beforeunload 保护。

**修复：** 保存绑定提交快照/编辑版本，只在当前内容仍与提交快照相同才清 dirty；服务端直接返回提交版本 hash。增加离开保护和按用户/workspace/doc 隔离的草稿恢复。

## 7. 推荐方案：以资料和证据为中心组织产品

### 7.1 用户入口

默认提供四个清晰入口：

| 入口 | 用户要做的事 | 默认呈现 |
|---|---|---|
| 资料 | 上传、阅读、整理、编辑、恢复 | 搜索框与上传主按钮；标题、状态、更新时间、可见性、索引状态；原件/提取稿关系 |
| 搜索 | 提问、找片段、核查来源 | 默认全部可见资料；库/目录筛选；命中文档、证据位置、版本；部分覆盖与降级说明 |
| 质量与审核 | 处理失败导入、纠正知识、审核冲突 | 待处理数、具体失败原因与可执行重试、前后差异、审核后的索引生效状态 |
| 管理 | 创建托管库、挂载目录、模型与成员权限 | 普通成员只见授权范围；服务器路径、embedding/重排、图谱维护置于高级设置 |

3D 图谱保留为资料关联视图；命令面板、快捷键、多标签继续服务熟练用户。普通阅读者进入时优先预览，编辑者明确点击“编辑”；二进制资料使用原件查看器和独立提取稿。

创建知识库默认使用已有 team 后端，填写名称即可使用词法检索；语义层作为可选增强。已有本地目录库继续支持，由有权限的维护者明确挂载，界面标注目录位于服务端。

### 7.2 后端需要共同维护的六条不变量

1. **任何返回的证据都属于调用方可读范围。** HTTP、Agent、联邦、图扩展、卡片、时态查询共用授权与范围语义。
2. **原件与派生稿分别建模。** 原文件 MIME 与位置不因抽取而改变；编辑提取稿不会覆写原件。
3. **所有正文变更都有版本，所有索引都知道对应版本。** 保存、治理、写回、同步走统一提交与可恢复索引任务。
4. **移动、覆盖、删除遵守所属存储的生命周期。** 文件与数据库无法共用物理事务时，使用持久操作记录、幂等步骤和补偿；不承诺不存在的原子性。
5. **UI 的已保存/已索引/已生效都有可核对的事实。** 草稿版本、持久版本、检索版本分别明确，不能由单个布尔值代替。
6. **没有评估就不输出评估置信度。** 空结果、依赖降级、部分覆盖、索引落后分别告知用户/Agent。

~~~mermaid
flowchart LR
    A[原件 local / 正文 team] --> B[有版本的内容提交]
    B --> C[可恢复索引任务]
    C --> D[词法 / 向量 / 块引用 / 图谱]
    D --> E[统一授权与范围检索]
    E --> F[回答与真实证据锚点]
    F --> G[反馈 / 人工治理]
    G --> B
~~~

该方案保留现有公司→部门→岗位、专项 Agent、按花名册编排与知识引用方式。知识权限从已有身份与组织节点获得，不需要改变组织架构或给所有 Agent 配置共用工具面。

## 8. 最小实施顺序与验收门

以下为建议迭代边界，不是已授权的实现承诺；跨模块设计应按 AS-ADR-01 记录决策，行为变更同步 37 三件套。

| 顺序 | 交付范围 | 完成标准 |
|---|---|---|
| 第一批：数据与授权 | KB-01/02/03/04/05/09/10；为不支持的移动组合明确禁用 | 非授权库任何入口不可读写；编辑不改坏原件；覆盖失败可恢复；删除重启不复活；保存中输入与切页草稿不丢 |
| 第二批：一致性与核心操作 | KB-06/07/08/11/12/13 | 文件、正文与索引版本收敛；依赖失败仍可词法用；治理后已否决事实不再被正常召回；跨库结果可打开；活动笔记上下文正确；上传者可管理自己的隐私 |
| 第三批：普通用户产品入口 | 默认托管库、明确导入入口、原件/提取稿阅读、任务恢复、可见性展示 | 无服务器知识的成员能完成建库/导入/查找/更新；不需要理解 embedding/dim |
| 第四批：检索可信度 | KB-15/16/17/18、卡片证据、覆盖披露与真实问答集 | 时间/目录/元数据筛选对全部召回腿一致；未评估与低质量可辨认；配置重启不漂移；真实问题具备可追溯前后对比 |

建议使用下面的业务验收用例，而非只检查接口返回 200：

1. 本地导入 PDF/图片/Office，阅读和编辑提取稿后核对原件 hash 不变。
2. 两个已索引同名文件执行覆盖；分别在文件移动、数据库更新、索引刷新处注入失败，验证补偿与恢复。
3. 删除本地文件，随后重启、重新扫描，确认不会复活；从回收站恢复后身份与引用符合设计。
4. 四种存储组合逐项验收；未支持组合在 UI/API 均有一致拒绝。
5. 用两个工作区、普通用户、共享系统库、private/shared 文档覆盖 HTTP/Agent/图谱/治理所有路径。
6. 审核事实冲突后分别查全文、BM25、向量与引用，确认都指向生效版本。
7. embedding 断网后导入和更新资料，验证词法可用、退避生效、恢复后向量补齐。
8. 保存过程中继续输入，随后切页、刷新、重开，确认已保存标记与恢复结果真实。
9. A 库打开笔记后切 B 库，分别测试跨库搜索打开、同名链接和悬空链接新建。
10. 关系生成前后的 valid_at/recorded_at 查询与目录过滤同时启用，确认三路召回都守约。
11. 零命中、未评估、部分库未搜索、索引落后分别有明确输出，不能统一包装成“没有知识”或“100% 充分”。
12. 保存 embedding 配置后重启核对模型、维度、配置来源与索引兼容性。

质量集应覆盖真实中文自然问句、专有名词、错误前提、无答案、多库同名、私有资料、过时事实、扫描件及长手册；分别观察召回、引用正确性、拒答与权限。评审本身没有执行这些用例，不能把上述验收计划写成通过记录。

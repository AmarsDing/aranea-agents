# 数字孪生 3D 机房（Sci-Fi Digital Twin Datacenter）方案设计

> 类型：方案设计（design）| 日期：2026-07-26
> 定位：Aranea-Agents 平台的一个**应用方向** —— 以「语音精灵」为通用指令入口，以「数字孪生 3D 机房」为首个落地场景。
> 关联文档：[18-monitor](../development/18-monitor.md)（告警/AI 诊断）、[37-knowledge](../development/37-knowledge.md)（知识库）、[20-skill](../development/20-skill.md)（技能）、[63-tts](../development/63-tts.design.md)（语音合成规划）、[62-overview-command-center](../development/62-overview-command-center.md)（概览指挥台）。

## 1. 概述

### 1.1 目标

构建一个科幻现代化风格的 3D 数字孪生机房监控系统：

1. **主屏四宫格**：每个宫格展示一个机房监控区域内部的 3D 机柜阵列（不含建筑，只有排列整齐的机柜）。
2. **真实机柜建模**：机柜内含服务器、交换机与整齐网线，按真实 42U 机柜规格制作；机柜与设备半透明显示，线缆虚化半透明，选中有高亮效果。
3. **语音精灵指令**：语音下达指令 → LLM 理解 → 视角自动追踪 → 标签展示 → 语音播报，覆盖「区域 → 机柜 → 服务器 → 硬件部件」四级下钻与「库存 / 报告 / 告警 / 自愈」四类业务。
4. **智能告警与自愈**：基于监控数据的根因分析（防误报、防告警风暴），告警可视化追踪，LLM 给出指导性建议并关联知识库与技能；支持审批后的自动治愈与成熟度分级。
5. **报告生成**：按模板由 LLM 汇总运行数据，生成服务器 / 备件 / 整体机房报告。
6. **知识沉淀**：从问题解决过程中沉淀核心技术方案，可追溯、可复用、可逐步降低安全策略实现自动执行。

### 1.2 非目标（Non-Goals）

- 不建模建筑外观、园区、安防摄像头画面 —— 只建模机房内部机柜与设备。
- 不在 Phase 1 实现 UE5 —— UE5 + 3D 数字人为远期方向（§11），本文档只做接口预留。
- 不做真实带外管理（BMC/IPMI 直接控制）—— 所有操作经由 Aranea 平台的 Agent/Skill 体系，受审批与安全策略约束。
- 不替代现有 18-monitor 监控页面 —— 3D 机房是新增的可视化入口，与现有监控页并存。

### 1.3 关键性能指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 语音指令首响 | ≤ 2s（通常），上限 5s | 从语音结束到 LLM 返回首个动作/文本 |
| 视角过渡动画 | 1.2–2.0s | 平滑贝塞尔过渡，不打断用户操作 |
| 3D 帧率 | ≥ 50 FPS（中端 GPU） | InstancedMesh + LOD 保障 |
| 告警到 3D 高亮 | ≤ 1s | WebSocket 推送直达 |
| 四宫格每格机柜规模 | ≤ 200 柜/格（实例化渲染） | 超出自动分页/聚合 |

## 2. 总体架构

### 2.1 分层架构

```
┌─────────────────────────── 呈现层 ───────────────────────────┐
│  Web 端（Quasar + Vue 3）                                     │
│  ├─ DigitalTwinPage（主屏四宫格 + HUD + 语音球）               │
│  ├─ Three.js 渲染器（SceneManager / CameraDirector / 标签层）  │
│  └─ 语音链路（ASR 上传 / TTS 播放 / WebSocket 指令事件）        │
│  远期：UE5 客户端（像素流送 + 3D 数字人，§11）                  │
├─────────────────────────── 平台层 ───────────────────────────┤
│  Aranea 后端（Kratos + trpc-agent-go）                        │
│  ├─ 精灵助手（Spirit）：通用指令入口 + 意图路由                 │
│  ├─ 语音服务：ASR（语音→文本）/ TTS（63-tts 规划落地）          │
│  ├─ 数字孪生服务：Topology / Telemetry / Inventory / Report    │
│  ├─ 告警中心：规则、分级、根因分析、风暴抑制（扩展 18-monitor）  │
│  ├─ 自愈引擎：诊断 → 建议 → 审批 → 执行 → 验证 → 维护日志       │
│  └─ 知识库(37) / 技能(20)：告警处置建议与执行能力来源           │
├─────────────────────────── 感知层 ───────────────────────────┤
│  监控适配层（MetricAdapter 接口）                              │
│  ├─ MockAdapter（演示先行：确定性数据生成器）                   │
│  └─ PrometheusAdapter / SNMPAdapter / IPMIAdapter（后续接入）  │
└──────────────────────────────────────────────────────────────┘
```

**核心原则**：3D 场景只是「一种呈现」。所有指令都先进入精灵助手的统一意图路由（与现有聊天/飞书等渠道一致），数字孪生场景是意图的一类**执行目标（Execution Target）**。这保证语音精灵是通用入口，而非机房专用遥控器。

### 2.2 语音指令全链路与时延预算

```
用户语音 ──▶ 浏览器采集(VAD 端点检测)
        ──▶ ASR 流式识别 ──▶ 文本指令
        ──▶ 精灵助手意图路由（LLM function calling）
        ──▶ ① 场景指令（view.focus_rack 等）──▶ WS 推送前端 ──▶ 3D 视角动作
        ──▶ ② 数据查询（telemetry/report）──▶ 服务层聚合
        ──▶ LLM 生成概要 ──▶ TTS ──▶ 前端语音播报 + 标签展示
```

| 阶段 | 预算 | 手段 |
|------|------|------|
| ASR（流式，边说边出） | ≤ 600ms | 流式识别；句尾即出最终文本 |
| 意图路由（小模型优先） | ≤ 500ms | 意图分类用轻量模型 + function calling；命中缓存模板更快 |
| 数据查询 | ≤ 300ms | 遥测走内存态快照（见 §8.2），不落盘查询 |
| 场景指令下发（WS） | ≤ 100ms | 复用现有 EventBus → WebSocket 链路 |
| TTS 首包 | ≤ 500ms | 流式合成，分段播放；概要文本与播报并行 |
| **合计（首响）** | **≤ 2.0s** | 视角动画与语音播报**并行开始**，不串行等待 |

**降级策略**：TTS 未配置时仅文字标签；ASR 未配置时降级为文本指令输入框 + 快捷指令按钮；LLM 超时返回预设模板响应，保证「指令必有反馈」。

## 3. 视觉设计（符合本项目色调）

### 3.1 色彩体系

项目现有主题为暖色玻璃拟态（`--canvas-base: #FEFBF4`、`--color-accent: #DCA03E` 金、`--q-primary: #4F46E5` 靛蓝）。3D 机房采用**深空模式变体**（科幻场景需要暗底发光），但**沿用项目的品牌色作为发光主色**，保证与整体产品气质一致：

| 用途 | 色值 | 来源 |
|------|------|------|
| 场景底色 | `#0B1020` → `#131B33` 径向渐变 | 深空蓝黑（衍生自靛蓝 #4F46E5） |
| 主发光色（描边/网格/选中） | `#4F46E5` 靛蓝 | `--q-primary` |
| 辅助发光 / 数据流 | `#8B7CFF` 浅靛 | primary 提亮 |
| 强调 / 交互 / 语音球 | `#DCA03E` 金 | `--color-accent` |
| 正常状态 | `#34D399` 绿 | 项目 success 色 |
| 警告 | `#FBBF24` 琥珀 | 项目 warning 色 |
| 严重告警 | `#F87171` 红 | 项目 danger 色 |
| 半透明材质 | 靛蓝基色 + opacity 0.25–0.4 | 呼应 glass 主题变量 |

HUD 面板复用前端 glass 变量（`--glass-elevated`、`--glass-border`），让 2D 面板与 3D 场景在同一套设计语言中。

### 3.2 主屏布局

```
┌──────────────────────────────────────────────────────┐
│ 顶栏：Logo · 全局状态摘要（告警 N · 自愈中 M）· 语音球    │
├────────────┬────────────┬────────────────────────────┤
│ 宫格 A      │ 宫格 B      │  侧边栏（上下文相关）         │
│ 区域-东区   │ 区域-西区   │  · 机柜详情 / 告警卡片       │
├────────────┼────────────┤  · 报告 / 库存 / 维护日志     │
│ 宫格 C      │ 宫格 D      │  · 指令历史                 │
│ 区域-南区   │ 区域-北区   │                            │
└────────────┴────────────┴────────────────────────────┘
```

- 四宫格每格是一个独立 Three.js 视口（共享一个 WebGLRenderer，Scissor 分区域渲染，避免 4 个 GL 上下文）。
- 单击宫格 → 该格聚焦放大（占主区 2/3）；双击 → 全屏该格；ESC 或语音「返回全局」复位。
- 语音球常驻顶栏右侧：待机（金色呼吸）→ 聆听（波纹扩散）→ 思考（旋转）→ 播报（频谱跳动）。

## 4. 3D 场景设计（Three.js）

### 4.1 场景图模型

```
Scene
 └─ Zone（机房区域 ×4，对应四宫格）
     └─ Rack（机柜，InstancedMesh 阵列，行列对齐）
         ├─ RackShell（U 位框架 + 前后玻璃门，半透明）
         ├─ Device[ ]（Server / Switch，按 U 位填充）
         │    └─ Component[ ]（CPU/GPU/内存/电源/风扇/盘，爆炸视图用）
         └─ Cable[ ]（设备 → 交换机，CatmullRom 曲线管）
```

**实体坐标约定**：`ZoneID / RowID / RackID / UPosition / DeviceID / ComponentID` 六级定位，全链路（遥测、告警、库存、报告）共用同一套 ID，保证任何数据都能映射到 3D 对象。

### 4.2 机柜建模（按真实 42U 规格）

- **尺寸**：高 42U（1U = 0.04445m）× 宽 600mm × 深 1000mm；场景内按 1:100 缩放。
- **框架**：U 位立柱 + 横梁，线框材质（`LineSegments`），发光靛蓝描边。
- **外壳/玻璃门**：`MeshPhysicalMaterial`，`transmission: 0.9`（或 `opacity: 0.28` 低性能档），`roughness: 0.15`，让内部设备隐约可见。
- **设备填充**：
  - 服务器（1U/2U）：面板 + 把手 + 状态灯带（左绿右琥珀，运行状态驱动颜色）。
  - 交换机（1U，通常置顶 U42/U41）：端口阵列用 1×48 小方块 InstancedMesh。
  - 状态灯用 `emissive` 材质，支持闪烁动画（告警时红色呼吸）。
- **网线**：按真实走线 —— 每台服务器 2 根（业务 + 管理）上至本柜交换机；`CatmullRomCurve3` + `TubeGeometry`（径向分段 4，控制面数），`opacity: 0.35` 虚化半透明，颜色按链路类型（业务=靛蓝、管理=金）。线缆两端吸附到设备端口点，选中设备时其线缆渐显（opacity → 0.8）并叠加流动虚线动画（`dashOffset` 滚动）。

### 4.3 半透明与选中效果

| 对象 | 常态 | 悬停 | 选中 |
|------|------|------|------|
| 机柜外壳 | opacity 0.28 | 0.45 + 描边提亮 | 0.15（更透，突出内部）+ 外壳发光脉动一次 |
| 设备 | opacity 0.85 | emissive +20% | 金色描边（OutlinePass）+ 状态灯常亮 |
| 线缆 | opacity 0.35 | — | 关联线缆渐显 0.8 + 流动动画 |
| 未选中对象 | — | — | 整体 opacity ×0.4（淡化压暗） |

选中后弹出**跟随标签**（CSS2DRenderer）：设备名称 + 状态徽章（绿/琥珀/红）+ 关键指标一行（CPU/内存/温度）。标签背景色即状态色（见 §6.3）。

### 4.4 性能设计

- **实例化渲染**：机柜框架、服务器面板、交换机端口、线缆全部 `InstancedMesh`；四宫格合计 800 柜 × 20 设备 ≈ 1.6 万实例，DrawCall 控制在 < 50/格。
- **LOD**：全局视角只渲染机柜外壳 + 状态灯带（内部设备剔除）；进入机柜详情才实例化内部设备与线缆。
- **标签层**：CSS2DRenderer 独立于 WebGL，标签数量上限 32，超出聚合为「+N」。
- **按需渲染**：无动画/无数据更新时 `renderOnDemand`，GPU 空闲帧不渲染。

## 5. 语音指令与视角追踪

### 5.1 视角层级状态机

```
GLOBAL（四宫格全局）
  └─ ZONE（单区域聚焦）
      └─ RACK（机柜聚焦：其他柜淡化，标签显示运行概要）
          └─ RACK_DETAIL（左 2D 详情面板 + 右 3D 机柜内部）
              └─ SERVER（服务器聚焦 + 历史曲线）
                  └─ SERVER_EXPLODE（爆炸拆分：CPU/GPU/内存/电源）
```

每次状态迁移由 `CameraDirector` 执行：贝塞尔路径（位置 + 注视点双插值，缓动 `easeInOutCubic`），时长 1.2–2.0s；迁移期间锁定新指令的视角动作（指令仍接收并排队，动作串行执行，防视角打架）。

### 5.2 指令意图表（核心指令集）

| 用户指令（示例） | 意图 | 系统行为 | 语音播报 |
|------------------|------|----------|----------|
| 「查看 A-03 机柜的运行情况」 | `twin.focus_rack` | 视角 → RACK；标签展示运行状态数据 | 播报机柜概要（设备数/告警数/平均负载/温度） |
| 「查看机柜的详细运行情况」 | `twin.rack_detail` | 其他机柜渐隐；左面板详情 + 右 3D 内部；服务器用折线+标签展示名称/操作系统等，标签底色=运行状态 | 播报详情概要 |
| 「查看 3 号服务器的运行状态」 | `twin.focus_server` | 视角 → SERVER；详情 + 历史曲线（CPU/内存/网络/温度，默认 24h） | 播报服务器状态概要 |
| 「服务器硬件详情」 | `twin.explode_server` | 爆炸拆分动画（部件沿轴向分离 + 连线标签：型号/规格） | 播报硬件配置概要 |
| 「CPU 的库存情况」 | `inventory.query` | 切到库存视图（2D 面板为主，3D 中高亮该部件）；低库存触发告警样式 | 播报库存数量与预警 |
| 「把某台服务器最近 30 天运行情况做个报告」 | `report.generate` | 按模板 LLM 汇总 → 报告面板（可导出 PDF/Markdown） | 播报报告结论摘要 |
| 「备件情况做个报告」 / 「整体机房运行情况做报告」 | `report.generate` | 同上，模板不同 | 同上 |
| 「这个问题是怎么解决的」 | `healing.trace` | 追溯解决步骤时间线 → 报告化展示 | 播报问题核心 + 概要解决步骤 |
| 「返回全局」 | `twin.focus_global` | 视角 → GLOBAL | 简短确认 |

**通用性**：意图路由挂在精灵助手上，`twin.*` 只是命名空间之一；用户任何其他指令（如「帮我建个团队」「查一下昨天 token 用量」）仍走原有精灵能力，3D 页面不打断、不抢占。

### 5.3 视角追踪算法（CameraDirector）

- **聚焦定位**：`focusOn(object3D, padding)` —— 计算目标包围盒，求相机球面坐标（方位角保持当前方向、俯角 30°），距离 = `boundingSphere.radius / tan(fov/2) × padding`。
- **过渡**：`position` 与 `target` 各自三次贝塞尔插值；控制点沿当前位置与目标连线的垂直方向偏移，产生弧线运镜感。
- **多目标取景**（告警场景复用，§7.4）：对 N 个目标点求最小包围球；N=1 聚焦，N≤3 且同区域 → 区域级取景，跨区域 → 全局取景并标注。

## 6. 机柜详情与服务器详情（左侧 2D + 右侧 3D）

### 6.1 机柜详情视图（`twin.rack_detail`）

- **左侧面板（2D，glass 风格）**：机柜概要（U 位占用率、功耗、进/出风口温度、告警数）、设备清单表格（U 位 / 名称 / 类型 / OS / 状态）。
- **右侧 3D**：该机柜单独居中，外壳高透，内部设备逐个浮现。
- **服务器标注**：每台服务器引出一根**折线**（leader line：设备 → 拐点 → 标签），标签含名称 + OS + 状态徽章；**标签背景色 = 运行状态**（绿=正常 / 琥珀=警告 / 红=严重 / 灰=离线）。折线按设备 U 位奇偶分左右两侧排布，避免重叠。

### 6.2 服务器详情视图（`twin.focus_server`）

- 3D：服务器从机柜中「抽出」居中，其他设备淡化。
- 2D 面板：基础信息（名称、SN、OS、固件、上架日期）+ 实时指标 + **历史曲线**（CPU/内存/磁盘 IO/网络吞吐/温度，时间窗可选 1h/24h/7d/30d）。

### 6.3 爆炸拆分视图（`twin.explode_server`）

- 动画：上盖滑开 → 部件沿预设轴向分离（CPU/GPU 向上、内存向右、电源向后、风扇向前、硬盘向前抽出），时长 1.6s，缓动回弹。
- 每个部件引出标签：**类别 + 型号 + 规格**（如「CPU · Xeon Platinum 8480+ · 56C/112T 2.0GHz」「GPU · L40S · 48GB」「内存 · DDR5 64G×8 4800MT/s」「电源 · 2000W 钛金 1+1 冗余」）。
- 部件标签附带**库存角标**（如「备件库存 3」），低库存部件标签转琥珀色并链入库存视图（§9）。
- 再次点击或语音「合上」→ 逆动画复位。

## 7. 告警系统（根因定位、防风暴、可视化追踪）

### 7.1 告警数据流

```
MetricAdapter ─▶ 告警评估器（规则引擎，扩展 18-monitor Alerts）
   ─▶ 去重/聚合/抑制 ─▶ 根因分析器 ─▶ AlertEvent（含 rootCause 与拓扑路径）
   ─▶ ① EventBus ─▶ WebSocket ─▶ 3D 场景高亮（≤1s）
   ─▶ ② 通知渠道（Webhook/Channel，复用现有）
   ─▶ ③ 自愈引擎（若命中自愈策略）
```

### 7.2 根因定位与防误报、防风暴（设计要点）

| 机制 | 说明 |
|------|------|
| **拓扑依赖推断** | 基于 §4.1 六级 ID 构建依赖图（网络：服务器→交换机→上联；供电：设备→PDU→UPS）。下游 N 个告警 + 上游 1 个告警 → 判定上游为根因，下游标记 `suppressed_by` |
| **去重 (Dedup)** | 同实体同指标同状态的告警按 fingerprint 合并，计数递增而非新增 |
| **分组 (Grouping)** | 5 分钟窗口内同 Zone/同根因候选的告警聚为一个 Incident，通知只发一次 |
| **抑制 (Inhibition)** | 严重级告警存在时，同链路低级别告警静默（只记录不通知） |
| **静默 (Silence)** | 维护窗口/计划任务期间按标签静默 |
| ** flap 防抖** | 状态 3 分钟内反复切换 ≥3 次 → 标记 `flapping`，暂停通知，保留观察 |
| **多指标佐证** | 单指标超阈不立即告警：要求关联指标佐证（如 CPU 高 + 温度高 + 负载高 三取二）或持续时长达标，防毛刺误报 |

### 7.3 告警配置（Web 端）

每条告警规则可配置：

- **严重等级**：`info / warning / critical`（映射绿/琥珀/红）。
- **动态追踪开关**：开启后，该等级告警触发 3D 场景自动追踪（§7.4）。
- **自动解决开关**：开启后，命中自愈策略时进入自愈闭环（§8），默认**需人工审批**。
- 通知渠道、静默窗口、佐证条件 —— 复用 18-monitor 规则模型扩展字段。

### 7.4 告警 3D 可视化与视角追踪策略

**单告警（动态追踪开启）**：

1. 全局视角 → 所有机柜切换为**虚幻半透明体**（opacity 0.15，去饱和）。
2. 故障点亮起**红色脉冲点**（shader 呼吸 + 扩散环）。
3. 视角**逐级定位**：全局 → 区域（0.8s）→ 机柜（0.8s）→ 服务器（0.6s），每级停留一拍让用户感知路径；到位后弹出告警卡片（指标、阈值、当前值、根因推断、建议摘要）。
4. 若启用自动解决：卡片内显示「LLM 分析中 → 根因 → 方案 → 待审批 → 执行中 → 验证中 → 已恢复」的自愈流水线状态。

**多告警（告警风暴）**：

- **视角停留全局**，不切聚焦 —— 全局虚幻半透明，所有故障点红色脉冲。
- 每个故障点生成**问题卡片**（3D 场景内 billboard）：实体名 + 核心症状 + 自愈进度条；卡片有最小尺寸保证可读，数量多时**允许相互遮挡**，按严重度排序前后（critical 永远最前），hover/点击可置顶放大。
- 每个告警点**独立自愈**：卡片实时显示「分析 → 审批 → 执行 → 自检」进度；**自检通过后卡片变绿，1.5s 后自动收缩关闭**。
- **视角再收敛算法**（告警减少时）：每当卡片关闭，重新评估剩余告警点 —
  - 剩 0：视角回到标准全局位，全场恢复常态材质；
  - 剩 1–2 个且**在同一区域/同一机柜**：视角平滑定位到该区域（包围球取景，padding 1.3）；
  - 剩余**跨区域**：保持全局取景，但相机自动调整到能同时看到所有红点的最佳视角（最小包围球 + 方位角选择使点间屏幕距离最大），保证用户最大程度看到全部告警信息。

### 7.5 告警与知识库、技能的关联

- 告警生成时，以「告警类型 + 实体型号 + 症状指纹」检索**知识库（37）**：命中 → 卡片展示「历史处置经验 / 官方手册章节」摘要与链接。
- 匹配**技能（20）**：处置动作（重启服务、切换备用链路、清理磁盘、扩容）映射为可执行 Skill；自愈方案 = LLM 基于知识库经验 + 可用 Skill 编排出的步骤序列。

## 8. 自愈闭环与知识沉淀

### 8.1 自愈闭环（Healing Loop）

```
检测(AlertEvent) → 诊断(LLM 根因分析：监控数据+拓扑+知识库)
  → 方案(步骤序列，每步标注：使用 Skill / 风险等级 / 回滚动作)
  → 审批(默认人工确认；成熟方案可自动，见 8.3)
  → 执行(Agent 调 Skill 逐步执行，全程事件流可见)
  → 验证(指标回归检查 + 自检脚本，持续观察窗 5–15min)
  → 汇报(语音 + 卡片 + 通知) → 维护日志(HealingRecord 落库)
```

- 执行中 3D 卡片实时显示步骤进度；任一步失败 → 自动回滚已执行步骤 → 卡片转红并升级通知。
- **全程历史记录**：检测快照、诊断推理摘要、审批人/时间、每步执行参数与输出、验证数据、结论 —— 落库 `healing_records`，不可篡改（只追加）。

### 8.2 知识沉淀（从解决到方案库）

- 自愈成功后，LLM 将过程**总结为核心技术方案**（症状指纹 → 根因 → 标准处置步骤 → 验证条件），写入方案库（知识库的 `solution` 命名空间）。
- 下次同类告警（症状指纹相似度 ≥ 阈值）→ 直接命中方案，跳过全量诊断，**实现自动治愈**。

### 8.3 成熟度与安全策略降级

| 成熟度 | 条件 | 安全策略 |
|--------|------|----------|
| L0 新方案 | 首次生成 | 仅展示建议，必须人工执行 |
| L1 验证中 | 人工执行成功 ≥1 次 | 自愈执行前必须审批 |
| L2 可信 | 审批执行成功 ≥3 次、回滚率 0 | 低风险动作自动执行 + 事后通知；高风险仍需审批 |
| L3 自治 | 连续成功 ≥10 次、观察期 30 天无事故 | 全部自动执行（仍受动作风险白名单约束） |

降级由管理员在「自愈方案管理」页审核操作；所有成熟度变更进审计日志。

### 8.4 指令：问题追溯

用户问「某问题是怎么解决的」→ `healing.trace`：按时间线回放 HealingRecord（检测→诊断→步骤→验证），生成追溯报告；语音播报「问题核心 + 概要解决步骤」（控制在 3–5 句）。

## 9. 库存与备件

- **备件台账**：`spare_parts`（类别 / 型号 / 规格 / 数量 / 存放位置 / 关联设备型号）。爆炸视图部件标签直接显示库存角标。
- **库存作为告警的一类**：`low_stock` 告警规则（数量 ≤ 安全库存 → warning；=0 → critical），走同一告警管道（§7），3D 中表现为部件级琥珀/红角标，支持动态追踪定位到「使用该部件的设备」。
- **备件报告**：`report.generate(spare_parts)` —— 消耗趋势、低库存清单、采购建议（LLM 汇总）。

## 10. 报告系统

| 报告类型 | 触发指令 | 数据来源 | 模板要点 |
|----------|----------|----------|----------|
| 服务器 30 天运行报告 | 「把某台服务器最近 30 天运行情况做个报告」 | 遥测历史 + 告警记录 + 维护日志 | 可用率、负载/温度趋势、告警 TOP、事件时间线、健康评分与建议 |
| 备件报告 | 「备件情况做个报告」 | 库存台账 + 更换记录 | 库存水位、消耗趋势、低库存预警、采购建议 |
| 整体机房运行报告 | 「整体机房运行情况做个报告」 | 全量聚合 | 区域/机柜可用率、容量（U 位/电力/制冷）、告警统计与根因分布、自愈成效（次数/MTTR/自动化率）、下月建议 |

- **模板机制**：Markdown 模板 + 数据槽位；LLM 负责「数据 → 洞察」的叙述层，数值一律来自结构化查询（防幻觉），关键数字由模板直接填充不经过 LLM。
- 产物：面板内渲染 + 可导出 Markdown/PDF；报告生成记录落库可追溯。

## 16. 风险与权衡

| 风险 | 影响 | 缓解 |
|------|------|------|
| 万级实例渲染性能 | 帧率下降 | LOD + 实例化 + 按需渲染；超规模自动聚合 |
| LLM 报告数值幻觉 | 报告失真 | 数值模板直填，LLM 只写叙述层；生成后校验数值一致性 |
| 自愈误操作 | 生产事故 | 默认人工审批；动作风险白名单；每步带回滚；成熟度渐进 |
| 告警风暴淹没 UI | 不可读 | §7.2 五级抑制 + 卡片遮挡与严重度排序 + 全局停留策略 |
| 语音链路厂商依赖 | 锁定 | ASR/TTS 抽象为 Provider 接口（对齐 9-provider 体系），可替换 |
| Three.js 与 UE5 双端漂移 | 维护成本 | 共享协议与 ID 体系；UE5 仅展示端，功能子集 |

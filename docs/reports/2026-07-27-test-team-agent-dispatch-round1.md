## 四、发现的问题

### P1【派遣准确性】小红书子任务未匹配到小红书运营专家 — 中

- **证据**：日志 `DAG 模式：为子任务分配多成员团队 lead=__dept_lead_media_operations__`（小红书子任务）；同时段日志 `Layer 2 embedding 失败，降级为 TF-IDF / embedder not configured`
- **根因**：测试环境未配置知识 embedder → Layer 2 语义匹配降级为 TF-IDF 关键词匹配 → 匹配质量下降；且该子任务文本与「小红书运营专家」能力描述的关键词重叠度不足时，部门主管（能力描述宽泛）得分反超
- **影响**：领域专家闲置，非专家产出专业方案，业务质量风险

### P2【能力空白】精灵不会从团队库选择已有团队 — 高（核心发现）

- **现象**：预置的 3 个测试团队（含"正好"的 standard 团队）完全未被考虑，精灵一律新建团队
- **代码证据**：`internal/biz/spirit_team_usecase.go:584 findReusableTeam` 仅查询**同一 spirit 会话内**、同 task_description/dag_node_id、非终态的团队 —— 设计上只是防重去重（Issue 5），**不是团队库选择**；全代码库无其他库选择路径；精灵系统提示词为「自动组装团队并委派工作」，无团队库感知
- **结论**：用户期望的"不指明 team → 派遣到已有正好团队"能力**当前架构不存在**。场景 2/3（多/少 agent 团队选择）在当前架构下必然复现同一结果，属能力空白而非实现 bug，需先立项实现再重测

### P3【状态一致性】team_stages_v2 状态滞留 running — 中

- **证据**：任务完成后，`team_stages_v2` 3 行仍 `status=running, stage=executing`；且 stage 2/3 的 `dag_node_id` 为空、`members` 为 NULL；而 `team_runs_v2` 3 条全部 completed
- **影响**：依赖 team_stages_v2 的查询（孤儿恢复、部分统计）会误判任务仍在执行；重启后孤儿恢复机制可能误处理

### P4【前端一致性】聊天 URL 的 session 参数与实际会话不一致 — 高

- **证据**：测试时地址栏为 `session=d78029b9`（旧会话「帮我做个方案」，医疗云任务），但新任务实际创建会话 `49dd810d`（sessions 表证实两者独立）；测试当时页面显示新会话内容（WebSocket 驱动），**重新加载该 URL 后显示的是旧医疗云会话**
- **影响**：刷新/分享链接会打开错误会话；用户无法可靠收藏对话；自动化测试与人工复查被误导

### P5【工具健壮性】write_file 执行失败一次 — 低

- **证据**：日志 `tool execute failed, function name: write_file`（部门主管-专项服务部，16:43:00）；随后策略师改用 `file_save_file` 成功落盘
- **影响**：本轮自愈，未影响交付；但工具命名双轨（write_file / file_save_file）易混淆 agent

### P6【测试环境】测试后端被外部因素终止 — 低（环境）

- **证据**：日志 01:00:42 干净截断，无 panic/fatal；端口 18000 拒绝连接
- **结论**：应用无崩溃，系外部进程管理干扰；已通过重启脚本恢复，后续关注是否需要进程守护

## 五、解决方案（系统 / 用户体验 / 业务三视角）

### P2 团队库选择能力（核心，需评审后立项）

| 视角 | 方案 |
|------|------|
| 系统 | 在 Allocate 阶段新增 **Layer 0：团队库匹配**——先对 subtask 与 active 团队库（display_name + definition_json 描述 + 成员能力集）做语义/关键词匹配，命中阈值（如 ≥0.75）则直接派遣已有团队（复用其 team_session 或基于定义重建成员会话）；未命中再走现有组装路径。匹配候选与得分落入 AllocationPlan.MatchReason 供审计 |
| 体验 | 命中已有团队时，精灵回复中明示「已为您派遣已有团队：社媒运营测试团队-标准（3 名成员）」，团队卡片标注「已有团队」徽标；未命中时说明「为您新建团队」 |
| 业务 | 团队库成为可复用资产：稳定团队沉淀领域知识与协作记忆，减少重复组建成本；"正好/超员/缺员"选择由匹配分数 + 成员覆盖率共同决定，缺员团队命中时精灵应提示「该团队缺少小红书专家，是否补充？」 |

### P1 派遣准确性

| 视角 | 方案 |
|------|------|
| 系统 | ① 测试/生产环境补齐 embedder 配置（memory 模块 UI 配置 provider/base_url/api_key），恢复 Layer 2 语义匹配；② TF-IDF 降级路径增加 agent **display_name 精确包含**加权（任务文本含「小红书」时 `小红书运营专家` 应显著加分）；③ 部门主管类宽泛能力 agent 在专家命中时降权（lead 优先专家，主管仅作 supervisor 附加） |
| 体验 | 派遣结果在 UI 可解释：团队卡片 hover 显示「为什么选他」（MatchReason 透出） |
| 业务 | 建立派遣准确率度量：按域统计专家命中率，纳入 monitor 指标 |

### P3 状态一致性

| 视角 | 方案 |
|------|------|
| 系统 | 修复 team_stages_v2 写路径：team_run 终态时同事务更新对应 team_stage（status/dag_node_id/members）；启动孤儿恢复把「run 已终态但 stage 滞留 running」的 stage 对齐为 run 状态 |
| 体验 | 消除 UI 潜在的状态闪烁（流程图节点状态以 stage 为准时不会卡在执行中） |
| 业务 | 保证审计与统计口径一致（stage 与 run 同源同终态） |

### P4 会话 URL 一致性

| 视角 | 方案 |
|------|------|
| 系统 | 前端：新会话创建成功后 `router.replace` 更新地址栏 session 参数；加载时以 URL session 为准强制刷新 store，避免旧会话渲染新数据 |
| 体验 | 刷新/分享链接始终打开当前对话；左侧会话列表高亮与地址栏一致 |
| 业务 | 保证会话可回溯、可分享，是协作产品的基础契约 |

### P5 工具命名

| 视角 | 方案 |
|------|------|
| 系统 | 收敛文件写工具为单一入口（保留 file_save_file，write_file 设别名或下线），减少 agent 选择困惑 |
| 业务 | 降低工具失败率与 token 浪费 |

### P6 测试环境守护

| 视角 | 方案 |
|------|------|
| 系统 | 为测试后端加 `start /b` + 守护循环或 nssm 服务化；测试报告记录环境中断事件 |
| 业务 | 保障多轮回归测试连续性 |

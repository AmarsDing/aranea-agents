# 评审报告：知识库核心能否长期给 Agent 干活（2026-08-15）

> 日期：2026-08-15 | 类型：review | 状态：对照代码，不以三件套自称当事实
> 合格线：常年累计、知识关联、知识更新。**不评**插件、市场、主题、移动端、Canvas。
> 对象：模块 37 Knowledge 作为 Agent 的知识底座（入库 / 索引 / 检索注入 / 写回 / 文档更新）
> 前序：[2026-08-15-review-knowledge-vs-obsidian.md](./2026-08-15-review-knowledge-vs-obsidian.md)（口径已过时，仅作 PKM 壳对照）

---

## 1. 先给结论

**现在能当「可检索的文档库」给 Agent 用，还不能当「会自己保持正确的知识库」用上好几年。**

三条拆开看：

| 能力 | 现在 | 常年能否干活 |
|------|------|----------------|
| 累计 | 人写入库 + vault 同步 + 会话过门写进日记，都能进 PG chunks 被搜到 | **能堆**。堆的是日志和页面，不是「当前为真」的知识集 |
| 关联 | `[[wikilink]]` → `knowledge_links` → 检索一跳扩展，已接上 Agent 预检索 | **能跳一层**。标题对不上文件名就几乎没有边 |
| 更新 | 文档级：保存 CAS、watcher 重索引、重嵌入、重建块索引 | **页面能改**。事实不能作废、不能替换、不能从日记晋升成正文 |

Agent 侧今天的供粮路径是：首轮用户问题预检索 top-4（每段最多 280 字、2 秒超时）写进 `## Retrieved Knowledge`；不够再让模型调 `knowledge_search` / `knowledge_reflect`。没有 `knowledge_write`。会话沉淀是 AutoMemory 的副作用，不是 Agent 主动维护知识。

---

## 2. 累计：能进库，进的是流水账

**已经接通的写入口**

- 人：工作台编辑、粘贴入库、文件同步（local vault `VaultSyncApplier.ApplyOne` 改文件就重建 chunks + 块索引）。
- Agent 间接：AutoMemory 过门（kind 白名单 ∩ ≥0.85 ∩ ≥8 字）追加 `inbox/writeback-YYYY-MM-DD.md`；0.60–0.84 进 pending，人勾选后再写。
- 去重：同一日记正文里相同 `fact_id` 或相同陈述不重复追加。
- 检索：词法 + 向量（有语义层时）+ AdaptiveRouter 上的 GraphExpander；联邦检索走同一 Router，一跳在 Agent 路径上。

**常年会坏的地方**

1. **写回是按日追加，不是维护词条。** 一年约 365 篇日记。2026 年写「必须双人值守」，2028 年写「夜班改单人」，两篇同等可被检索命中，没有 valid_to、没有作废、没有「以哪篇为准」。
2. **去重键太窄。** 换一个 `fact_id`、换一种措辞，同一约束会再进一篇。没有语义合并。
3. **inbox 不会自动变成正文。** 晋升（Promote）是人把整篇文档推到团队库的动作，不是「日记里的事实晋升成 `值班制度.md`」。Agent 常年喝到的是收件箱碎片 + 人整理过的页面，两套东西平权。
4. **预检索窗口极窄。** 4 段 × 280 字。库越大，首轮命中「当前有效的那条」的概率越靠检索排序，而排序没有时间衰减、没有「已作废」过滤。
5. **G1 投影**（`agents/{id}.md` 覆盖写）是当前快照，方向对；日记写回是相反方向（只增不改）。

所以「能累计」成立；「累计之后仍然是一份能信的知识」不成立。

---

## 3. 关联：一跳是真的，粮不够密

**已经接通**

- 写时把正文里等于**文件名 basename** 的提及编成 `[[wikilink]]`（ingest/保存自动；存量要显式回填）。
- 块级 refs + `knowledge_links`（explicit / entity / semantic）。
- 查询时 GraphExpander：种子文档最多 5 个，邻居最多 8，explicit×3 > entity×2 > semantic×1，邻文档各取 2 chunk，800ms 超时；即时定位查询跳过。
- 金标（假图、不连 PG）证明：成链后一跳能拿到邻文档事实，纯混合种子拿不到。
- 给人看的：反链、出链、未链接提及、dangling、3D 图。这些对 Agent 供粮的贡献，主要是边被物化进 `knowledge_links`。

**常年会空的地方**

1. **边几乎只认文件名。** `duty-rota.md` 对不上「值班制度」。frontmatter aliases 在解析键里有口子，成链匹配没用上。真实库文件名习惯会让图长期稀疏。
2. **只有一跳。** 手册 → 值班制度 可以；手册 → 值班制度 → 机房门禁 不会在一次检索里走完。
3. **没有「事实↔事实」边。** 日记里两条 provenance 块不会互链，除非陈述里恰好出现某篇标题。
4. **入库期 NER 没做**，entity 边不会自己变密。

关联能力对 Agent 有用的前提是：人（或回填）已经把标题写成可匹配的名字，并且相关知识在相邻一跳之内。这够撑「小而整理过的团队库」，不够撑「几年流水账自己长出一张网」。

---

## 4. 更新：改得了页面，改不了「这条知识过时了」

**文档级更新（这层是齐的）**

- 保存：`UpdateDocumentContent` + CAS（`base_hash`），冲突不覆盖。
- local：watcher → `ApplyOne` → 删旧 chunks、重切、按需重嵌入、`RebuildBlockIndex`。
- 语义层：单文档重嵌入、整库启用语义。
- 派生索引：重建块/refs **不再**顺便改 Markdown。
- 删除/移动：镜像删除或改 rel_path，chunks 随文档走。

**知识级更新（这层是空的）**

| 应有行为 | 代码 |
|----------|------|
| 新事实替换旧事实 | 无。只追加 |
| 声明某条作废 | 无 valid_to / superseded_by |
| Agent 主动写回指定词条 | 无 `knowledge_write`；只有 AutoMemory 副作用写日记 |
| 检索默认用「当前有效」 | 无。旧日记与新日记同等召回 |
| 改一页之后图边跟着对 | 有（整文档重插 blocks/refs） |

人可以打开 `值班制度.md` 改正文，索引会跟上——这是知识更新里**唯一可靠的路径**。Agent 和自动写回都不会走这条路径去修订词条。

---

## 5. 对 Agent 而言「能干活」的最低定义

不是 Obsidian，也不是 GraphRAG 论文。三句话：

1. **问到的时候能拿到现在仍有效的段落**（不是三年前那条反话）。
2. **相关页能顺着链多拿到一跳**（标题对得上）。
3. **人改了正文、或后来纠正了事实，下次检索不再把旧句当真理。**

今天：2 在整理过的库上成立；1 和 3 只在「人维护的 Markdown 词条」上成立，在自动日记上不成立。

---

## 6. 若只补核心，只值得做这三刀（仍然不是愿望清单）

外围（插件/市场/主题）不要做。下面三刀直接对准「常年供粮」：

1. **词条优先于日记。** 高置信写回默认 upsert 到 `agents/` 或按 kind 落到已有标题页（匹配文件名/aliases）；日记只保留 provenance 流水。没有这一刀，累计越久检索越脏。
2. **别名参与成链与跳转。** frontmatter `aliases` / `title` 与 basename 同等作为提及键。没有这一刀，关联网长不出来。
3. **事实可替换。** 同一 `(kind, 归一化陈述或同一 fact_id)` 再写入时更新旧块并留下 superseded；检索默认过滤已替换。没有这一刀，更新能力永远停在「改文件」。

这三刀之后，才谈得上「真正能干活的知识库」。现在不要用「已经有写回和一跳」代替这三刀。

# Skill: 游戏服务端架构

## 概述
游戏服务端的架构模式、状态同步、网络协议、数据持久化、扩展性与安全规范。目标是构建低延迟、高并发、可扩展的游戏服务端系统。

## 核心规则

### 1. 架构模式
- ECS（Entity-Component-System）适合大量同类实体：逻辑在 System 中，Entity 只是 ID + Component 组合
- Actor Model 适合天然隔离的实体：每个玩家/NPC 是独立 Actor，通过消息通信，无共享状态
- 微服务适合独立部署的子系统：匹配、聊天、排行榜按服务拆分，服务内可用 ECS/Actor
- 选型决策：单服同屏 ≤ 千级用 ECS，逻辑强隔离用 Actor，跨团队独立迭代用微服务
- 禁止混合范式在同一进程内：ECS 的 System 不要直接操作 Actor 状态
- 网关层统一接入：客户端连接网关，网关路由到逻辑服，逻辑服不直接暴露

### 2. 状态同步
- 帧同步：确定性逻辑 + 输入广播，适合 RTS/格斗，要求浮点确定性或定点数运算
- 状态同步：服务端权威状态 + 增量下发，适合 MMO/FPS，客户端做插值渲染
- 增量同步：只发送变化字段，使用字段掩码或变更集，减少带宽
- 插值与平滑：客户端使用插值缓冲（Interpolation Buffer）消除网络抖动
- 预测回滚：客户端预测操作结果，服务端纠正时回滚重放，减少感知延迟
- 同步频率按业务分级：位置 20-60Hz、属性变化即时、聊天走独立通道
- 断线重连：服务端保留最近 N 帧状态快照，重连后追赶而非全量重发

### 3. 网络协议
- 实时游戏使用可靠 UDP（KCP / ENet），非实时用 TCP/WebSocket
- 序列化优先 Protobuf：跨语言、向后兼容、二进制紧凑
- 超低延迟场景考虑 FlatBuffers：零拷贝反序列化，适合帧同步
- 协议版本化：每个消息携带协议版本号，支持灰度升级
- 心跳机制：客户端 5s 心跳，服务端 15s 超时断开，重连走 token 验证
- 消息压缩：大包体使用 LZ4/Zstd 压缩，小包体不压缩（压缩开销 > 收益）
- 帧同步消息必须全量广播到所有参与者，不可丢弃

### 4. 数据持久化
- 热数据在 Redis，冷数据在 DB：在线玩家状态 Redis，离线后异步落库
- 定时快照：每隔 N 分钟将内存状态快照到 Redis/DB，崩溃恢复有界
- Write-Behind 模式：写操作先到内存 + WAL，异步批量刷盘，不阻塞游戏循环
- 关键操作（充值、交易）同步写 DB：保证一致性，不走 Write-Behind
- 数据版本号：每条记录带版本号，乐观锁防并发覆盖
- 合服/迁移：玩家数据自包含（不引用服内 ID），支持跨服迁移
- 归档策略：离线超过 N 天的玩家数据归档到冷存储

### 5. 扩展性
- 分区/分服：按地理/玩法分区，单服承载有上限（ECS 万级实体/Actor 千级）
- 跨服通信：跨服消息走消息队列（Kafka/NATS），不直接 RPC 同步调用
- 动态扩缩容：无状态网关可水平扩展，有状态逻辑服需状态迁移后扩缩
- 热更新：逻辑层使用脚本（Lua/JS）或热加载机制，不停服更新玩法
- 配置驱动：数值/规则由配置表驱动，代码只实现通用引擎逻辑
- 背压控制：下游过载时上游降频/丢帧，不级联崩溃

### 6. 安全
- 服务端权威：所有关键逻辑在服务端执行，客户端只发操作意图
- 反作弊校验：移动速度/攻击频率/资源产出服务端校验，超阈值踢出
- 输入验证：所有客户端输入在服务端校验范围和合法性
- 速率限制：每玩家每秒操作数上限，防刷协议和 CC 攻击
- 协议加密：关键消息加密（AES + 动态密钥），防抓包篡改
- 日志审计：敏感操作（交易、充值、GM 指令）记录不可篡改审计日志
- 防重放：请求携带递增序列号 + 时间戳，服务端校验

## 反模式（禁止）

- 单点状态：关键状态只存在一个进程内存，崩溃即丢失
- 同步 IO 在游戏主循环：数据库/网络 IO 阻塞游戏 tick，导致全服卡顿
- 信任客户端：客户端发送"我击杀了 Boss"，服务端不校验直接结算
- 无版本协议：协议字段增删不兼容，客户端升级后老服务端无法解析
- 全量状态同步：每帧发送完整状态，带宽随实体数线性增长
- 共享内存跨服通信：破坏隔离性，一个服崩溃影响其他服
- 硬编码数值在代码中：无法热更新，每次调参需重新编译部署

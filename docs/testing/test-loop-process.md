# 测试闭环流程：开发 → 测试 → 优化 → 再测试 → 发布

> 版本：1.0 | 日期：2026-05-30

---

## 1. 流程总览

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  开发     │───→│  测试     │───→│  报告     │───→│  优化修复  │───→│  再测试   │
│ Develop  │    │ Test     │    │ Report   │    │ Fix      │    │ Retest   │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └────┬─────┘
     ↑                                                              │
     │                    全部通过                                   │
     │              ┌──────────────┐                                │
     │              │   发布        │←───────────────────────────────┘
     │              │  Release     │
     │              └──────┬───────┘
     │                     │
     └─────────────────────┘  新需求/回归
```

## 2. 阶段详解

### 2.1 开发阶段（Develop）

**输入**：需求文档（`docs/需求/*.md`）

**活动**：
1. 读取需求 + 架构蓝图 + 模块交叉参考
2. 编码实现
3. 编写/更新对应测试用例
4. 本地快速验证

**输出**：代码变更 + 测试代码

**AI 职责**：
- 编码时遵循 `aranea-coding-guide` / `aranea-frontend-guide` SKILL
- 自动生成配套测试用例
- 本地运行 `go test` / `pnpm test` 快速验证

### 2.2 测试阶段（Test）

**输入**：代码变更

**活动**：按 L1→L5 分层执行测试

#### 自动化测试执行顺序

```
Step 1: L1 单元测试
  → make test (Go)
  → pnpm test (前端)

Step 2: L2 业务逻辑测试
  → go test ./internal/biz/... -count=1
  → go test ./internal/runtime/... -count=1
  → go test ./internal/service/... -count=1

Step 3: L3 API 接口测试
  → go test ./internal/server/... -count=1
  → make check-overlay

Step 4: L4 集成测试（需环境）
  → go test ./internal/team/... -run TestE2E -count=1
  → go test ./internal/server/... -run TestE2E -count=1

Step 5: 代码质量门禁
  → make lint
  → make wire-clean
  → make proto-clean
  → pnpm check:layer

Step 6: L5 端到端验收（人工）
  → 按用户旅程表逐项验证
```

**输出**：原始测试结果

**AI 职责**：
- 自动执行 Step 1-5
- 收集所有测试输出
- 标记失败项

### 2.3 报告阶段（Report）

**输入**：原始测试结果

**活动**：
1. 解析测试输出
2. 按模板生成结构化报告
3. 分类：PASS / FAIL / SKIP / ERROR
4. 失败项根因分析

**输出**：测试报告（`docs/testing/reports/report-YYYYMMDD-HHMMSS.md`）

**AI 职责**：
- 自动解析测试输出
- 自动生成报告
- 自动进行根因分析
- 自动标记修复优先级

### 2.4 优化修复阶段（Fix）

**输入**：测试报告中的 FAIL/ERROR 项

**活动**：
1. 根据根因分析定位代码
2. 实施修复
3. 验证修复（仅失败项）

**输出**：修复代码

**AI 职责**：
- 自动定位失败原因
- 自动实施修复
- 自动运行失败项的回归测试
- 修复后更新报告状态

### 2.5 再测试阶段（Retest）

**输入**：修复后的代码

**活动**：
1. 运行全量测试（确保修复无回归）
2. 重点关注之前失败的区域
3. 生成最终报告

**输出**：最终测试报告

**判定**：
- 全部 PASS → 进入发布阶段
- 仍有 FAIL → 回到优化修复阶段
- 连续 3 轮仍有 FAIL → 标记为阻塞，需人工介入

### 2.6 发布阶段（Release）

**输入**：最终测试报告（全部 PASS）

**活动**：
1. 确认所有门禁通过
2. 生成发布说明
3. 提交代码

**门禁清单**：
- [ ] `make test` 全部 PASS
- [ ] `make lint` 0 errors
- [ ] `make smoke` 编译成功
- [ ] `make wire-clean` 无 diff
- [ ] `make proto-clean` 无 diff
- [ ] `pnpm test` 全部 PASS
- [ ] `pnpm lint` 0 errors
- [ ] `pnpm build` 构建成功
- [ ] `pnpm check:layer` 0 violations
- [ ] 覆盖率 ≥ 40%
- [ ] 无 P0/P1 级遗留缺陷

## 3. AI 自动化闭环规则

### 3.1 自动修复循环

```
最大循环次数: 3
每轮操作:
  1. 运行测试 → 收集结果
  2. 分析失败 → 定位根因
  3. 实施修复 → 验证修复
  4. 更新报告

退出条件:
  - 全部 PASS → 进入发布
  - 达到最大循环次数 → 生成阻塞报告，请求人工
  - 同一错误连续出现 2 次 → 标记为顽固问题，请求人工
```

### 3.2 修复优先级

| 优先级 | 条件 | 处理 |
|--------|------|------|
| P0 | 编译失败 / panic | 立即修复，阻塞发布 |
| P1 | 核心业务逻辑失败 | 本轮必须修复 |
| P2 | 非核心功能失败 | 可降级到下轮 |
| P3 | Lint 警告 / 风格问题 | 批量修复 |

### 3.3 回归保护

- 每次修复后必须运行全量测试（不仅是失败项）
- 修复代码不得引入新的测试失败
- 修复不得降低覆盖率

## 4. 报告存档规则

| 规则 | 说明 |
|------|------|
| 命名格式 | `report-YYYYMMDD-HHMMSS.md` |
| 存放路径 | `docs/testing/reports/` |
| 保留策略 | 最近 10 份报告保留，更早的可归档 |
| 对比分析 | 新报告与上一份对比，展示改善/退化 |

## 5. 指标追踪

| 指标 | 目标 | 采集方式 |
|------|------|---------|
| 测试通过率 | ≥ 99% | 报告统计 |
| 覆盖率 | M3:40% → M4:60% → M5:70% | `go test -cover` / `vitest --coverage` |
| 平均修复轮次 | ≤ 1.5 | 报告统计 |
| P0 缺陷数 | 0 | 报告统计 |
| Lint 错误数 | 0 | `make lint` 输出 |

# 代码审查维度检查清单

> **文档地位**：12 维度 × 双面卡片（A 面=编码预防，B 面=Review 检查）。与 `project_rules.md` 红线 + 编程规范互补。
> **使用方式**：按变更范围动态加载维度（见 `project_rules.md` §九），不做无差别全量审查。

---

## 维度加载规则

| 变更范围 | 必查维度 |
|----------|----------|
| 所有变更 | 1（架构）、2（质量）、3（正确性）、8（错误处理） |
| 涉及 DB | + 4（性能） |
| 涉及外部输入/API | + 5（安全） |
| 涉及 Usecase | + 6（可测试性）、11（业务逻辑） |
| 涉及跨模块 | + 7（可维护性）、12（文档同步） |
| 涉及前端 | + 9（前端性能）、10（前端安全） |

## 维度 1：架构设计

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| 依赖方向向内 | `api → service → biz → data`，跨层只允许向内依赖 |
| 红线 #1-3 | biz 不 import trpc-agent-go/proto；server 不 new Runner |
| 红线 #4-5 | Service 不写业务逻辑；Server 不写业务路由 |
| 红线 #7 | 跨模块通过 biz 级窄接口，不持有对方 Service 具体类型 |
| 红线 #13 | Service 不直接依赖 Repo，通过 Usecase 层 |
| 端口-适配器 | 接口定义在 biz（端口），实现在 data（适配器），Wire 绑定在 Service |
| 扩展点预留 | 新增能力用接口+工厂模式，不硬编码具体实现 |
| Agent 运行时 | A1-A6 铁律：Agent 接口 5 方法、事件走 agent.EmitEvent、工具用 NewFunctionTool |

### B 面：Review 检查

- □ 依赖方向是否违反？（biz import data/service/trpc-agent-go/proto？）
- □ Service 层是否有业务逻辑？（if/for 超出映射转换？）
- □ 跨模块调用是否通过窄接口？（是否持有对方 Service 完整类型？）
- □ 新增能力是否预留了扩展点？（硬编码 vs 接口+工厂？）
- □ 模块间是否存在循环依赖？
- □ Agent 运行时是否合规？（A1-A6 铁律逐项检查）

## 维度 2：代码质量与风格

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| CS-B5 | 函数体不超过 80 行，超过必须拆分 |
| CS-B6 | 圈复杂度不超过 15，超过必须简化分支 |
| CS-B7 | 参数列表不超过 5 个，超过用 Option struct |
| CS-B8 | 禁止魔法数字，必须定义命名常量 |
| CS-F4 | 组件 props 必须有 TypeScript 类型定义 |
| CS-F6 | 禁止 `any` 类型，必须用具体类型或泛型 |
| CS-F7 | 事件处理器命名：`onXxx` |
| 命名规范 | 包名小写、结构体大驼峰、函数大驼峰导出/小驼峰内部、错误变量 Err 前缀 |
| 无死代码 | CS-B2：不得新增已无调用者的 deprecated 方法 |

### B 面：Review 检查

- □ 是否存在超过 80 行的函数？（应拆分）
- □ 是否存在圈复杂度 > 15 的函数？（应简化）
- □ 参数列表是否超过 5 个？（应用 Option struct）
- □ 是否有魔法数字？（应定义命名常量）
- □ 命名是否表意清晰？（变量/函数/类型命名）
- □ 是否有重复代码？（应提取公共函数/组件）
- □ 是否有死代码？（未使用的 import/变量/函数）
- □ 前端：是否有 `any` 类型？（应替换为具体类型）
- □ 前端：props 是否有类型定义？

## 维度 3：功能正确性

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| 边界条件 | 空值、零值、空切片、nil 指针必须显式处理 |
| 错误路径 | CS-B14：错误路径必须有测试用例覆盖 |
| 幂等性 | CS-B16：写操作必须保证幂等 |
| 前端消息分组 | 红线 #15：禁止 turn_index，用堆栈模型 |
| Proto 完整性 | 红线 #6：对外能力必须在 proto 中印全 |

### B 面：Review 检查

- □ 空值/nil 是否正确处理？（有无 nil pointer 风险？）
- □ 边界条件是否覆盖？（空切片、零值、极值？）
- □ 所有 if/else 分支是否正确？（有无遗漏分支？）
- □ 并发场景是否有竞态条件？（map 并发读写、slice 并发 append？）
- □ 数据库操作是否保证一致性？（事务、CAS？）
- □ 写操作是否幂等？（相同请求是否产生相同结果？）
- □ 前端：消息分组是否用堆栈模型？（是否误用 turn_index？）

## 维度 4：性能与资源效率（后端）

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| CS-B9 | 数据库查询必须带 `context` 超时 |
| CS-B10 | 循环内禁止逐条 DB 操作，必须批量 |
| Ent 优化 | 查询用 `.Select()` 限制返回字段；大列表用分页 |
| 读写分离 | 读操作用 `readClient(ctx)`，写操作用 `txClient(ctx)` |
| 连接收口 | 红线 #11：不得在 NewData 外另开 SQLite 连接 |

### B 面：Review 检查

- □ 是否存在 N+1 查询？（循环内调 Repo 方法？）
- □ 是否有未带超时的 DB/网络调用？
- □ 是否有不必要的大对象创建/拷贝？
- □ 是否有可批量化但未批量化的操作？
- □ Ent 查询是否用 `.Select()` 限制字段？
- □ 分页查询是否正确？（offset/limit？）
- □ 是否有慢查询风险？（全表扫描、缺少索引？）

## 维度 5：安全性审查（后端）

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| CS-B11 | 外部输入必须校验后才进入 biz 层 |
| CS-B12 | 敏感字段（key/secret/token）禁止日志输出 |
| Proto 必填 | `(google.api.field_behavior) = REQUIRED` 标记必填 |
| MCP 安全 | A13：MCP Broker `AllowAdHocHTTP` 默认 false |

### B 面：Review 检查

- □ 外部输入是否在 Service 层校验后才传入 biz？
- □ 是否有 SQL 注入风险？（Raw SQL 是否参数化？）
- □ 敏感字段是否在日志中暴露？（key/secret/token？）
- □ API 是否有鉴权中间件保护？
- □ 是否有未授权的数据访问？（跨租户/跨用户？）
- □ MCP Broker 安全边界是否正确？（AllowAdHocHTTP？）

## 维度 6：可测试性审查

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| CS-B13 | 核心业务 Usecase 必须有单元测试，覆盖率 ≥ 70% |
| CS-B14 | 错误路径必须有测试用例覆盖 |
| CS-F5 | 核心业务 Store/composable 必须有单元测试 |
| 依赖注入 | Wire DI：构造函数接收接口，便于 mock |
| 接口隔离 | 窄接口便于 mock：CS-B4 Repo 方法 ≤ 5 |

### B 面：Review 检查

- □ 核心业务逻辑是否有单元测试？
- □ 测试是否覆盖错误路径？（不仅是 happy path？）
- □ 依赖是否通过接口注入？（能否 mock？）
- □ 测试是否隔离？（无 DB/网络依赖？）
- □ 前端 Store/composable 是否有测试？
- □ 测试命名是否清晰？（TestXxx_HappyPath / TestXxx_ErrorCase？）

## 维度 7：可维护性审查

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| CS-B17 | 技术债务用 `// TODO(debt):` 标记，含 issue 编号和预期偿还时间 |
| CS-F8 | 前端技术债务用 `// TECH-DEBT:` 标记，含 issue 编号 |
| 模块化 | 复杂逻辑拆分为小的、可复用的函数/类 |
| 端口设计 | 接口定义在 biz，Wire 绑定在 Service，返回值用 biz 类型 |

### B 面：Review 检查

- □ 复杂逻辑是否拆分为小函数？（有无超 80 行函数？）
- □ 技术债务是否标记？（`// TODO(debt):` 或 `// TECH-DEBT:`？）
- □ 本次修改的影响范围是否可控？
- □ 是否引入了新的技术债务？（有无偿还计划？）
- □ 接口是否稳定？（频繁变更的接口是否需要重新设计？）

## 维度 8：错误处理与鲁棒性

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| 红线 #9 | 所有 `go func()` 必须走 `pkg/safego` |
| CS-B1 | 禁止 `log/slog`，统一 `pkg/loggateway.Logger` |
| kerrors | 红线 #14（SKILL）：biz 层禁止 `fmt.Errorf` 返回业务错误 |
| CS-B15 | 重试次数上限 3 次，必须指数退避 |
| CS-B16 | 写操作必须保证幂等 |
| CS-B3 | 压缩操作必须通过 CAS + 事务保证原子性 |
| ctx 传递 | 所有跨层调用必须传递 `ctx` |

### B 面：Review 检查

- □ goroutine 是否走 safego？（有无裸 `go func()`？）
- □ 业务错误是否用 kerrors？（有无 `fmt.Errorf` 返回业务错误？）
- □ 错误是否吞掉？（`_ = someFunc()` 忽略 error？）
- □ 错误信息是否清晰有用？（便于排查？）
- □ 重试逻辑是否合理？（上限 3 次？指数退避？）
- □ 写操作是否幂等？
- □ 日志是否用 loggateway.Logger？（有无 log/slog 残留？）
- □ 共享状态是否有锁保护？

## 维度 9：前端性能

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| 虚拟滚动 | 大列表用 `q-virtual-scroll` 或第三方虚拟滚动 |
| 懒加载 | 路由级代码分割（`() => import()`） |
| 响应式优化 | 大对象用 `shallowRef` / `markRaw` 避免深度响应式 |
| 计算属性 | 复杂计算用 `computed` 缓存，避免模板内计算 |
| Store 按需 | `storeToRefs` 只解构需要的字段 |

### B 面：Review 检查

- □ 是否有全量数据加载？（应分页/虚拟滚动？）
- □ 是否有不必要的深度响应式？（大对象应用 shallowRef？）
- □ 是否有重复请求？（同一数据多处 fetch？应合并到 Store？）
- □ v-for 是否有 :key？
- □ 组件是否按需加载？（路由级代码分割？）
- □ 是否有内存泄漏风险？（定时器/事件监听未清理？）

## 维度 10：前端安全

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| XSS 防护 | 禁止 `v-html` 渲染用户输入；Markdown 渲染需 sanitize |
| CSRF | API 调用经 `services/index.ts` 统一处理 |
| 敏感数据 | Token/密钥不存 localStorage（用 sessionStorage 或内存） |
| 类型安全 | CS-F6：禁止 `any` 类型 |

### B 面：Review 检查

- □ 是否有 `v-html` 渲染用户输入？（XSS 风险？）
- □ 敏感数据是否安全存储？
- □ API 调用是否经统一 Service 层？
- □ 是否有硬编码的密钥/Token？
- □ 是否有未类型化的数据流？（`any` 类型？）

## 维度 11：业务逻辑审查

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| 领域模型 | biz 层纯 Go struct，字段用基本类型，不用 proto 类型 |
| 业务规则 | 复杂业务规则封装为 Usecase 方法，不散落在 Service/Data |
| 交叉参考 | 开发前必须读 `docs/module-cross-reference.md` |
| 事件一致性 | 新增 Envelope 类型必须同步前端 dispatcher |

### B 面：Review 检查

- □ 业务规则是否正确实现？（与产品需求/PRD 一致？）
- □ 业务逻辑是否在正确的层？（Usecase vs Service vs Data？）
- □ 领域模型是否准确反映业务概念？
- □ 是否有业务层面的风险/漏洞？
- □ 交叉参考手册是否已检查？（上下游影响？）
- □ 新增事件类型是否同步前端？

## 维度 12：文档同步更新

### A 面：编码预防

| 规则 | 说明 |
|------|------|
| 交叉参考 | 新增/修改 biz 接口、共享类型、事件类型、DB Schema 时必须同步交叉参考手册 |

### B 面：Review 检查

- □ 新增/修改 biz 接口是否同步交叉参考手册？
- □ 新增/修改共享类型是否同步影响表？
- □ 新增/修改事件类型是否同步前端 dispatcher？
- □ 新增/修改 DB Schema 是否同步交叉参考？
- □ Proto 变更是否同步前端 api.ts？
- □ 新增 Store 是否在 stores/index.ts 导出？

## 一、模块全景

项目的日志体系由两套并行系统构成：

| 系统 | 包路径 | 定位 | 输出目标 |
|------|--------|------|----------|
| **loggateway** | `pkg/loggateway` | 通用结构化日志（替代 `log/slog`，红线 #10） | zap → 文件(lumberjack) + stdout |
| **Flow Log** | `internal/event` | 业务流程步骤追踪（chat turn、agent 构建、LLM 调用等生命周期） | EventBus → WS 推送 + JSONL 落盘 + DB 持久化 |

两者通过 `EnvelopeTypeLog` / `EnvelopeTypeFlowLog` 在事件总线层面汇合，最终由 `FlowFileAppender` 统一落盘。

## 二、已发现的业务逻辑 Bug

### Bug #1：`loggerWith` 双重 `withBase` 导致字段重复追加

**严重性**：🟡 中（当前不触发，但代码逻辑错误）

**位置**：`pkg/loggateway/gateway.go:289-303`

**问题代码**：

```go
func (l *loggerWith) Debug(msg string, fields ...Field) {
    l.g.Debug(msg, l.g.withBase(append(l.base, fields...))...)
}
```

**问题链路**：

1. `loggerWith.Debug` 先调用 `l.g.withBase(append(l.base, fields...))` → 追加 `g.base`
2. 然后调用 `l.g.Debug(msg, result...)` → `Gateway.Debug` 内部再次调用 `g.withBase(fields)` → **再次追加 `g.base`**

**影响**：当 `Gateway.base` 非空时（虽然当前 `New()` 创建的 Gateway `base` 始终为空），`With()` 返回的 `loggerWith` 调用日志方法会导致 `g.base` 字段被重复追加。

**解决方案**：

`loggerWith` 的日志方法应直接调用 `l.g.logger.Debug(msg, all...)` 而非 `l.g.Debug(msg, all...)`，避免二次 `withBase`：

```go
func (l *loggerWith) Debug(msg string, fields ...Field) {
    all := make([]Field, 0, len(l.base)+len(fields))
    all = append(all, l.base...)
    all = append(all, fields...)
    l.g.logger.Debug(msg, l.g.withBase(all)...)
}
```

或更简洁地，让 `loggerWith` 跳过 `Gateway.Debug` 的 `withBase`，直接写 `l.g.logger`：

```go
func (l *loggerWith) Debug(msg string, fields ...Field) {
    all := make([]Field, 0, len(l.base)+len(fields))
    all = append(all, l.base...)
    all = append(all, fields...)
    l.g.logger.Debug(msg, all...)
}
```

### Bug #2：`busHook.onWrite` 使用 `f.Interface` 丢失类型化字段值

**严重性**：🔴 高（激活桥接后所有字段值为 nil）

**位置**：`pkg/loggateway/bus_hook.go:40-41`

**问题代码**：

```go
for _, f := range fields {
    meta[f.Key] = f.Interface  // ❌ 类型化字段值为 nil
}
```

**问题**：zap 的 `Field` 结构体对类型化字段（`zap.String`、`zap.Int`、`zap.Int64` 等）将值存储在 `Field.String` / `Field.Integer` 中，而非 `Field.Interface`。只有 `zap.Any` 等少数类型才会设置 `Interface`。

**影响**：当 `SetBusPublish` 被激活后，通过 `loggateway.StepID("xxx")`、`loggateway.SessionID("yyy")`、`loggateway.Err(err)` 等构造的字段，在桥接到事件总线时 **值全部丢失为 nil**。

**解决方案**：使用 `zapcore.NewMapObjectEncoder()` 正确序列化字段：

```go
func (h *busHook) onWrite(entry zapcore.Entry, fields []zap.Field) {
    h.mu.RLock()
    pub := h.publish
    threshold := h.hookLevel
    h.mu.RUnlock()

    if pub == nil || entry.Level < threshold {
        return
    }

    enc := zapcore.NewMapObjectEncoder()
    for _, f := range fields {
        f.AddTo(enc)
    }
    enc.Fields["level"] = entry.Level.String()
    enc.Fields["ts"] = entry.Time.Format(time.RFC3339Nano)

    pub(EnvelopeLog{
        Level:     entry.Level.String(),
        Message:   entry.Message,
        Fields:    enc.Fields,
        Timestamp: entry.Time,
    })
}
```

### Bug #3：`SetBusPublish` 已实现但从未调用——桥接机制形同虚设

**严重性**：🔴 高（loggateway 日志无法到达前端 Monitor 面板）

**位置**：`pkg/loggateway/gateway.go:219`

**问题描述**：`SetBusPublish(fn)` 方法允许将 loggateway 的日志输出桥接到事件总线，但 **整个代码库中没有任何调用点**。`busHook.publish` 始终为 nil，`onWrite` 中的 `if pub == nil` 检查总是返回。

**影响**：

- loggateway 的日志写入只输出到文件/stdout，不会自动发布到事件总线
- 旧体系 `SysLog*` 函数通过 `emitSystem()` 直接发布到 MonitorBus，新体系的桥接未启用
- 前端 Monitor 面板无法收到通过 `loggateway.Logger` 写入的日志
- 形成了"红线要求用 loggateway，但业务上仍需 Flow Log/SysLog* 才能被前端看到"的矛盾

**解决方案**：

在 `cmd/admin/main.go` 的 `BeforeStart` 中激活桥接：

```go
kratos.BeforeStart(func(ctx context.Context) error {
    if eventInfra != nil {
        event.BindInfra(eventInfra)

        // 激活 loggateway → EventBus 桥接
        if gw, ok := lg.(*loggateway.Gateway); ok {
            gw.SetBusPublish(func(env loggateway.EnvelopeLog) {
                envelope := event.NewEnvelope(event.EnvelopeTypeLog, "system", "")
                envelope.Channel = "monitor"
                envelope.Content = &event.EnvelopeContent{
                    Text:       env.Message,
                    IsPartial:  false,
                }
                envelope.Metadata = env.Fields
                eventInfra.Publish(context.Background(), envelope)
            })
        }
    }
    return nil
})
```

> **前提**：必须先修复 Bug #2，否则桥接后字段值全部为 nil。

## 三、两套系统的关系与冲突

### 当前状态

```
┌──────────────────────────────────────────────────────────────┐
│                    日志双轨制现状                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  loggateway.Logger                    Flow Log (TraceEmitter)│
│  ├─ lg.Info/Warn/Error(...)           ├─ emitter.LogDone(...)│
│  ├─ lg.With(SessionID).Info(...)      ├─ emitter.LogError(.) │
│  └─ 输出: 文件 + stdout               └─ 输出: EventBus     │
│       │                                     │                │
│       │  (SetBusPublish 未激活)              │                │
│       │  ❌ 不到达前端                       │ ✅ 到达前端     │
│       │                                     │                │
│  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─  │
│                                              │                │
│  SysLog* (Deprecated) ──────────────────────→│                │
│  ├─ 仅剩 bus.go 3 处调用                      │                │
│  └─ 直接调 bus.Publish()                     │                │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 核心矛盾

| # | 矛盾 | 说明 |
|---|------|------|
| 1 | loggateway 是红线 #10 指定的唯一日志 API | 但它的输出不到达前端 Monitor 面板 |
| 2 | Flow Log 系统能到达前端 | 但它不是通用日志 API，而是业务流程追踪专用 |
| 3 | SysLog* 废弃函数仍被 bus.go 使用 | 形成了"废弃但不可删"的僵局 |
| 4 | 两套系统各自独立落盘 | loggateway 写 `aranea.log`，FlowFileAppender 写 `flow-*.jsonl`/`log-*.jsonl`，同一事件可能被记录两次 |

### 两套系统对比

| 维度 | Flow Log 系统 (`internal/event`) | loggateway (`pkg/loggateway`) |
|------|----------------------------------|-------------------------------|
| **定位** | 业务流程追踪（chat turn、agent 构建、LLM 调用等步骤的生命周期） | 通用结构化日志（替代 `log/slog`，项目红线 #10） |
| **输出目标** | EventBus → WS 推送 + FlowFileAppender 落盘 + DB 持久化 | zap → 文件（lumberjack）+ stdout |
| **数据格式** | FlowLogEntry（结构化，含 Correlation/Step/Severity/Timing） | zap JSON（标准日志格式） |
| **消费者** | 前端 Monitor 面板、FlowFileAppender、flowLogPersistConsumer | 运维人员、日志聚合系统 |
| **传输通道** | EnvelopeTypeFlowLog → MonitorBus | hookedCore → busHook → SetBusPublish（预留桥接） |
| **调用方式** | `TraceEmitter.LogStart/Done/Error` 或 `CtxFlowLog*` | `lg.Info/Warn/Error(msg, loggateway.StepID(...))` |

## 六、解决方案：从架构、设计、业务场景与业务需求出发

### 6.1 架构层：双系统定位与桥接

#### 6.1.1 核心判断：保持双系统，激活桥接

**不合并** loggateway 与 Flow Log，原因：

| 维度 | loggateway | Flow Log |
|------|-----------|----------|
| **回答的问题** | "发生了什么"（What happened） | "进行到哪了"（How it progressed） |
| **数据模型** | 扁平 zap JSON（msg + fields） | 结构化 FlowLogEntry（Correlation + Step + Severity + Timing + Span） |
| **生命周期** | 无状态，单次写入 | 有状态，Start → Done/Error/Skip + 自动计时 + Span 追踪 |
| **消费者** | 运维、日志聚合（ELK/Loki） | 前端 Monitor 面板、AI 排障、Trace 瀑布图 |
| **调用模式** | `lg.Info/Warn/Error` — 任意位置 | `emitter.LogStart/LogDone/LogError` — 仅在 Turn 上下文中 |

合并会丢失 Flow Log 的生命周期语义（Start/Done 计时、Span 追踪、TraceID 关联），或让 loggateway 承担不属于它的复杂度。

**激活桥接**是正确方向：loggateway 的输出通过 `SetBusPublish` 自动进入 EventBus，作为 `EnvelopeTypeLog` 到达前端，与 `EnvelopeTypeFlowLog` 互补。

#### 6.1.2 目标架构

```

│                     统一日志架构（目标状态）                       │
├──────────────────────────────────────────────────────────────────┤

│  │                     │     │                             │    │
```

#### 6.1.3 开发者决策树：该用哪个 API？

```
你要记录什么？
│
├─ 业务流程步骤（有开始/结束生命周期、需要计时、需要 Trace 关联）
│   → TraceEmitter.LogStart/LogDone/LogError
│   → CtxFlowLogWarn/Done/Error（深层调用）
│   → 前端 Monitor 面板可见
│
├─ 通用结构化日志（错误、警告、状态变更、降级通知）
│   → loggateway.Logger.Info/Warn/Error
│   → 激活桥接后前端 Monitor 面板可见（EnvelopeTypeLog）
│   → 始终写入 aranea.log（运维可查）
│
├─ 步骤计时（不需要 Trace 关联，只需记录耗时）
│   → loggateway.Logger.BeginStep → Step.Done/Warn/Error
│   → 仅写入 aranea.log（激活桥接后到达前端）
│
└─ 系统域通知（启动、关闭、全局事件）
    → loggateway.Logger.Info/Warn/Error + loggateway.StepID("system.xxx")
    → 激活桥接后作为 EnvelopeTypeLog 到达前端
    → 不再使用 SysLog*（废弃函数将在迁移后删除）
```

### 6.2 设计层：Bug 修复与桥接激活

#### 6.2.1 Phase 1 — 修复 Bug（前置条件）

**Bug #2 修复**：`busHook.onWrite` 字段值丢失

这是激活桥接的前置条件。当前 `f.Interface` 对 `zap.String`/`zap.Int` 等类型化字段返回 nil，激活桥接后所有字段值将为空。

修复方案：使用 `zapcore.NewMapObjectEncoder()` 正确序列化所有 zap 字段类型：

```go
func (h *busHook) onWrite(entry zapcore.Entry, fields []zap.Field) {
    h.mu.RLock()
    pub := h.publish
    threshold := h.hookLevel
    h.mu.RUnlock()

    if pub == nil || entry.Level < threshold {
        return
    }

    enc := zapcore.NewMapObjectEncoder()
    for _, f := range fields {
        f.AddTo(enc)
    }
    enc.Fields["level"] = entry.Level.String()
    enc.Fields["ts"] = entry.Time.Format(time.RFC3339Nano)

    pub(EnvelopeLog{
        Level:     entry.Level.String(),
        Message:   entry.Message,
        Fields:    enc.Fields,
        Timestamp: entry.Time,
    })
}
```

**Bug #1 修复**：`loggerWith` 双重 `withBase`

`loggerWith` 的日志方法调用 `l.g.Debug(msg, l.g.withBase(append(l.base, fields...))...)` 导致 `g.base` 被追加两次。当前 `g.base` 为空不触发，但代码逻辑错误应修正。

修复方案：`loggerWith` 直接写 `l.g.logger`，跳过 `Gateway.Debug` 的 `withBase`：

```go
func (l *loggerWith) Debug(msg string, fields ...Field) {
    all := make([]Field, 0, len(l.base)+len(fields))
    all = append(all, l.base...)
    all = append(all, fields...)
    l.g.logger.Debug(msg, l.g.withBase(all)...)
}
```

对 `Info`/`Warn`/`Error` 方法做同样修复。

#### 6.2.2 Phase 2 — 激活桥接

在 `cmd/admin/main.go` 的 `BeforeStart` 中激活 `SetBusPublish`：

```go
kratos.BeforeStart(func(ctx context.Context) error {
    if eventInfra != nil {
        event.BindInfra(eventInfra)

        if gw, ok := lg.(*loggateway.Gateway); ok {
            gw.SetBusPublish(func(env loggateway.EnvelopeLog) {
                sessionID, _ := env.Fields["session_id"].(string)
                envelope := event.NewEnvelope(event.EnvelopeTypeLog, "system", sessionID)
                envelope.Channel = "monitor"
                envelope.Content = &event.EnvelopeContent{
                    Text:      env.Message,
                    IsPartial: false,
                }
                envelope.Metadata = env.Fields
                eventInfra.Publish(context.Background(), envelope)
            })
        }
    }
    return nil
})
```

**设计要点**：

| 要点 | 说明 |
|------|------|
| 从 `env.Fields` 提取 `session_id` | loggateway 的 `With(loggateway.SessionID(sid))` 绑定的 session_id 会被提取到 Envelope 的 SessionID 字段，使前端可按会话过滤 |
| `envelope.Channel = "monitor"` | 与 FlowLog 的系统域路由一致，确保 WS Monitor 连接能收到 |
| `envelope.Author = "system"` | 标识来源为 loggateway 桥接，与 FlowLog 的 "system"/"chat"/"team" 域区分 |
| 使用 `context.Background()` | 桥接回调在 zap Write 链路中执行，不应继承请求 ctx |

### 6.3 业务场景层：场景与 API 映射

#### 6.3.1 场景 1：Chat Turn 执行追踪

**业务需求**：前端 Monitor 面板需要实时展示 Chat Turn 的执行进度（构建 Agent → 加载插件 → 创建 Runner → 调用 LLM → 保存回复），每步有计时，支持 Trace 瀑布图。

**当前方案**：`TraceEmitter.LogStart/LogDone/LogError` — 正确，无需改动。

**桥接补充**：Turn 过程中的非步骤日志（如 JSON 容错 Warn、降级通知）通过 `loggateway.Logger` 记录，激活桥接后自动到达前端 `EnvelopeTypeLog`，与 `EnvelopeTypeFlowLog` 在 `LogStreamPanel` 的 "进程日志" Tab 中展示。

#### 6.3.2 场景 2：系统域事件通知

**业务需求**：前端 Monitor 需要看到系统级事件（启动、关闭、总线丢弃、定时任务执行等），不关联特定 Session。

**当前问题**：旧体系通过 `SysLog*` → `emitSystem()` → `bus.Publish(EnvelopeTypeFlowLog, channel=monitor)` 到达前端。新体系 `loggateway.Logger` 的输出不到达前端。

**解决方案**：激活桥接后，`loggateway.Logger.Warn("...", loggateway.StepID("system.xxx"))` 自动作为 `EnvelopeTypeLog` 到达前端。`EnvelopeTypeLog` 与 `EnvelopeTypeFlowLog` 在前端 `LogStreamPanel` 的不同 Tab 中展示（"进程日志" vs "流程日志"），语义清晰。

#### 6.3.3 场景 3：运维排障

**业务需求**：运维人员通过 ELK/Loki 聚合日志，需要结构化 JSON、字段可检索、文件轮转。

**当前方案**：`loggateway.Logger` → zap JSON → lumberjack 文件轮转 — 正确，无需改动。

**注意**：激活桥接后，同一条日志会同时写入 `aranea.log`（lumberjack）和 `log-*.jsonl`（FlowFileAppender）。这是**有意为之**的双写：`aranea.log` 面向运维聚合，`log-*.jsonl` 面向前端 Monitor 和 AI 排障。两者格式不同（zap JSON vs FlowFileAppender 自定义 JSONL），消费者不同。

#### 6.3.4 场景 4：AI 排障与 Trace 回溯

**业务需求**：AI 排障需要按 TraceID 查询完整的执行时间线，包括步骤计时、Span 瀑布图、错误上下文。

**当前方案**：`TraceEmitter` 的 `spans` 数组 + `MetadataJSON()` 序列化为 usage metadata — 正确，无需改动。

**桥接补充**：`loggateway.Logger` 的日志通过桥接进入 `EnvelopeTypeLog`，由 `FlowFileAppender` 写入 `log-*.jsonl`，可被 AI 排障工具检索。但 `EnvelopeTypeLog` 不进入 `flowLogPersistConsumer`（不写 DB），避免与 `EnvelopeTypeFlowLog` 的结构化查询冲突。

#### 6.3.5 场景 5：事件总线丢弃通知

**业务需求**：当 EventBus 因背压丢弃消息时，需要通知前端 Monitor。

**当前方案**：`bus.go` 中 3 处 `SessionSysLogWarn` 调用 — 废弃但无法删除。

**解决方案**：Phase 3 迁移后，bus 持有 `loggateway.Logger`，丢弃通知通过 `b.lg.Warn(...)` 记录。激活桥接后自动到达前端。

#### 6.4.4 需求 4：运行时日志级别调整

| 维度 | 说明 |
|------|------|
| **业务需求** | 生产环境默认 info 级别，排查问题时需要临时切换到 debug 级别，不重启服务 |

```go
type Gateway struct {
    atomicLevel zap.AtomicLevel  // 新增：支持运行时修改
    core        zapcore.Core
    logger      *zap.Logger
    // ...
}

func New(c *conf.Logging) *Gateway {
    atomicLevel := zap.NewAtomicLevelAt(parseLevel(c.GetLevel(), zapcore.InfoLevel))
    core := zapcore.NewCore(encoder, ws, atomicLevel)  // 使用 atomicLevel 替代静态 level
    // ...
}

func (g *Gateway) SetLevel(level string) {
    if g == nil {
        return
    }
    g.atomicLevel.SetLevel(parseLevel(level, zapcore.InfoLevel))
```

#### 6.4.5 需求 5：高频日志采样

| 维度 | 说明 |
|------|------|
| **业务需求** | Agent 运行时的高频日志（stream delta、tool call progress）可能在并发场景下产生大量日志，导致磁盘 I/O 压力和 EventBus 背压 |
| **当前状态** | ❌ 无采样机制 |
| **解决方案** | 在 `busHook.onWrite` 中添加采样装饰器，对指定 StepID 前缀的日志进行限速 |

```go
type busHook struct {
    mu          sync.RWMutex
    hookLevel   zapcore.Level
    publish     func(env EnvelopeLog)
    sampler     *logSampler  // 新增
}

type logSampler struct {
    mu      sync.Mutex
    buckets map[string]*rate.Limiter  // stepID 前缀 → 限速器
}

func (s *logSampler) Allow(stepID string) bool {
    prefix := stepPrefix(stepID)
    s.mu.Lock()
    limiter, ok := s.buckets[prefix]
    if !ok {
        limiter = rate.NewLimiter(rate.Every(time.Second), 10)
        s.buckets[prefix] = limiter
    }
    s.mu.Unlock()
    return limiter.Allow()
}
```

### 6.6 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 激活桥接后日志量暴增，EventBus 背压 | Monitor WS 延迟、消息丢弃 | `hook_level` 配置控制桥接阈值（默认 info）；Phase 5 采样机制限速高频日志 |
| `EnvelopeTypeLog` 与 `EnvelopeTypeFlowLog` 在前端混淆 | 用户无法区分"流程日志"和"进程日志" | 前端 `LogStreamPanel` 已有双 Tab 设计（"流程日志"/"进程日志"），`kind: "flow"` vs `kind: "log"` 区分 |
| 桥接回调在 zap Write 链路中执行，可能阻塞日志写入 | 日志写入延迟 | `busHook.onWrite` 已有 `recover()` 保护；`EventBus.Publish` 使用 `BlockUpTo(100ms)` 策略，超时后降级为 DropOldest |
| `NewBus` 签名变更影响 Wire 注入 | 编译失败 | `NewBus` 在 `internal/event` 包内使用，Wire 注入的是 `*Infra`，不影响 `wire_gen.go` |
| 同一日志双写（aranea.log + log-*.jsonl） | 磁盘空间增加 | 两者面向不同消费者，格式不同；lumberjack 和 FlowFileAppender 各自独立轮转，磁盘占用可控 |

## 九、总结评分

| 评估维度 | 评分 | 说明 |
|----------|------|------|
| **架构设计** | ⭐⭐⭐⭐ | loggateway 作为统一日志门面的设计思路正确，接口简洁，与 Wire DI 集成良好 |
| **业务逻辑正确性** | ⭐⭐⭐ | 存在 2 个代码 Bug（`loggerWith` 双重 base、`f.Interface` 字段值丢失）和 1 个功能缺失（`SetBusPublish` 未激活） |
| **功能完整性** | ⭐⭐⭐ | 基础日志功能完善，但 loggateway → EventBus 桥接未激活导致前端不可见，且零单元测试 |
| **红线合规** | ⭐⭐⭐⭐⭐ | `log/slog` 禁令完全合规，构造函数注入覆盖率极高 |
| **代码卫生** | ⭐⭐⭐ | 存在死代码（`KratosLogger`/`ZapSugar`/`BeginStep`/`Step` 无调用者）和 3 处废弃函数残留 |

**核心结论**：loggateway 的架构设计合理，作为项目统一日志门面的定位正确。最关键的问题是 **loggateway → EventBus 桥接未激活**，导致通过 `loggateway.Logger` 写入的日志无法到达前端 Monitor 面板。激活桥接 + 修复字段值丢失 Bug 是最优先的改进项。
